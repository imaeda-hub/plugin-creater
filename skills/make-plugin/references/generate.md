# 段階「生成」

目的：よいと答えた内容で生成プラグインを作り、試験し、できたことを説明し、質問の改善案を示す。

- 以下の `<スキルのフォルダ>` は、「Base directory for this skill」のフォルダの絶対パスである。`<作業フォルダ>` は、ユーザーが Copilot CLI を動かしているフォルダの絶対パスである。
- コンパクションの後は、作業フォルダを見て続きを決める。`.plugin-creator-work/parts/manifest.json` がなければ1から、生成プラグインのフォルダがなければ3から、あれば4から続ける。

## 1. 部品の分け方を決める

高い推論力が要るので、自分で決める。

- 生成プラグインの名前（英小文字・数字・ハイフン。作業が分かる英語）と、1行の説明
- 入口のスキルの名前と description。description は日本語で、何ができあがるかを手順でない短い1句で書き、続けて呼ばれる場面（ユーザーが頼むときの言葉を入れる）と、呼ばれてはいけない似た頼み（例：その作業についての質問、プラグインの試験）を書く。手順の要約は書かない。
- どの手順をスクリプトにし、どこを AI に任せるか。決まった処理はスクリプトにし、推論が要ることだけを AI に任せる。
- 作業役の AI の数と呼び名（作業の定義の案と同じ）、要る MCP サーバー。合否の判定にコマンドの結果が要る基準は、成果物を書き換えない確かめのスクリプトを、確認役の AI の MCP のツールにする。
- 公開のプラグインを使うと決めた部分は作らない。

決めたら、次をする。

- `<作業フォルダ>/.plugin-creator-work/parts/manifest.json` を自分で書く。形：`{ "plugin_name", "plugin_description", "entry_skill": { "name", "description" }, "workers": [{ "agent", "label", "extra_tools": [] }], "verifier": { "extra_tools": [] }, "orchestrator": { "extra_tools": [] } }`。`extra_tools` は MCP のツール（`サーバー名/ツール名`）など、役ごとに足すツールである。
- シェルで次を写す。作業エージェントは文書や画像のファイルを写せないためである。
  - `.plugin-creator-work/draft/task.json` を `.plugin-creator-work/parts/task.json` に
  - 課題の実物の入力のファイルを `.plugin-creator-work/parts/files/tests/eval/<課題>/inputs/` に
  - 流用するファイルを `.plugin-creator-work/parts/files/` の下の、生成プラグインで使う場所に

## 2. 作業エージェントに書かせる

`task` ツールで `plugin-creator:worker` に頼む。作業エージェントは会話を見ていないので、次をすべて渡す。渡していないことは、生成プラグインに入らない。

- 作業フォルダ、`.plugin-creator-work/parts/`、ひな形（`<スキルのフォルダ>/assets/template/`）の絶対パス
- よいと答えたナレッジの一覧（番号、種類、項目、文、例、例外）
- 振る舞いの案と、1で決めた部品の分け方
- 試験の課題：頼むときの言葉、入力のファイルの場所、作業の画面に入れる設定の値、基準にするナレッジの番号と採点のしかた（文字や形で決まるものはプログラム、それ以外はモデル）、仮の入力のファイルの中身
- 流用する資産と写した場所、使うと決めた公開のプラグイン
- 作り直しなら、元のプラグインのフォルダ、引き継ぐことと変わること

量が多いときは、いくつかに分けて、1つずつ頼む。作業エージェントが足りないことを返したら、補って頼み直す。

## 3. 組み立て

1. `plugin-creator_state` で、ヒアリングの記録（state.json）の場所を見る。
2. 次を動かす。
   `python3 <スキルのフォルダ>/scripts/scaffold.py build --hearing <state.json の場所> --work <作業フォルダ>/.plugin-creator-work --out <作業フォルダ>/<生成プラグインの名前>`
3. 失敗したら、返った理由を作業エージェントに渡して直させ、もう一度動かす。この直しも、4の直しの回数に数える。
4. 終わると、生成プラグインのフォルダが git のリポジトリになり、`.plugin-creator-work/` は消える。

## 4. 試験と直し

1. `python3 <生成プラグインのフォルダ>/tests/run.py` を動かす。結果は `<生成プラグインのフォルダ>/tests/results/latest.json` にある。
2. 道具が足りないと出たら、`python3 <スキルのフォルダ>/../test-plugin/scripts/check_tools.py --plugin <生成プラグインのフォルダ>` で、足りない道具と、入れ方と、入れる場所を見て示す。入れてよいかを聞く（承認の問い。選択肢は「入れない」「入れてよい」の順）。よいと答えたら `--install` を付けて動かし、1に戻る。入れないと答えたら、試験をせずに5に進み、試験をしていないことを示す。
3. 不合格なら、落ちた試験とその理由を作業エージェントに渡し、生成プラグインのフォルダで直させる。ナレッジが抜けたときは、抜けたナレッジの文も渡す。
4. 直させたら、`python3 <スキルのフォルダ>/scripts/scaffold.py check-base --out <生成プラグインのフォルダ>` で、土台のファイルがひな形と同じかを見る。違えば不合格とし、`--restore` を付けて動かしてひな形から入れ直し、土台を変えずに直すよう作業エージェントに伝える。
5. 1に戻る。直しは3回までにする。3回直しても合格しないときは止め、残った不合格の試験とその理由を示す。
6. 合否は試験の結果で決める。自分でも作業エージェントでも、合否を決めない。
7. 試験が終わったら（合格しても、上限で止めても）、生成したときの印を付ける。直したところがあれば `git -C <生成プラグインのフォルダ> add -A` と `git -C <生成プラグインのフォルダ> commit -m "plugin-creator: 試験に合わせて直す"` でコミットし、続けて `git -C <生成プラグインのフォルダ> tag plugin-creator-generated` を動かす。後で、ユーザーが直したところを、この印からの差分で見分けるためである。
8. `plugin-creator_results` に結果のファイルの場所を渡し、クリエイターの画面に出す。

## 5. できたことの説明

次の6つを示す。言葉は `references/words.md` に従う。

1. 生成プラグインのフォルダの場所。入れ方と使い方は、そのフォルダの README.md にあること。
2. 組み込んだ仕事のやり方や決まり
3. 流用した資産。公開のプラグインを使うときは、その入れ方（`copilot plugin install <プラグイン>@<マーケットプレイス>`）
4. 生成プラグインが自分のリポジトリに Issue を起票できるようにする手順：GitHub に公開する。`plugin.json` の `repository` にそのリポジトリの URL を書き、生成プラグインを入れ直す。gh を入れて、`gh auth login` でログインする。
5. ファイルの形の検査と、動きの試験の結果（段階ごとの合否）
6. 試験のしかた：ファイルの形の検査と動きの試験は、生成プラグインのフォルダで `python3 tests/run.py` の1つのコマンドで動き、AI クレジットを使わない。試しに動かして採点する試験は、plugin-creator に試験を頼むと行われ、AI クレジットを使う。

作り直しのときは、元のプラグインから変わったことと、作り直したものを元のリポジトリに入れ替えるやり方（新しいフォルダの中身を、`.git` を除いて元のリポジトリに写してコミットする）も示す。元のプラグインのフォルダは変えていない。
