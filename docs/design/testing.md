# 試験の設計

クリエイターと生成プラグインを、どう試験するかを定める。

## 1. 前提

試験には次の2つがある。2章と11章は両方に共通で、3〜9章は開発の試験、10章はユーザーの試験について書く。

| 試験 | 目的 | 行う人と環境 |
| --- | --- | --- |
| 開発の試験 | クリエイターを開発する。クリエイターと、クリエイターが作った生成プラグインを試験し、クリエイターを採点する | AI が Claude Code で自律的に行い、人は結果を見る |
| ユーザーの試験 | ユーザーが、受け取った生成プラグインを試験する（[試験の要件](../specs/test-requirements.md)） | ユーザーが頼むと、クリエイターがユーザーの手元の Copilot CLI で行う |

- クリエイターと生成プラグインは Copilot CLI 向けだが、開発の試験は Claude Code だけで行う。開発のクラウド環境では、Copilot CLI を動かす試験は行わない。Copilot CLI での確かめは、最終確認で、人が手元の Copilot CLI で行う（9章）。

## 2. 試験の段階

| 段階 | 確かめること | やり方 |
| --- | --- | --- |
| 1 構造の検査 | 設定ファイル、ファイルの置き場所、フロントマターが正しいか | 公式のスキーマと公式ドキュメントの決まりで検査する |
| 2 部品の試験 | スクリプト、フック、MCP サーバーなどが正しく動くか | 部品を直接動かし、正常な入力と異常な入力で確かめる |
| 3 EVAL | 必要な場面で呼ばれ、期待する成果物を作れるか | 実際のモデルで課題を実行して採点する。プラグインあり・なしで同じ課題を繰り返し実行し、スコアを比べる |

- 開発の試験とユーザーの試験は、同じ3段階で行う。1・2段目は、同じ仕組みを使う（10.2）。
- 1・2段目はモデルを使わないので、費用がかからず、結果も毎回同じになる。
- 1段目では、Agent Plugins の公式スキーマを手元に写して使う。カスタムエージェントの項目は、Copilot CLI のコマンドリファレンスとカスタムエージェントの設定リファレンスとで一部違うので、両方を認める。
- 生成プラグインの1段目では、生成前の確認でよいと答えたナレッジが、すべて入っているかも確かめる（10.3）。クリエイター自身の1段目では、会話例の版も確かめる（6.6）。
- 2段目では、たとえば次のように部品を動かす。
  - フック：標準入力に JSON を渡し、標準出力の JSON と終了コードを確かめる。入力の形は Copilot CLI と Claude Code で違う（例：エージェント名が `agentName` と `agent_type`）ので、両方の形で確かめる。
  - MCP サーバー：単体で起動し、MCP のクライアント（MCP 公式の Inspector の CLI モードなど）からツールを呼ぶ。
  - Web管理画面：エクステンションの中心の処理と画面を、偽物のつなぎ口（テストのフォルダに置く）につないで動かし、ブラウザーを操作するプログラム（Playwright）で、人と同じ操作をして確かめる。エージェントの状態は、本物のエージェントを動かさず、偽物のつなぎ口から用意したイベントを流して確かめる。開始や止めるの操作が、つなぎ口への正しい呼び出しになるかも確かめる（[生成プラグインの構造](generated-plugin-structure.md) 3.2、10章）。つなぎ口そのものは、最終確認で確かめる（9章）。

## 3. 試験は2重になる

クリエイターの出力は生成プラグインである。生成プラグインが正しいかは、その生成プラグインをさらに試験して確かめる。

```text
外側の試験（クリエイターを試す）
  模擬した会話 ──▶ クリエイター ──▶ 生成プラグイン
                                        │
内側の試験（生成プラグインを試す）        ▼
  分野の課題 ─────────────────▶ 生成プラグイン ──▶ 成果物
```

| 段階 | 外側（クリエイター） | 内側（生成プラグイン） |
| --- | --- | --- |
| 1 構造の検査 | クリエイターのファイル（会話例の版を含む） | できた生成プラグインのファイル |
| 2 部品の試験 | クリエイターのスクリプト、クリエイターの画面など | 生成プラグインのスクリプト、フック、MCP サーバー、Web管理画面 |
| 3 EVAL | 模擬した会話を入力し、生成プラグインを作らせる | 分野の課題を入力し、成果物を作らせる |

1・2段目の仕組みは、外側と内側で同じものを使う。

試験は次の順に進める。

1. クリエイターに、1・2段目の試験を行う。
2. クリエイターを Claude Code 向けに置き換え、外側の EVAL を行う。生成プラグインができる。
3. できた生成プラグインに、1・2段目の試験を行う。
4. 生成プラグインを Claude Code 向けに置き換え、内側の EVAL を行う。
5. 1〜4の結果から、クリエイターを採点する。

模擬ユーザーやユーザー役を変えたときは、先にユーザー役の試験（6.2）を行う。

## 4. Claude Code 向けの置き換え

3段目は Claude Code で実行するため、プラグインを Claude Code が読み込める形に置き換えてから試す。

| 部品 | Copilot CLI 向けの形 | Claude Code 向けの形 |
| --- | --- | --- |
| マニフェスト | 直下の `plugin.json` | `.claude-plugin/plugin.json` |
| スキル | `skills/<名前>/SKILL.md` | 同じ場所。フロントマターの `allowed-tools` や本文に書いたツール名を、Claude Code の名前にそろえる |
| MCP サーバー | `mcp.json` | `.mcp.json`。サーバー本体は同じで、設定の書き方（`${PLUGIN_ROOT}` を `${CLAUDE_PLUGIN_ROOT}` にするなど）を置き換える |
| カスタムエージェント | `com.github.copilot/agents/` | `agents/` のサブエージェント。`tools` の別名（`read`、`edit`、`execute`、`search` など）と MCP のツール（`サーバー名/ツール名`）を Claude Code の名前（`Read`、`Edit` と `Write`、`Bash`、`Grep` と `Glob`、`mcp__plugin_<プラグイン名>_<サーバー名>__<ツール名>`）にし、モデル名を置き換える |
| フック | `com.github.copilot/hooks/hooks.json` | `hooks/hooks.json` の形。イベント名（`subagentStart` → `SubagentStart` など）、コマンドの項目（`bash` → `command`）、`${PLUGIN_ROOT}` を置き換える |
| インストラクション | `com.github.copilot/rules/` | Claude Code では、プラグインの直下に置いた CLAUDE.md は読み込まれない。EVAL の課題の側で、指示として足す |
| エクステンション | `com.github.copilot/extensions/<名前>/` | Claude Code にはない。置き換えた版から外し、試験の仕組みが Agent SDK 用のつなぎ口を持って、同じ中心の処理と画面を動かす（下） |

- ツール名は、Copilot CLI の公式ドキュメント（フックのリファレンス）にある対応表に従う。例：`bash` → `Bash`、`view` → `Read`、`ask_user` → `AskUserQuestion`、`task` → `Agent`。
- 本文の中のツール名は、バッククォートで囲んだもの（`` `task` `` など）と、`ask_user` のような普通の単語と紛れない名前だけを置き換える。そのため、SKILL.md やエージェントの本文では、ツール名をバッククォートで囲んで書く。
- モデル名は、Claude Code で使える名前にする。Claude 以外のモデルは、Claude Code では使えない。次の決まりで置き換える。
  - カスタムエージェントの `model`（1つ、または優先する順のリスト）は、Claude Code の `model` 1つにする。候補の中に Claude のモデルがあれば、最初のものを Claude Code の ID にする（例：`claude-haiku-5.5` → `claude-haiku-5-5`）。
  - 候補に Claude のモデルがなければ、Copilot の価格表で同じ値段の Claude のモデルにする（例：`gpt-6-luna` → `claude-haiku-5-5`）。この対応は、変換スクリプトに表として持つ。
  - `model-policy` は Claude Code にないので外す。`reasoningEffort` は `effort` にする。
- メインのエージェントのモデルは、試験の仕組みが決める。Copilot CLI ではプラグインからメインのエージェントのモデルを決められないので、Claude Code のプラグインの `settings.json` の `agent`（プラグインのエージェントをメインにする設定）は使わない。使うと、Copilot CLI にない振る舞いを試すことになる。
- Claude Code では、サブエージェントは質問のツール（`AskUserQuestion`）を使えない。クリエイターは、ユーザーへの質問をメインのエージェントだけで行うので（[クリエイターの構造](creator-structure.md) 3.2）、置き換えてもこの点の振る舞いは変わらない。
- 生成プラグインの Web管理画面は、エクステンションの中で動く（[生成プラグインの構造](generated-plugin-structure.md) 4.1）。エクステンションは、Copilot CLI とつなぐ薄いつなぎ口と、Copilot CLI に依らない中心の処理と画面に分かれている（同 3.2）。開発の試験では、試験の仕組みが Agent SDK 用のつなぎ口を持ち、生成プラグインの中心の処理と画面をそのまま動かす。
  - 画面を開くツールと記録のツールは、試験の仕組みが、試すエージェントに MCP のツールとして出す。
  - 開始では、統括のエージェントの定義（指示とモデル）で、Agent SDK の別の実行を始める。作業・検証のモデルは、置き換えたエージェントの定義の `model` を、画面で選んだモデルにしてから始める。
  - 止めるでは、Agent SDK の実行を中断する。
  - 状態は、Agent SDK のフックとメッセージ（サブエージェントの開始と終わり、ツールの使用）から作る。
  - つなぎ口が違うので、Copilot CLI とのつなぎ（統括の起動、モデルの上書き、取り消し、イベント）は、開発の試験では確かめられない。最終確認で確かめる（9章）。
- 置き換えは、変換スクリプトで行う。毎回同じ結果になるようにするためである。変換スクリプトも2段目で試験する。
- 置き換えた版は、`claude plugin validate` で Claude Code に読み込めることを確かめてから試す。警告（作者の情報がないなど）は不合格にしない。
- 置き換えた版を試すので、結果は Copilot CLI での振る舞いと完全には一致しない。特に、スキルが呼ばれる場面や、エージェントへの仕事の割り振りは、ツールが違うと変わりうる。質問のツールも、Claude Code では選択肢が必要で、Copilot CLI では自由に答えられるので、質問のしかたが少し変わる。作業エージェントも Claude のモデルで動くので、本来のモデル（GPT-6 Luna など）で書いたときの出来は、この試験では分からない。

## 5. EVAL を実行する仕組み

- ここでは、開発の試験の EVAL の仕組みを書く。ユーザーの試験の EVAL は、Copilot SDK で動かす（10.4、10.5）。
- 外側と内側の EVAL は、Agent SDK（Claude Code をプログラムから動かす公式の部品）を使った、同じ自作の仕組みで実行する。
- Claude Code の `claude plugin eval` は使わない。公式ドキュメントに、ユーザー役が質問に答える仕組みも、実行中にブラウザーを操作する仕組みも見当たらないためである。
- 実行のたびに、まっさらな作業フォルダで始め、試すプラグインだけを読み込む。プラグインなしで比べるときは、何も読み込まない。
- 試されるエージェントは、次のように隔離する。
  - 環境変数は、必要なもの（パス、プロキシと証明書、モデルの接続先）だけを渡し、実行のたびに一時的なホームフォルダを使う。試験する側のセッションの設定が混ざると振る舞いが変わり、資格情報が混ざると試されるコードから見えてしまうためである。
  - ユーザー設定とプロジェクト設定は読み込ませない。
  - コマンドは OS のサンドボックスで動かし、書き込みを作業フォルダに限る。ファイルの書き込みのツールも、作業フォルダの中だけを許す。サンドボックスがないと、エージェントが自分の判断で作業フォルダの外に作業を移すことがあるためである。
  - 生成プラグインの Web管理画面を操作するスクリプトだけは、パスを指定してサンドボックスの外で動かす。Linux のサンドボックスの中では、コマンドごとに専用の localhost を持つので、中で起動した画面にはブラウザーからつながらないためである。
- 普段のツールと、試すプラグインの MCP サーバーのツールは、あらかじめ許可する。許可を求める仕組みに回すのは、ユーザー役が答える質問だけにする。裏で動くサブエージェントの許可の求めは、受け付けられずに失敗することがあるためである。
- 使われたスキル、サブエージェントとそのモデルは、Agent SDK の実行の記録から採点に使う。

## 6. 外側の EVAL

### 6.1 模擬した会話

- 人間との会話は、ユーザー役の AI で模擬する。
- ユーザー役には、模擬ユーザーごとに、依頼の内容と、その人が持っているナレッジを渡す。ナレッジごとに、答える条件と、自分から話すかどうかを決める。聞かれないと話さないナレッジ（当たり前すぎて話されにくいこと、すでに持っている資産）は、具体的に聞かれたときだけ答える条件にする。
- 答える条件は、人ならどう答えるかを考えて決める。狭く書きすぎると、人なら答える質問にも答えない（6.4）。
- ユーザー役は、クリエイターに聞かれたことだけに答える。ナレッジにないことは「特に決まっていません」と答え、推測で決まりを作らない。
- ユーザー役には、それまでのやり取りも渡す。「その2つ以外は？」のように、前の答えを指す質問に答えるためである。
- ユーザー役は、自分への指示（答える条件など）のことを話さない。人はそう話さないうえ、クリエイターに手がかりを与えるためである。
- クリエイターからの質問には、試験の仕組みが、ユーザー役の答えを返す。クリエイターが質問のツールを使わずに、文章で質問して手番を終えたときも、ユーザー役の答えを次の発言として返す。

### 6.2 ユーザー役の試験

ユーザー役が、話すべきでないことを話したり、ナレッジにないことを作ったりすると、EVAL の結果が変わる。そのため、模擬ユーザーやユーザー役（モデルや指示）を作ったり変えたりしたときは、外側の EVAL に使う前に、ユーザー役だけを試験する。クリエイターは動かさず、模擬ユーザーごとに決めた質問を、ユーザー役に直接聞く。

| 観点 | 聞くこと | 合格の条件 |
| --- | --- | --- |
| 漏らさない | 「守らないと困ることはありますか？」のような大まかな質問 | 聞かれないと話さないナレッジを話さない |
| 答える | ナレッジごとの具体的な質問 | そのナレッジを答える |
| まとめて答える | いくつかのことを1つにまとめた質問 | 聞かれたことをすべて答える |
| 作らない | ナレッジにないこと | 「特に決まっていません」と答える |
| 前の話を踏まえる | 前の答えを指す質問 | 前の答えに沿って答える |
| 選択肢で済ませない | 選択肢のついた質問 | 選択肢の言葉だけでなく、具体的に答える |
| 指示のことを話さない | すべての質問 | 答える条件など、自分への指示のことを話さない |

- 同じ質問を何回か聞き、割合で見る。
- ユーザー役のモデルと指示は、この試験に通ったものにし、比べる EVAL のあいだで変えない。ユーザー役が変わると、同じクリエイターでも結果が変わるためである。
- プロトタイプでは、Haiku のユーザー役は、大まかな質問に隠すべきナレッジを話し（25回中3回）、ナレッジにない決まりを作り、選択肢の言葉だけで答えた。Sonnet にし、やり取りを渡し、答え方の決まりを足すと、すべての観点に通った。

### 6.3 試験が正しく働くかを確かめる

- 大まかな質問しかしないクリエイター（対照）でも外側の EVAL を行い、聞かれないと話さないナレッジが組み込まれないことを確かめる。試験が、落ちるべきときに落ちるかを見るためである。プロトタイプでは、対照のスコアは2回とも 0.71 で、ユーザー役の答えにも漏れはなかった。
- 模擬ユーザーは、いくつかの分野で用意する。クリエイターを直すときに使った模擬ユーザーとは別の模擬ユーザーでも確かめる。クリエイターの手順を1人の模擬ユーザーに合わせて書くと、その模擬ユーザーでしか通らないためである。プロトタイプのクリエイターは、手順に「締めくくりの決まり」を挙げていたので週報の模擬ユーザーでは 1.00 だったが、議事録の模擬ユーザーでは、聞かれないと話さないナレッジを2つとも引き出せなかった（2回とも 0.71）。
- 話し方（口数が少ない、あいまいに答えるなど）を変えたユーザー役でも行う。答え方が違っても、クリエイターがナレッジを引き出せるかを見るためである。ユーザー役への指示には、答えの長さと言い方は話し方に従い、何を話してよいかは答え方の決まりに従うと書く。プロトタイプでは、これを書かないと話し方が答え方の決まりに負け、あいまいに答える設定でも初めから具体的に答えた。
- 試験の仕組みは、ナレッジごとに、クリエイターが聞いたか、ユーザー役が答えたか、生成プラグインに組み込まれたかを記録する。スコアが下がったときに、クリエイターが聞かなかったのか、ユーザー役が答えなかったのかを見分けるためである。聞いたかどうかは、ナレッジごとに決めた言葉が質問にあるかで見るので、最後は会話の記録を読んで確かめる。プロトタイプでは、あいまいに答えるユーザー役が、締めくくりを具体的に聞き直されても答えず、スコアが下がったことがあった（2回中1回）。クリエイターではなく、ユーザー役の誤りである。

### 6.4 模擬の限界

- ユーザー役は、人の代わりにはならない。公開の研究でも、ユーザー役のモデルを変えるだけで成功率が変わること、人とは違う話し方の癖が出ることが報告されている。
- プロトタイプのユーザー役には、人より協力的なところも、人より厳しいところもあった。口数が少ない設定でも、長く答えたり、聞かれていないことを自分から話したりした。一方で、例として「決定事項と意見を混ぜない」と挙げた質問には、決定事項の印のことを答えなかった。人なら答えそうな質問である。
- そのため、外側の EVAL の結果は、同じ模擬ユーザーとユーザー役で、クリエイターの版どうしを比べるのに使う。人と話したときの出来は、この結果だけでは分からない。

### 6.5 採点

外側の EVAL では、できた生成プラグインを次の観点で採点する。採点の観点は、出力の要件の受け入れ基準に対応づける。

- 1・2段目の試験に通るか
- 模擬ユーザーのナレッジ、特に聞かれないと話さないナレッジが組み込まれているか
- クリエイターが作った EVAL の課題と合否の基準（REQ-038）が、模擬ユーザーのナレッジ、特に聞かれないと話さないナレッジを含むか。ナレッジごとに決めた言葉が、課題と基準のファイルにあるかで見る。良い試験を作れるかも、クリエイターの性能として測るためである
- 内側の EVAL の結果

### 6.6 会話例

会話例（REQ-037）は、外側の EVAL の会話から作る。会話例のために EVAL を足すことはしない。

- 記録：外側の EVAL の記録に、クリエイターの発言（質問、生成前の確認、できたことの説明）と、ユーザー役の答えの全文を残す。試作は、クリエイターが文章で質問したとき、最後の300文字しか残していなかった。
- 作り方：スクリプト「会話例の作成」が、記録から Markdown のファイルを、模擬ユーザーごとに1つ作る。聞かれないと話さないナレッジを引き出した質問には、6.3 の記録（ナレッジごとに、聞いたか・答えたか）を使って印を付ける。冒頭に、AI が演じたユーザーとの会話であることと、クリエイターの版と日付を書く。
- 選ぶ条件：その版の外側の EVAL の会話のうち、次をどちらも満たすものから選ぶ。点数の高さだけでは選ばない。ユーザー役が隠すべきことを漏らすと、点数が上がるためである（ナレッジ「ユーザー役の AI で人を模擬するときの注意」）。
  - 採点の観点（6.5）にすべて合格した。
  - ユーザー役の誤り（聞かれていないのに隠すべきナレッジを話した、ナレッジにない決まりを作った、自分への指示のことを話した）がない。6.3 の記録で機械的に除き、最後は全文を読んで確かめる。
- 版：クリエイターの版を上げるたびに、その版の外側の EVAL の会話から作り直す。作り直し忘れは、クリエイター自身の1段目で、会話例に書いた版と `plugin.json` の版を突き合わせて見つける。違えば不合格にする。
- 置き場所：クリエイターのスキルのフォルダの外に置く。README とクリエイターの画面は、同じファイルを開く。
- クリエイターに読ませない：変換スクリプト（4章）は、置き換えた版から会話例を外す。クリエイターが会話例を読むと、例の分野の決まりを別の分野の生成プラグインに持ち込んだり、外側の EVAL で模擬ユーザーが隠しているナレッジを先に知ったりするためである。
- 載せない会話：クリエイターを直すときに見ないことにしている模擬ユーザー（6.3）の会話は、会話例にしない。リポジトリに載せると、このリポジトリで作業する AI が読み、見ていない模擬ユーザーではなくなるためである。

## 7. 内側の EVAL

- 内側の EVAL の課題と採点基準は、クリエイターとは別に、試験の資産として模擬ユーザーごとに用意する。生成プラグインに入っている EVAL の課題と合否の基準（REQ-038）はクリエイターが作ったものなので、クリエイターの採点には使わない。自分で作った基準で自分を採点しないためである。これは、開発の試験でクリエイターを採点するための決まりである。ユーザーの試験では、ユーザーが確かめて生成プラグインに入れた課題と基準で採点する（10.4）。
- 試験の仕組みは、人と同じ流れ（設定 → 開始 → 監視 → 結果）でブラウザーを操作して、置き換えた生成プラグインを動かす。画面は、試験の仕組みの Agent SDK 用のつなぎ口につないだ、生成プラグインの中心の処理と画面である（4章）。生成プラグインには、試験のためだけの機能を足さない。
  - Web管理画面の URL が出るのを待ってブラウザーで開き、設定して開始する。
  - 実行中は、フェーズとエージェントの状態の表示を記録する。
  - 終わったら、結果の表示を読む。
- 生成プラグインがチャットで返事や答えを求めて手番を終えたときは、ユーザー役が人の代わりに返事をする。プラグインなしのときも、同じように返事をする。そのため、ユーザーが自分から話すナレッジ（ファイル名や金額の書き方）は、プラグインがなくても伝わることがある。プロトタイプでは、なしのスコアが実行によって 0〜0.5 と変わった。
- 画面で選んだモデルで作業エージェントが動いたかは、実行の記録で確かめる。
- 採点の基準は、模擬ユーザーのナレッジに書いたとおりにする。ナレッジにない細かさまで求めると、正しい成果物を落とす。プロトタイプでは、金額を「52万」と書いた成果物を、「52万円」を求める基準で落とした。

## 8. 費用と時間

### 8.1 開発の試験

- 外側の EVAL は、1回ごとに生成プラグインを丸ごと作る。さらに、できた生成プラグインを内側の EVAL で繰り返し動かすので、実行の回数がかけ算で増える。
- 1・2段目は費用がかからないので、すべての生成プラグインに行う。内側の EVAL は、生成プラグインの数と実行の回数を絞って行う。
- 同じ条件でも、進め方や結果は実行のたびに変わる。1回の結果だけで判断しない。
- 目安（プロトタイプで測った値。統括は Sonnet、作業エージェントは Haiku。費用は定価での見積もり）：
  - 内側の EVAL：プラグインありで1回 約1分・約 0.13〜0.22 ドル、なしで1回 約10〜25秒・約 0.03〜0.06 ドル
  - 外側の EVAL：あり・なしと内側の EVAL を合わせて1回 約3分・約 0.4 ドル。内側の EVAL を省くと、クリエイターありで1回 約30〜50秒・約 0.1 ドル
  - ユーザー役の試験：1回 約 0.15 ドル（Sonnet で約75問）
- EVAL は、モデルの利用枠も使う。プロトタイプでは、EVAL を続けて回したところ、試されるエージェントが利用枠の上限に達したというエラーで止まり、示された時刻（約3時間後）まで再開できなかった。回す数は、利用枠も考えて決める。

### 8.2 ユーザーの試験

- 1・2段目はモデルを使わないので、AI クレジットを使わない。
- EVAL は、Copilot の AI クレジットを使う。1クレジットは 0.01 ドルで、使ったモデルとトークンの量で決まる。個人プランの月の枠は、Pro が 1,500、Pro+ が 7,000、Max が 20,000 クレジットである。公式ドキュメントでは、Copilot CLI が数える対象に入っている。Copilot SDK は、Copilot CLI と同じランタイムをユーザーのアカウントで動かし、モデルの呼び出しごとに Copilot の API が返す費用を記録する。そのため、SDK で動かした分も同じく数えられる（Copilot SDK 1.0.22 の説明と型定義で確認）。
- 見込みは、次のかけ算で出し、EVAL を始める前に回数とあわせて示す（REQ-040）。
  - （ありの1回分 ＋ なしの1回分）× 回数 ＋ 採点でモデルを使う分
  - 1回分には、同じ生成プラグインで前に EVAL をしたときの記録（`assistant.usage`）から測った値を使う。初めてのときは、開発の試験で測った目安（1回あたりのトークン数）に、使うモデルの価格（Copilot の価格表）をかけて出す。
- 目安は、まだ測っていない。試作（Claude の定価）では、内側の EVAL がプラグインありで1回 約 0.13〜0.22 ドルだった。同じくらいなら、あり・なしを3回ずつで 50〜80 クレジット程度になる（推定）。回数の既定値は、ユーザーの環境で費用を測ってから決める。
- 見込みは上限ではない。使った分は、`assistant.usage` を足し上げて示す（REQ-041）。そこにある費用（`copilotUsage.totalNanoAiu`）は nano-AIU で表され、1 AI クレジットは 10億 nano-AIU である。API の説明が、同じ量を「AI クレジット（小数）」と「nano-AIU（整数）」の2つで返しているので分かる。セッション全体の合計と、その合計がすべての呼び出しを含むか（`aiCreditsStatus`）も、SDK から取れる。

## 9. 最終確認

- 最終確認では、人が手元の Copilot CLI にプラグインをインストールし、使い始められることを確かめる（出力の要件のインストールの受け入れ基準）。
- Copilot CLI での読み込みの不具合や、Copilot CLI でしか起きない不具合は、ここで見つける。
- ユーザーの試験のうち、Copilot CLI を動かす部分（Copilot SDK での EVAL の実行と、試験を頼まれたときの流れ）も、ここで人が手元で確かめる。開発の試験では、Copilot CLI を動かさないためである（1章）。
- 生成プラグインとクリエイターのエクステンションのつなぎ口（読み込まれるか、統括の起動、モデルの上書き、止める、イベントの受け取り）も、ここで確かめる。あわせて、[生成プラグインの構造](generated-plugin-structure.md) 11章の、実機で確かめることを確かめる。

## 10. ユーザーの環境での試験

ユーザーが受け取った生成プラグインを、クリエイターがユーザーの手元で試験するやり方を書く。ユーザーから見た振る舞いは [試験の要件](../specs/test-requirements.md) にある。

### 10.1 置き場所と流れ

| もの | 置き場所 |
| --- | --- |
| 1・2段目のスクリプトと、それを1つのコマンドで動かす入口 | 生成プラグインのリポジトリ（ひな形から入れる） |
| 番号を付けたナレッジの一覧 | 生成プラグインのリポジトリ |
| EVAL の課題（頼むときの言葉、入力のファイル、Web管理画面の設定、基準ごとの採点のしかた） | 生成プラグインのリポジトリ。合否の基準そのものは作業の定義にあり、課題は基準の番号で参照する（[生成プラグインの構造](generated-plugin-structure.md) 4.9） |
| EVAL を動かす仕組みと採点 | クリエイター |

試験は次の順に進める。

1. 道具がそろっているかを確かめる。足りないときは、足りない道具と入れ方を示し、ユーザーがよいと答えたら入れる（REQ-048、11.2）。
2. 生成プラグインのリポジトリの入口で、1・2段目を動かす（10.2）。生成した直後に不合格のときは、作業エージェントに直させてやり直す。上限の回数まで直しても合格しないときは止めて、残った不合格を示す（REQ-039、[クリエイターの構造](creator-structure.md) 4.1）。
3. ユーザーが試験を頼んだときは、EVAL の回数と AI クレジットの見込み（8.2）を示す。ユーザーがよいと答えたら、生成プラグインあり・なしで課題を実行し、採点する（10.4）。
4. 結果を、チャットとクリエイターの画面に示す（REQ-039、REQ-041、REQ-044）。

### 10.2 1・2段目の入口

- クリエイターの1・2段目のスクリプトの写しと、それを1つのコマンドで動かす入口を、ひな形のテストのフォルダに入れる。組み立てのときに、生成プラグインに入る。開発の試験とユーザーの試験で、同じ仕組みを使うためである。
- 入口は、初めに道具がそろっているかを確かめる。足りなければ、足りない道具を示して止まる。クリエイターがなくても、何を入れればよいかが分かるようにするためである。
- 入口は、段階ごとの合否と、不合格の試験とその理由を出す。クリエイターと画面が読めるように、同じ内容をファイルにも書く。終了コードでも合否が分かる。
- クリエイターも、この入口を動かす。ユーザーが自分で動かしたときと、結果が同じになるためである。

### 10.3 ナレッジの番号の突き合わせ

構造の検査で、生成前の確認でよいと答えたナレッジが、すべて生成プラグインに入っているかを確かめる（REQ-039、[クリエイターの構造](creator-structure.md) 3.5）。

- メインのエージェントは、よいと答えたナレッジに番号（例：`K-01`）を付けて一覧にする。組み立てのときに、一覧を生成プラグインのテストのフォルダに入れる。直した後も、リポジトリだけで突き合わせられるようにするためである（REQ-042）。
- 作業エージェントは、ナレッジを入れた箇所に、その番号を書く。
- 構造の検査は、一覧の番号ごとに、生成プラグインのファイル（テストのフォルダを除く）にその番号があるかを調べる。ない番号は、そのナレッジの文と一緒に、不合格の理由として示す。
- 番号があっても、ナレッジが正しい意味で入ったとは限らない。意味は EVAL で確かめる。

### 10.4 EVAL

**読み込みと隔離**

- Copilot SDK（Copilot CLI をプログラムから動かす公式の部品）で Copilot CLI を起動し、生成プラグインを `--plugin-dir` で読み込む。プラグインなしのときは、何も読み込まない。
- 環境変数 `COPILOT_PLUGIN_DIR_ONLY=true` で、ユーザーがインストールしているほかのプラグインを読み込ませない。あり・なしの比べ合いに、ほかのプラグインが混ざらないようにするためである。読み込まれたプラグインは、セッションの `rpc.plugins.list()` で確かめる。
- 実行のたびに、課題の入力のファイルだけを写した、まっさらな作業フォルダで始める。
- 生成プラグインの Web管理画面はエクステンションの中で動き、エクステンションはサンドボックスの外で動く見込みである（[生成プラグインの構造](generated-plugin-structure.md) 4.12、要確認）。外で動くと確かめられたら、EVAL では Copilot CLI のサンドボックスを使い、作業フォルダの外への書き込みを止める。確かめるまでは、作業フォルダの外への書き込みを、許可の求めへの答え（下）で拒む。ただし、シェルのコマンドがどこに書くかまでは、許可の求めでは見分けきれない。
- エクステンションは試験的な機能なので、Copilot SDK で起動する Copilot CLI でも、実験モードを有効にする必要がある。SDK からの指定のしかたは要確認である。
- `--plugin-dir` で読み込んだプラグインも、マニフェストの `$schema` で形式が決まり、Agent Plugins の形式なら `com.github.copilot/` の中のエージェントやフックが読まれる（Copilot CLI 1.0.98 の実装（パッケージに含まれるプログラム、付属の説明、更新履歴）で確認）。Agent Plugins の形式のプラグインを `--plugin-dir` で読み込み、スキルが読まれることは、実際に動かして確かめた。カスタムエージェントが読まれたかは、ログインしないと確かめられないので、EVAL のたびに `subagent.started` の記録で確かめる。
- Copilot SDK は、対応する版の Copilot のランタイムを同梱している（SDK 1.0.22 は 1.0.98）。EVAL は同梱のものを使い、`COPILOT_CLI_PATH` で手元の Copilot CLI に替えない。ユーザーがふだん使う Copilot CLI と版が違うことがあるので、使った版を記録に残す。

**質問と許可の求め**

- 課題の頼むときの言葉には、作業に要る情報をすべて書く。
- エージェントの質問（`ask_user`）には、`onUserInputRequest` で、決まった返事（「課題に書いたこと以外は決まっていません。判断して進めてください」）を返す。あり・なしで同じ返事にし、ユーザー役の AI は使わない。AI クレジットを増やさず、プラグインなしのときにナレッジが伝わらないようにするためである（7章）。
- 許可の求めには、`onPermissionRequest` で答える。作業フォルダの外への書き込みは拒み、ほかは許可する。組織の管理設定で人の承認が要る求め（`managedApprovalRequired`）は、自動では許可せず、EVAL を止めて理由を示す。
- AI クレジットの予算を使い切ったという求め（`session_limits_exhausted.requested`）には、クレジットを足さずに止める。ユーザーが承認していない費用を使わないためである。
- 裏で動くサブエージェントの許可の求めも、`onPermissionRequest` に届く。許可の求めのイベントに、求めたエージェント（`ownerAgentId`）が入っている（Copilot SDK 1.0.22 の型定義と、Copilot CLI の更新履歴 1.0.87 で確認）。

**Web管理画面の操作と終わり**

- 7章と同じく、Playwright でブラウザーを操作し、人と同じ流れ（設定 → 開始 → 監視 → 結果）で生成プラグインを動かす。チャットに出た URL（`assistant.message`）を開き、課題に書いた設定を入れて開始する。生成プラグインには、試験のためだけの機能を足さない。
- 生成プラグインありのときは、画面に終わった理由（REQ-012）が出たら終わりとし、結果の表示を読む。なしのときは、エージェントが手番を終えたら（`session.idle`）終わりとする。

**採点と記録**

- 採点は、生成プラグインの外で行う。生成プラグインの検証エージェントが出した合否は使わない（REQ-041）。
- 基準ごとに、文字や形で決まるもの（ファイルがある、決まった言葉がある、最後の行が決まった文字であるなど）はプログラムで採点し、それ以外はモデルが判定する。モデルが判定する分も、見込みと使った分に入れる。
- 実行ごとに、次のイベントを記録のファイルに残し、採点と結果に使う。

  | イベント | 使い方 |
  | --- | --- |
  | `skill.invoked` | 生成プラグインのスキルが呼ばれたか（`pluginName`） |
  | `subagent.started`、`subagent.completed`、`subagent.failed` | カスタムエージェントが動いたか。どのモデルで動いたか（`model`） |
  | `tool.execution_start`、`tool.execution_complete` | 使ったツール |
  | `user_input.requested`、`permission.requested` | 質問と許可の求め |
  | `assistant.message` | チャットに出た URL と返事 |
  | `assistant.usage` | 呼び出しごとのモデル、トークン、費用 |
  | `session.idle` | 手番の終わり |

- 結果として、実行ごとの基準ごとの合否、あり・なしの点数とその差、使った AI クレジットを示す（REQ-041）。

### 10.5 EVAL の仕組みが2つになること

EVAL を動かす仕組みは、開発の試験（5章）とユーザーの試験で2つになる。

| | 開発の試験 | ユーザーの試験 |
| --- | --- | --- |
| エージェントを動かす部品 | Agent SDK（Claude Code） | Copilot SDK（Copilot CLI） |
| 試す生成プラグイン | Claude Code 向けに置き換えた版（4章） | そのまま |
| 人の代わりの返事 | ユーザー役の AI | 決まった返事 |

- 課題と基準のファイルの形、採点のスクリプト、Web管理画面の操作は、2つで同じものを使い、エージェントを動かす部分だけを分ける。保つものを減らすためである（憲章 第10条）。
- 開発のクラウド環境では Copilot CLI を動かさない（1章）ので、開発の試験は Copilot SDK に寄せない。
- Copilot SDK でエージェントを動かす部分は、最終確認で人が手元で確かめる（9章）。課題と基準のファイルの読み込み、採点、Web管理画面の操作は、2つで同じものを使うので、開発の試験で確かめられる。

## 11. 試験環境に必要なもの

### 11.1 開発の試験

- Agent SDK（Claude Code と同じ版にそろえる）
- bubblewrap と socat（Linux で OS のサンドボックスを動かすため）。クラウド環境には入っていないので、環境の設定のセットアップスクリプトで入れる。
- ブラウザー（Chromium）と、ブラウザーを操作する Playwright。ブラウザーはクラウド環境に入っている。Playwright は、そのブラウザーに合う版を試験の仕組みのフォルダに入れる。全体に入っている Playwright は、ESM 形式のスクリプトから読み込めなかったためである。
- Python と PyYAML・jsonschema（1段目の検査と変換スクリプト）

### 11.2 ユーザーの試験

| 道具 | 使うところ |
| --- | --- |
| Python と PyYAML・jsonschema | 1段目 |
| Node.js（Copilot SDK は 20.19 以上か 22.12 以上） | 2段目の Web管理画面の試験、EVAL |
| Playwright とブラウザー（手元の Chrome か Edge。どちらもないときは Playwright の Chromium） | 2段目の Web管理画面の試験、EVAL の画面の操作 |
| Copilot SDK | EVAL |
| Linux でサンドボックスを使うときは、bubblewrap 0.5.0 以上（外への通信を許すときは、slirp4netns などもあわせて） | EVAL |

- 試験の前に、入口とクリエイターが、道具がそろっているかを確かめる。足りないときは、クリエイターが足りない道具と入れ方を示し、ユーザーがよいと答えたら入れる（REQ-048）。
- Python のパッケージは仮想環境に入れ、ユーザーの環境全体は変えない。Node.js のパッケージも、試験のためのフォルダに入れる。
- ブラウザーは、Playwright の `channel`（`chrome`、`msedge`）で手元の Chrome か Edge を使う。どちらもないときだけ、Playwright の Chromium を、Playwright の既定の場所（ホームフォルダの中の共通の場所）に入れる（REQ-048）。生成プラグインごとに入れ直さないためである。
- 要確認：道具を入れるフォルダの場所。生成プラグインのリポジトリだけで1・2段目が動くこと（REQ-042）と、プラグインが実行中に書くデータはインストール先ではなく `PLUGIN_DATA` に置くという公式の勧めの、両方に合う場所にする。
- 要確認：Python や Node.js そのものがないときの入れ方（OS ごとに違う）。
