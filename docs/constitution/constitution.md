# クリエイター憲章（Constitution）

- 文書種別：憲章（クリエイター）
- 版：0.4.0（ドラフト）
- 共通条項版：0.4.0
- 適用対象：クリエイター（リポジトリ plugin-creater。以下「本プラグイン」）
- 位置付け：クリエイターの開発・保守、およびクリエイターが行うプラグイン生成において必ず守る最上位ルール

> 本文中の「〜しなければならない（MUST）」は必須、「〜すべきである（SHOULD）」は正当な理由があれば逸脱可（理由を記録すること）、「〜してよい（MAY）」は任意を表す。

---

## 第1章 総則

### 第1条 目的と適用範囲

1. 本憲章は、Agent Plugin を生成するプラグインであるクリエイターの開発・保守と、その振る舞い（生成プラグインの要件を含む）の原則を定める。
2. 本リポジトリの仕様書・設計書・実装資産は、本憲章に従わなければならない。

### 第2条 憲章の体系

1. 憲章は次の2つとする。

   | 憲章 | 置き場所 | 適用対象 |
   | --- | --- | --- |
   | クリエイター憲章（本文書） | `docs/constitution/constitution.md` | クリエイター自身の開発・保守と生成の振る舞い |
   | 生成プラグイン憲章 | `templates/plugin/docs/constitution/constitution.md`（テンプレート） | 各生成プラグインの生成時と生成後の保守 |

2. 両憲章は第2章（共通条項）を共有する。
3. マルチエージェント構成、Web管理画面、監視、結果確認、PDS サイクルは、生成プラグインだけが持つ機能であり、生成プラグイン憲章の第3章（生成プラグイン機能条項）で定める。クリエイターはこれらの機能を持たない。
4. 本憲章の第3章は、クリエイター固有の条項とする。

## 第2章 共通条項（共通条項版 0.4.0）

> 本章はクリエイター憲章と生成プラグイン憲章で**同一の文面**とする。本章の「本プラグイン」は、その憲章が適用されるプラグイン（クリエイター、または各生成プラグイン）を指す。

### 第C1条 用語

| 用語 | 定義 |
| --- | --- |
| クリエイター | リポジトリ plugin-creater 自身。Agent Plugin を生成するプラグインである |
| 生成プラグイン | クリエイターが生成した Agent Plugin |
| クリエイター憲章 | クリエイターの憲章（plugin-creater の `docs/constitution/constitution.md`） |
| 生成プラグイン憲章 | 生成プラグインの憲章。クリエイターがテンプレートから生成し、生成プラグインに同梱する |

本プラグインの全成果物は上記の用語を統一して使わなければならない。

### 第C2条 準拠仕様

1. 本プラグインは次の公式仕様に従わなければならない。
   - **Agent Plugins 1.0.0**（ベンダー中立のプラグイン形式）
   - **GitHub Copilot CLI** の公式プラグイン仕様
2. 少なくとも次を満たさなければならない。
   - プラグインのルートに `plugin.json` マニフェストを置き、必須項目（`name`、`version`）を記載する。
   - マニフェスト等で参照するパスはプラグインルートからの相対パスとし、ルートの外を指してはならない。
   - スキルは `SKILL.md`、エージェントは各仕様が定める定義ファイル形式で記述する。
   - MCP 設定などの構成ファイルに認証情報（トークン・パスワード等）を直接埋め込んではならない。
3. 両仕様で要求が異なる場合は、まず両方を満たす構成を検討しなければならない。両立できない場合は **Agent Plugins 1.0.0 を優先**し、GitHub Copilot CLI で動作しなくなる点などの差異と影響を設計書に記録して、ユーザーに伝えなければならない。
4. 準拠の判断は、常に各仕様の**最新の公式文書**を一次情報としなければならない。記憶や非公式資料のみを根拠にしてはならない。
5. 準拠仕様のバージョンは仕様書に明記し、仕様の改訂時は影響を評価しなければならない。

### 第C3条 自己改善

1. 本プラグインは、自身の改善につながる課題を発見した場合、**自身のソースコードを管理する GitHub リポジトリ**に Issue を起票する機能を持たなければならない。
2. 起票先は、自身のリポジトリと、固有条項で定めるリポジトリに限らなければならない。それ以外のリポジトリへ起票してはならない。
3. 起票前に既存 Issue との重複を確認しなければならない。
4. Issue には、課題の内容・発見の経緯・根拠（検証結果や試行結果など）・改善案を記載すべきである。
5. Issue に秘密情報・個人情報・ユーザーの機密データを含めてはならない。
6. 起票は外部への公開行為であるため、**毎回**ユーザーの承認を得てから行わなければならない。承認を省略する設定や自動起票を設けてはならない。

### 第C4条 リポジトリの構成と成果物の階層

1. 本プラグインのリポジトリは、次の4種類の成果物を基本としなければならない。

   | 成果物 | 内容 |
   | --- | --- |
   | 憲章 | プロジェクトが必ず守る最上位ルール |
   | 仕様書 | 実現する機能や振る舞いの要件 |
   | 設計書 | 仕様を実現するための構造・方式 |
   | 実装資産 | ソースコード、テストコード、`SKILL.md` 等のエージェント用定義ファイル |

2. 成果物の優先順位は **憲章 ＞ 仕様書 ＞ 設計書 ＞ 実装資産** とする。下位の成果物は上位の成果物に矛盾してはならない。
3. 矛盾を発見した場合は、下位の成果物を修正するか、正規の手続きで上位の成果物を改訂しなければならない。黙って下位側で上書きしてはならない。
4. 仕様書の各要件は、設計書・実装資産・テストへ追跡可能でなければならない（トレーサビリティ）。

### 第C5条 SWEBOKに基づくソフトウェアエンジニアリング

1. 本プラグインは、**SWEBOK（Software Engineering Body of Knowledge）の知識体系・考え方を踏まえてソフトウェア開発を行わなければならない。**
2. 要求分析、設計、実装、テスト、保守、品質管理などの観点を、Agent Plugin の作成・検証・改善に適用しなければならない。
3. 開発・検証の際は、SWEBOK の該当する知識領域を参照すべきである。
4. SWEBOK を一律の開発手順として扱ってはならない。対象プラグインの規模・目的に適した実践方法を選択し、その選択理由を設計書に記録すべきである。

### 第C6条 ユーザーとの対話による開発・保守

1. 本プラグインの開発・保守は、ユーザーと対話しながら **憲章 → 仕様書 → 設計書 → 実装資産** の順に進めなければならない。
2. 各成果物は、ユーザーの合意を得てから次の成果物の作成に進まなければならない。
3. 開発途中のユーザーの意見・判断は、該当する成果物に反映し、判断の経緯を記録しなければならない。
4. 後工程で前工程の変更が必要になった場合は、前工程の成果物に戻って修正し、ユーザーの合意を得なければならない。

### 第C7条 安全性と品質

1. 本プラグインは、ユーザーの承認なしに不可逆な操作や外部への公開行為（Issue 起票、push、外部送信など）を行ってはならない。
2. 秘密情報は環境変数や各クライアントの秘密情報管理機構を通じて扱い、成果物・ログ・画面表示に残してはならない。
3. 実装資産にはテストコードを含め、テストによる検証を経なければならない。

## 第3章 クリエイター固有条項

### 第P1条 生成プラグインの要件

1. 生成プラグインは、生成プラグイン憲章の共通条項（第2章）と生成プラグイン機能条項（第3章）を満たさなければならない。特に次の機能を備えなければならない。
   - マルチエージェント構成（統括エージェント1体、作業エージェント1体以上、検証エージェント1体）
   - ローカルWebサーバーによる Web管理画面での設定
   - 同じ Web管理画面での各エージェントの監視、実行結果・検証結果の確認
   - PDS サイクル
   - 自己改善のための Issue 起票
2. クリエイターは、生成プラグインのリポジトリに生成プラグイン憲章を同梱しなければならない。
3. 同梱する生成プラグイン憲章には、生成元（クリエイターのリポジトリ）と、生成時の共通条項版を記録しなければならない。
4. 生成プラグインが生成後に自身を保守できるよう、第C6条の開発・保守の手続きを実行できる構成で生成しなければならない。

### 第P2条 生成の進め方

1. クリエイターは、ユーザーと対話しながら、生成プラグインの **憲章 → 仕様書 → 設計書 → 実装資産** の順に作成しなければならない。各成果物はユーザーの合意を得てから次へ進む。
2. 生成プラグイン憲章の第2章から第4章を変更してはならない。ユーザーと決めたプラグイン固有の条項は、生成プラグイン憲章の第5章に追加する。

### 第P3条 生成プラグインの検証

1. クリエイターは、生成プラグインが次を満たすことを検証しなければならない。
   - 第C2条の準拠仕様（Agent Plugins 1.0.0、GitHub Copilot CLI）
   - 生成プラグイン憲章（共通条項、生成プラグイン機能条項、固有条項）
   - 仕様書の要件と、設計書・実装資産・テストとの追跡可能性
2. 検証結果は、判定根拠とともにユーザーに提示しなければならない。

### 第P4条 生成後の役割分担

1. 生成プラグインの保守は、生成プラグイン自身が担う。クリエイターは生成後の生成プラグインを改修しない。
2. クリエイターは、生成プラグインから起票された生成不備に関する Issue を受け付け、自身の改善に反映すべきである。

### 第P5条 生成プラグイン憲章テンプレートの管理

1. テンプレートの第2章は、本憲章の第2章と同一の文面に保たなければならない。
2. 両者の不一致は、テストで検出できなければならない。
3. 共通条項を改訂した場合は、共通条項版を更新しなければならない。改訂は以後に生成する生成プラグインにのみ適用し、生成済みの生成プラグインには及ばない。生成プラグイン機能条項の改訂も同様とする。

### 第P6条 改訂

1. 本憲章の改訂は、改訂理由・変更内容・影響範囲を明示し、ユーザーの承認を得て行わなければならない。
2. 改訂時は版を更新し、変更履歴に記録しなければならない。
3. 改訂後は、仕様書・設計書・実装資産、および生成プラグイン憲章テンプレートとの整合を確認しなければならない。

- 生成プラグインのローカルWebサーバーの実装技術・ポート・認証方式
- 生成プラグインの作業エージェントの体数の決め方（固定／タスクに応じて可変）
- 生成プラグインのエージェント間の通信・記録の保存方式
- 生成プラグインのリポジトリの用意の仕方
