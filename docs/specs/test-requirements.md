# 試験の要件

ユーザーが、クリエイターで作った生成プラグインを試験するとき、クリエイターがユーザーから見てどう振る舞うかを定める（憲章 第17条）。クリエイター自身を開発するための試験は、[試験の設計](../design/testing.md) で定める。

試験は、次の3段階で行う。

| 段階 | 確かめること |
| --- | --- |
| 構造の検査 | 設定ファイル、ファイルの置き場所、フロントマターが公式仕様に沿っているか |
| 部品の試験 | スクリプト、フック、MCP サーバー、Web管理画面などが正しく動くか |
| EVAL | 実際のモデルで課題を実行し、合否の基準で採点する。生成プラグインあり・なしで点数を比べる |

## 1. 試験の準備

### REQ-038 EVAL の課題と合否の基準

- 要件：生成する前の確認（REQ-020）で、クリエイターは、生成プラグインの EVAL に使う課題と合否の基準も示す。課題は、ユーザーが話した実際の1回（REQ-016）と、示したファイル（REQ-017）から作る。合否の基準は、ユーザーと確かめた合否の決め方（REQ-015）である。ユーザーが直したり足したりして、よいと答えたものを、生成プラグインのリポジトリに入れる。
- 根拠：憲章 第4条、第17条1項／[試験の設計](../design/testing.md) 7章（採点の基準は、ナレッジに書いたとおりにする。ナレッジにない細かさまで求めると、正しい成果物を落とす）
- 受け入れ基準：
  - 生成の前に、課題と合否の基準が、説明のない専門用語を使わずに示される。
  - ユーザーと確かめた合否の決め方が、すべて基準に入っている。ユーザーが確かめていない基準はない。
  - 生成プラグインのリポジトリに、課題（入力のファイルを含む）と合否の基準が入っている。

### REQ-048 試験の道具の用意

- 要件：試験を行う前に、クリエイターは、試験に要る道具（Python、画面を操作する Playwright とブラウザーなど）がユーザーの手元にあるかを調べる。足りないときは、足りない道具と入れ方と入れる場所を示し、ユーザーがよいと答えたら、クリエイターが入れる。ブラウザーは、ユーザーのパソコンにある Chrome か Edge を使う。どちらもないときだけ、Playwright のブラウザーを入れる。
- 根拠：憲章 第17条1項／Playwright のブラウザーの公式ドキュメント（手元の Chrome と Edge を操作できる。Playwright のブラウザーは1つ約 280 MB で、ホームフォルダの中の共通の場所に入る）
- 受け入れ基準：
  - 道具が足りない環境で試験を始めると、足りない道具と入れ方と入れる場所が示される。
  - ユーザーがよいと答えるまで、道具は入れられない。
  - よいと答えると道具が入り、試験が行われる。
  - Chrome か Edge があるパソコンでは、ブラウザーは入れられず、そのブラウザーで画面の試験が行われる。

## 2. 生成した直後

### REQ-039 構造の検査と部品の試験

- 要件：生成が終わると、クリエイターは、生成プラグインに構造の検査と部品の試験を行い、段階ごとの合否を示す。不合格のときは、クリエイターが直して試験をやり直し、合格してから渡す。上限の回数まで直しても合格しないときは止めて、残った不合格の試験とその理由を示す。この2つの段階はモデルを使わないので、AI クレジットを使わない。構造の検査では、生成する前の確認（REQ-020）でユーザーがよいと答えたナレッジが、すべて生成プラグインに入っているかも確かめる。
- 根拠：憲章 第5条、第16条2項、第17条1項。生成プラグインのファイルは費用の低いモデルが書き（REQ-046）、そのモデルは対話を見ていないので、ナレッジが抜けることがある
- 受け入れ基準：
  - 生成の後に、構造の検査と部品の試験の合否が示される。
  - 確かめたナレッジのうち、生成プラグインに入っていないものがあると、構造の検査が不合格になり、どのナレッジが抜けたかが分かる。
  - 公式仕様に合わない生成プラグイン（例：スキルのフロントマターに必須の項目がない）では、構造の検査が不合格になり、どこが合わないかが分かる。
  - 正しく動かない部品（例：異常な入力で止まるスクリプト）がある生成プラグインでは、部品の試験が不合格になる。
  - 不合格になったときは、直して合格した生成プラグインが渡される。上限の回数まで直しても合格しないときは、残った不合格の試験とその理由が示される。

## 3. EVAL

### REQ-040 試験を頼む

- 要件：ユーザーがチャットでクリエイターに生成プラグインの試験を頼むと、クリエイターは3段階の試験を行う。EVAL を始める前には、実行の回数と、使う AI クレジットの見込みを示し、ユーザーがよいと答えてから始める。
- 根拠：憲章 第17条1項／GitHub Copilot の使った分による課金（AI クレジット）
- 受け入れ基準：
  - 試験を頼むと、構造の検査と部品の試験の合否が示される。
  - EVAL の前に、実行の回数と AI クレジットの見込みが示される。
  - ユーザーがよいと答えるまで、EVAL は始まらない。断ると、EVAL は行われない。

### REQ-041 EVAL の実行と結果

- 要件：クリエイターは、Copilot CLI で、生成プラグインあり・なしで同じ課題を何回か実行し、合否の基準で採点する。生成プラグインありのときは、Web管理画面での設定と開始も、人の代わりに試験の仕組みが行う。終わると、次を示す。
  - 実行ごとの、基準ごとの合否
  - 生成プラグインあり・なしの点数と、その差
  - 使った AI クレジット
- 根拠：憲章 第5条、第17条1項／[試験の設計](../design/testing.md) 2章、10.4
- 受け入れ基準：
  - 終わると、上の3つが示される。
  - 基準を満たさないように壊した生成プラグインでは、その基準が不合格になる。
  - 採点は生成プラグインの外で行われる。生成プラグインの検証エージェントが出した合否は、採点に使われない。

## 4. 直した後

### REQ-042 直した後の試験

- 要件：ユーザーが生成プラグインを直した後も、試験をやり直せる。
  - 構造の検査と部品の試験は、生成プラグインのリポジトリで、1つのコマンドで動かせる。クリエイターを入れていなくても動く。
  - EVAL は、クリエイターに試験を頼むと（REQ-040）、生成プラグインのリポジトリに入っている課題と合否の基準で行われる。
- 根拠：憲章 第6条1項、第17条2項
- 受け入れ基準：
  - クリエイターを入れていない環境で、生成プラグインのリポジトリから1つのコマンドで構造の検査と部品の試験が動き、段階ごとの合否が示される。
  - 生成プラグインを直してから試験を頼むと、直した後の生成プラグインで3段階の試験が行われる。
