# 作る流れの要件

ユーザーがクリエイターをインストールしてから、生成プラグインを受け取るまでに、クリエイターがユーザーから見てどう振る舞うかを定める（憲章 第4条、第5条、第12条）。受け取った生成プラグインの振る舞いは、[出力の要件](output-requirements.md) で定める。

## 1. 使い始める

### REQ-023 クリエイターのインストール

- 要件：ユーザーは、クリエイターを Copilot CLI にインストールできる。チャットで作業の自動化を頼むと、クリエイターの対話が始まる。
- 根拠：憲章 第5条
- 受け入れ基準：
  - Copilot CLI でクリエイターをインストールできる。
  - チャットで作業の自動化を頼むと、クリエイターがナレッジを引き出す質問を始める。

## 2. ナレッジを引き出す

### REQ-015 項目ごとの質問

- 要件：クリエイターは、次の項目を、項目ごとにユーザーに質問する。答えがあいまいなときは、具体的に聞き直す。
  - 作業の目的
  - 頼む場面と言い方
  - 受け取るもの
  - 進め方
  - 成果物
  - 合否の決め方
  - 決まった書き方やルール
  - 守らないと困ること
  - 使う道具と環境（ツール、コマンド、外部のシステム）
  - いつもと違うとき（例外的な場合、困ったときの扱い）
- 根拠：憲章 第4条、第17条／ナレッジ「人からナレッジを引き出す手法」（インタビュー）、「スキル」、「実例：組み込み機器のプリントデバッグ」／SWEBOK の要求の出どころ（目的、業務のルール、動かす環境）／Anthropic の skill-creator（呼ばれる場面、出力の形、例外的な場合、成功の基準、依存するもの）
- 受け入れ基準：
  - 対話の中で、上の項目がすべて質問されている。
  - 「普通の書き方です」のようなあいまいな答えには、具体的に聞き直している。

### REQ-016 実際の1回をたどる

- 要件：クリエイターは、ユーザーに、最近実際にやった1回の作業を、最初から順に話してもらう。話の中に出てきた手順や決まりのうち、まだ聞いていないものを、その場で聞く。
- 根拠：憲章 第4条／ナレッジ「人からナレッジを引き出す手法」（シナリオ）。本人が当たり前だと思っていることは、項目ごとの質問では話されにくい
- 受け入れ基準：
  - 対話の中で、実際の1回をたどってもらう質問がある。
  - 項目ごとの質問では出てこない、その分野に固有の決まりも、生成プラグインに組み込まれる。

### REQ-017 ファイルを読んで確かめる

- 要件：ユーザーが過去の成果物や作業のファイルを示すと、クリエイターはそれを読み、そこから分かる決まりを「〜という決まりですか？」とユーザーに確かめる。確かめて正しいと答えられたものだけを、ナレッジとして使う。
- 根拠：憲章 第4条／Anthropic の skill-creator（例のファイルを聞く）
- 受け入れ基準：
  - 示したファイルから読み取った決まりが、確認の質問として示される。
  - 違うと答えた決まりは、生成プラグインに組み込まれない。

## 3. 既存の資産を探す

### REQ-018 ユーザーの資産

- 要件：クリエイターは、生成プラグインに使えるユーザーの資産（テンプレート、スクリプト、過去の成果物など）がないかを質問する。あるものは、生成プラグインで流用する。
- 根拠：憲章 第12条2項・4項／ナレッジ「ハーネスの調達」
- 受け入れ基準：
  - 対話の中で、既存の資産を聞く質問がある。
  - ユーザーが示した資産が、生成プラグインに組み込まれて使われる。

### REQ-019 標準機能と公開のプラグイン

- 要件：クリエイターは、作業の一部が Copilot CLI の標準機能や、公開されているプラグイン（Awesome Copilot など）で済まないかを調べる。使えるものがあれば、ユーザーに示し、使うかどうかを選んでもらう。自作するのは、それでも足りない部分だけにする。
- 根拠：憲章 第12条3項・4項／ナレッジ「ハーネスの調達」
- 受け入れ基準：
  - 標準機能や公開のプラグインで済む部分があるとき、それがユーザーに示される。
  - ユーザーが使うと選んだものは、自作されない。

## 4. 確かめてから作る

### REQ-020 生成する前の確認

- 要件：生成する前に、クリエイターは、引き出したナレッジの一覧と、生成プラグインの振る舞いの案（何を受け取り、どう進め、何を成果物にし、何で合否を判定するか）を示す。ユーザーが直したり足したりして、よいと答えてから生成する。ユーザーが直したときは、指摘の文言をそのまま残さず、目的に沿って案を直す。
- 根拠：憲章 第4条、第7条、第9条2項／ナレッジ「人からナレッジを引き出す手法」（試作品）、「人間と AI のコミュニケーション」。振る舞いの案は、生成プラグインの仕様に当たる
- 受け入れ基準：
  - 生成の前に、ナレッジの一覧と振る舞いの案が示される。
  - ユーザーが直した内容が、生成プラグインに反映される。
  - ユーザーがよいと答えるまで、生成されない。
  - 直した後の案に、「〜ではない」のように指摘を打ち消すだけの文がない。

## 5. 受け取る

### REQ-021 作る場所

- 要件：生成プラグインは、今の作業フォルダの中の新しいフォルダに、git のリポジトリとして作られる。クリエイターは、GitHub への公開など、手元の外に出る操作をしない。GitHub のリポジトリは、ユーザーが作る。
- 根拠：憲章 第6条1項、第18条2項
- 受け入れ基準：
  - 作業フォルダの中に、git のリポジトリとして生成プラグインのフォルダができる。
  - 作業フォルダの外や GitHub には、何も作られない。

### REQ-022 できたことの説明

- 要件：生成が終わると、クリエイターは次を示す。
  - 生成プラグインのフォルダの場所
  - 組み込んだナレッジ
  - 流用した資産。公開のプラグインを使うときは、そのプラグインの入れ方
  - GitHub に公開するしかた。公開すると、生成プラグインが自分のリポジトリに Issue を起票できるようになること
- 根拠：憲章 第4条、第12条、第18条2項
- 受け入れ基準：
  - 生成の後に、上の4つが示される。

## 6. 伝え方

### REQ-024 分かりやすい質問と説明

- 要件：クリエイターの質問と説明は、簡潔で、説明のない専門用語を使わない。
- 根拠：憲章 第9条1項
- 受け入れ基準：
  - クリエイターの質問と説明に、説明のない専門用語がない。
  - 同じことを繰り返して書いていない。
