# 作る流れの要件

ユーザーがクリエイターに作業の自動化を頼んでから、生成プラグインを受け取るまでに、クリエイターがユーザーから見てどう振る舞うかを定める（憲章 第4条、第12条）。受け取った生成プラグインの振る舞いは、[出力の要件](output-requirements.md) で定める。

## 1. ナレッジを引き出す

### REQ-015 項目ごとの質問

- 要件：クリエイターは、成果物、決まった書き方やルール、守らないと困ることなどを、項目ごとにユーザーに質問する。答えがあいまいなときは、具体的に聞き直す。
- 根拠：憲章 第4条／ナレッジ「人からナレッジを引き出す手法」（インタビュー）
- 受け入れ基準：
  - 対話の中で、上の項目がすべて質問されている。
  - 「普通の書き方です」のようなあいまいな答えには、具体的に聞き直している。

### REQ-016 実際の1回をたどる

- 要件：クリエイターは、ユーザーに、最近実際にやった1回の作業を、最初から順に話してもらう。話の中に出てきた手順や決まりのうち、まだ聞いていないものを、その場で聞く。
- 根拠：憲章 第4条／ナレッジ「人からナレッジを引き出す手法」（シナリオ）。本人が当たり前だと思っていることは、項目ごとの質問では話されにくい
- 受け入れ基準：
  - 対話の中で、実際の1回をたどってもらう質問がある。
  - 項目ごとの質問では出てこない、その分野に固有の決まりも、生成プラグインに組み込まれる。

### REQ-017 ファイルを読んで確かめる

- 要件：ユーザーが過去の成果物や作業のファイルを示すと、クリエイターはそれを読み、そこから分かる決まりを「〜という決まりですか？」とユーザーに確かめる。確かめて正しいと答えられたものだけを、ナレッジとして使う。
- 根拠：憲章 第4条／ナレッジ「人からナレッジを引き出す手法」（観察）
- 受け入れ基準：
  - 示したファイルから読み取った決まりが、確認の質問として示される。
  - 違うと答えた決まりは、生成プラグインに組み込まれない。

## 2. 既存の資産を探す

### REQ-018 ユーザーの資産

- 要件：クリエイターは、生成プラグインに使えるユーザーの資産（テンプレート、スクリプト、過去の成果物など）がないかを質問する。あるものは、生成プラグインで流用する。
- 根拠：憲章 第12条／ナレッジ「ハーネスの調達」
- 受け入れ基準：
  - 対話の中で、既存の資産を聞く質問がある。
  - ユーザーが示した資産が、生成プラグインに組み込まれて使われる。

### REQ-019 標準機能と公開のプラグイン

- 要件：クリエイターは、作業の一部が Copilot CLI の標準機能や、公開されているプラグイン（Awesome Copilot など）で済まないかを調べる。使えるものがあれば、ユーザーに示し、使うかどうかを選んでもらう。自作するのは、それでも足りない部分だけにする。
- 根拠：憲章 第12条／ナレッジ「ハーネスの調達」
- 受け入れ基準：
  - 標準機能や公開のプラグインで済む部分があるとき、それがユーザーに示される。
  - ユーザーが使うと選んだものは、自作されない。

## 3. 確かめてから作る

### REQ-020 生成する前の確認

- 要件：生成する前に、クリエイターは、引き出したナレッジの一覧と、生成プラグインの振る舞いの案（何を受け取り、どう進め、何を成果物にし、何で合否を判定するか）を示す。ユーザーが直したり足したりして、よいと答えてから生成する。
- 根拠：憲章 第4条／ナレッジ「人からナレッジを引き出す手法」（試作品）
- 受け入れ基準：
  - 生成の前に、ナレッジの一覧と振る舞いの案が示される。
  - ユーザーが直した内容が、生成プラグインに反映される。
  - ユーザーがよいと答えるまで、生成されない。

## 4. 受け取る

### REQ-021 作る場所

- 要件：生成プラグインは、今の作業フォルダの中の新しいフォルダに、git のリポジトリとして作られる。クリエイターは、GitHub への公開など、手元の外に出る操作をしない。
- 根拠：憲章 第6条1項
- 受け入れ基準：
  - 作業フォルダの中に、git のリポジトリとして生成プラグインのフォルダができる。
  - 作業フォルダの外や GitHub には、何も作られない。

### REQ-022 できたことの説明

- 要件：生成が終わると、クリエイターは、生成プラグインのフォルダの場所、組み込んだナレッジ、流用した資産を示す。
- 根拠：憲章 第4条、第12条
- 受け入れ基準：
  - 生成の後に、上の3つが示される。
