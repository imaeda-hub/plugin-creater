# 出力の要件

クリエイターが出力する生成プラグインが、ユーザーから見てどう振る舞うかを定める（憲章 第11条）。何の作業をするかなど、生成プラグインごとに異なる部分は、ユーザーとの対話で決める（憲章 第4条）。

## 1. 受け取るもの

### REQ-001 受け取るもの

- 要件：ユーザーは、クリエイターから生成プラグインのリポジトリ一式を受け取る。そこには、プラグイン本体とテストに加えて、生成プラグインの憲章・仕様書・設計書が入っている。
- 根拠：憲章 第6条1項
- 受け入れ基準：
  - 受け取ったリポジトリに、憲章・仕様書・設計書・プラグイン本体・テストがそろっている。

### REQ-002 生成プラグインの憲章

- 要件：ユーザーが生成プラグインの憲章を読むと、次の2つが書かれている。
  - 成果物の優先順位は、憲章 ＞ 仕様書 ＞ 設計書 ＞ 実装資産 であること
  - 開発と保守は、憲章 → 仕様書 → 設計書 → 実装資産 の順に行うこと
- 根拠：憲章 第6条2項、第7条
- 受け入れ基準：
  - 生成プラグインの憲章に、上の2つが書かれている。

### REQ-003 要件のたどり方

- 要件：ユーザーは、生成プラグインの仕様書の要件の番号から、その要件を実現している設計書の箇所・実装資産・テストをたどれる。
- 根拠：憲章 第6条3項
- 受け入れ基準：
  - 生成プラグインの仕様書のどの要件からも、設計書の箇所・実装資産・テストを番号でたどれる。

## 2. インストール

### REQ-004 インストール

- 要件：ユーザーは、生成プラグインを Copilot CLI にインストールし、すべての機能を使える。生成プラグインは、Agent Plugins 1.0.0 の形式に沿っている。
- 根拠：憲章 第5条／Agent Plugins 1.0.0／Copilot CLI プラグインリファレンス
- 受け入れ基準：
  - Copilot CLI でインストールでき、生成プラグインの機能を使い始められる。
  - Agent Plugins 1.0.0 の公式スキーマの検査に通る。

## 3. 使い始める

### REQ-005 Web管理画面

- 要件：ユーザーが Copilot CLI のチャットで生成プラグインに作業を頼むと、Web管理画面の URL が示される。ユーザーは、ブラウザーでこの画面を開き、開始前の設定をして開始ボタンを押す。実行中の監視と、終了後の結果確認も、この画面で行う。
- 根拠：憲章 第15条1項、第17条〜第19条／ナレッジ「ハーネスエンジニアリングの目的と人間の役割」
- 受け入れ基準：
  - チャットで作業を頼むと、Web管理画面の URL が示される。
  - 示された URL を開くと、Web管理画面が表示される。
  - 開始ボタンを押すと、チャットでもう一度頼まなくても、頼んだ作業が始まる。
  - 設定・監視・結果確認が、すべてこの画面でできる。

### REQ-029 サーバーの起動と終了

- 要件：ユーザーがチャットで作業を頼むと、Web管理画面のサーバーが起動する。使いたい番号（ポート）をほかのプログラムが使っていても、空いている番号で起動する。Copilot CLI を終えると、サーバーも終わる。
- 根拠：憲章 第15条1項、第17条1項
- 受け入れ基準：
  - チャットで作業を頼むと、サーバーが起動し、示された URL で画面が開ける。
  - いつもの番号をほかのプログラムが使っていても、別の番号で起動し、その番号の URL が示される。
  - Copilot CLI を終えると、サーバーのプロセスが残らない。

### REQ-006 接続の制限

- 要件：Web管理画面は、最初の設定では、生成プラグインを動かしているマシンのブラウザーからしか開けない。
- 根拠：憲章 第17条2項
- 受け入れ基準：
  - 最初の設定で、同じマシンのブラウザーからは開ける。
  - 最初の設定で、ほかのマシンからは開けない。

### REQ-007 開始前の設定

- 要件：ユーザーは、開始前に Web管理画面で次を設定できる。
  - 役割（統括・作業・検証）ごとに使うモデル。最初は、統括と検証に思考力の高いモデル、作業に費用の低いモデルが選ばれている。
  - 繰り返しの上限の回数
- 根拠：憲章 第17条1項／ナレッジ「マルチエージェントの強み」「カスタムエージェント」
- 受け入れ基準：
  - 設定を変えて開始すると、変えた設定で実行される。

### REQ-031 作業ごとの画面

- 要件：Web管理画面には、共通の表示に加えて、生成の前にユーザーと決めた、その作業だけの設定・実行中の表示・結果の見せ方がある（REQ-026）。
- 根拠：憲章 第15条3項、第17条〜第19条
- 受け入れ基準：
  - ユーザーと決めた設定と表示が、すべて画面にある。
  - その作業だけの設定を変えて開始すると、変えた設定で実行される。

## 4. 実行中

### REQ-008 実行中の表示

- 要件：実行中、ユーザーは Web管理画面で次を見られる。表示は、ページを再読み込みしなくても更新される。
  - 各エージェントの役割（統括・作業・検証）、状態、担当している作業
  - 今が計画・実行・評価のどれか
  - エージェント間のデータの受け渡しを表した図
- 根拠：憲章 第15条1項、第16条1項、第18条／ナレッジ「ハーネスエンジニアリングの目的と人間の役割」
- 受け入れ基準：
  - 実行中に、上の3つが表示される。
  - 統括エージェント1体、作業エージェント1体以上、検証エージェント1体が表示される。
  - エージェントの状態が変わると、再読み込みしなくても表示が変わる。実行の最初から最後まで、更新が止まらない。
  - 画面の表示が、実際の状態とずれない。たとえば、終わったエージェントが「実行中」のまま残らない。

### REQ-009 止める

- 要件：ユーザーが Web管理画面の止めるボタンを押すと、作業の途中でも、すべてのエージェントがすぐに止まる。
- 根拠：憲章 第15条1項、第18条
- 受け入れ基準：
  - 止めるボタンを押すと、すべてのエージェントがすぐに止まる。
  - 止めた後に、作業を続けるエージェントがない。

### REQ-010 作ることと判定することの分担

- 要件：成果物の合否は、成果物を作った作業エージェントではなく、検証エージェントが判定する。検証エージェントは成果物を直さず、指摘だけを統括エージェントに返す。
- 根拠：憲章 第16条2項
- 受け入れ基準：
  - 結果に示される合否は、すべて検証エージェントが出したものである。
  - 検証の前と後で、成果物の中身が変わっていない。

### REQ-011 計画・実行・評価の繰り返し

- 要件：生成プラグインは、計画 → 実行 → 評価 を1回の試行として繰り返す。毎回、実行の前に評価基準を決め、検証エージェントの指摘を次の計画に生かす。評価基準には、生成の前にユーザーと確かめた合否の基準（REQ-020）が必ず入る。統括エージェントは評価基準を足せるが、ユーザーと確かめた基準を外したり、ゆるめたりはしない。評価基準をすべて満たしたら終わる。満たさないまま上限の回数に達したら止まる。
- 根拠：憲章 最大の目的、第20条／ナレッジ「AI の思考サイクル（PDS）」
- 受け入れ基準：
  - ユーザーは、試行ごとに、評価基準と、評価基準ごとの合否・指摘を見られる。
  - どの試行の評価基準にも、ユーザーと確かめた合否の基準がそのまま入っている。
  - 2回目以降の試行の計画に、前の試行の指摘への対応が含まれている。
  - 評価基準をすべて満たした試行で、繰り返しが終わる。
  - 上限の回数に達すると、繰り返しが止まる。

## 5. 終了後

### REQ-012 結果の確認

- 要件：終了後、ユーザーは Web管理画面で次を見られる。
  - 各エージェントの実行結果
  - 検証結果（評価基準ごとの合否と指摘）
  - 実行全体のまとめ
  - 終わった理由（評価基準をすべて満たした、上限の回数に達した、ユーザーが止めた のどれか）
- 根拠：憲章 第19条／ナレッジ「ハーネスエンジニアリングの目的と人間の役割」
- 受け入れ基準：
  - 終了後に、上の4つが表示される。

### REQ-013 課題の一覧

- 要件：終了後、ユーザーは Web管理画面で、今回の実行で見つかった課題の一覧を見られる。課題は、実行の記録を振り返り、次の観点で洗い出されている。
  - 何かの実行に失敗していないか
  - エージェントが詰まったり止まったりしていないか
  - データがきれいに流れているか
- 根拠：憲章 第21条1項／ナレッジ「自己改善」
- 受け入れ基準：
  - 終了後に、課題の一覧が表示される。
  - わざと失敗を起こした実行では、その失敗が課題の一覧に出る。

### REQ-014 Issue の起票

- 要件：課題の一覧には、生成プラグイン自身を改善するための Issue の案（タイトルと本文）が並ぶ。ユーザーが案ごとに承認すると、その案が生成プラグイン自身の GitHub リポジトリに Issue として起票される。
- 根拠：憲章 第21条2項・3項／ナレッジ「自己改善」
- 受け入れ基準：
  - 承認した案は、生成プラグインのリポジトリに Issue として作られる。
  - 承認していない案は、作られない。

## 6. 見た目と伝え方

### REQ-030 見た目

- 要件：どの生成プラグインの Web管理画面も、同じ画面の構成と見た目（配色、文字、部品）でできている。見やすく、崩れない。
- 根拠：憲章 第9条1項、第15条1項・2項／ナレッジ「ハーネスエンジニアリングの目的と人間の役割」
- 受け入れ基準：
  - 別々の作業のために作った2つの生成プラグインで、共通部分の画面の構成と見た目が同じである。
  - 今が計画・実行・評価のどれかと、各エージェントの状態が、画面を開いてすぐ、スクロールせずに見える。
  - ノートパソコンから大きな画面まで、ブラウザーの幅を変えても、文字や部品が重なったり、はみ出したりしない。
  - 各エージェントの出力の全文など、長い内容は最初は畳まれていて、押すと開く。
  - 文字と背景の色の差が十分あり、文字を大きくしても崩れない（Web のアクセシビリティの国際基準 WCAG 2.2 の、色の差と文字の拡大の基準を満たす）。
  - 状態は、色だけでなく文字でも示される。

### REQ-025 分かりやすい表示

- 要件：Web管理画面の表示と Issue の案は、簡潔で、説明のない専門用語を使わない。
- 根拠：憲章 第9条1項
- 受け入れ基準：
  - Web管理画面の表示と Issue の案に、説明のない専門用語がない。
  - 同じことを繰り返して書いていない。
