# 出力の要件

クリエイターが出力する生成プラグインが、共通して備える構成と振る舞いを定める（憲章 第10条）。何の作業をするかなど、生成プラグインごとに異なる部分は、ユーザーとの対話で決める（憲章 第4条）。

## 1. 出力物

### REQ-001 出力物の構成

- 要件：クリエイターは、生成プラグインごとに、そのリポジトリの中身として次を出力する。
  - 生成プラグインの憲章・仕様書・設計書
  - 実装資産（プラグイン本体と、そのテスト）
- 根拠：憲章 第6条1項
- 受け入れ基準：
  - 出力に、憲章・仕様書・設計書・プラグイン本体・テストがそろっている。

### REQ-002 生成プラグインの憲章に書くこと

- 要件：生成プラグインの憲章には、次を書く。
  - 成果物の優先順位は、憲章 ＞ 仕様書 ＞ 設計書 ＞ 実装資産 とすること
  - 開発と保守は、憲章 → 仕様書 → 設計書 → 実装資産 の順に行うこと
- 根拠：憲章 第6条2項、第7条
- 受け入れ基準：
  - 生成プラグインの憲章に、上の2つが書かれている。

### REQ-003 要件の追跡

- 要件：生成プラグインの仕様書の要件には番号を付ける。設計書・実装資産・テストからは、その番号で要件を参照する。
- 根拠：憲章 第6条3項
- 受け入れ基準：
  - 生成プラグインの仕様書のどの要件からも、それを実現する設計書の箇所・実装資産・テストを、番号でたどれる。

## 2. プラグイン本体の形式

### REQ-004 パッケージの形式

- 要件：プラグイン本体は、Agent Plugins 1.0.0 の形式にする。
  - ルートに `plugin.json` を置く。`$schema` に Agent Plugins 1.0.0 のスキーマ、`name` にプラグイン名、`repository` に生成プラグイン自身の GitHub リポジトリの URL を書く。
  - スキルは `skills/` の下に、1つのスキルを1つのフォルダにして置く。
  - MCP サーバーを使う場合は、ルートの `mcp.json` に書く。
- 根拠：憲章 第5条／Agent Plugins 1.0.0（§4〜§7）
- 受け入れ基準：
  - `plugin.json` と `mcp.json` が、Agent Plugins 1.0.0 のスキーマに適合している。
  - Copilot CLI の `copilot plugin install` でインストールできる。

### REQ-005 Copilot CLI 固有の部品の置き場所

- 要件：Agent Plugins 1.0.0 が定めていない部品は、Copilot CLI の拡張用フォルダ `com.github.copilot/` の下に置く。
  - カスタムエージェント：`com.github.copilot/agents/` に `.agent.md` ファイルとして置く。
  - フックを使う場合：`com.github.copilot/hooks/hooks.json` に書く。
- 根拠：憲章 第5条2項／Agent Plugins 1.0.0（§8）／Copilot CLI プラグインリファレンス
- 受け入れ基準：
  - インストール後、Copilot CLI で生成プラグインのカスタムエージェントを使える。

## 3. エージェント

### REQ-006 エージェントの役割

- 要件：生成プラグインは、次の役割のカスタムエージェントを持つ。

  | 役割 | 数 | すること | しないこと |
  | --- | --- | --- | --- |
  | 統括 | 1 | 作業全体を指揮する。実施内容と評価基準を決め、作業エージェントに作業を割り当て、検証結果を次の試行に反映する | ― |
  | 作業 | 1以上 | 割り当てられた作業をして、成果物を統括エージェントに返す | 自分の成果物の合否を決める |
  | 検証 | 1 | 成果物を評価基準に照らして判定し、合否と指摘を統括エージェントに返す | 成果物を直す |

- 根拠：憲章 第3条、第11条、第15条
- 受け入れ基準：
  - 統括1つ、作業1つ以上、検証1つのカスタムエージェントが定義されている。
  - 検証エージェントは、成果物を書き換えるツールを使えない設定になっている。
  - 成果物の合否は、検証エージェントだけが出す。

### REQ-007 役割ごとのモデル

- 要件：エージェントが使うモデルは、役割ごとに設定できる。既定では、統括と検証には思考力の高いモデル、作業には費用の低いモデルを割り当てる。
- 根拠：憲章 第11条、第12条1項／ナレッジ「マルチエージェントの強み」「カスタムエージェント」
- 受け入れ基準：
  - Web管理画面で、役割ごとのモデルを変えられる。
  - 変えたモデルが、次の実行から使われる。

## 4. PDS サイクル

### REQ-008 試行の流れ

- 要件：生成プラグインは、次の流れを1回の試行として繰り返す。
  1. Plan：統括エージェントが、実施内容と評価基準を決める。
  2. Do：作業エージェントが、実施内容に沿って作業する。
  3. Study：検証エージェントが、成果物を評価基準に照らして判定し、合否と指摘を統括エージェントに返す。統括エージェントは、指摘を次の試行の計画に反映する。
- 根拠：憲章 第15条／ナレッジ「AI の思考サイクル（PDS）」
- 受け入れ基準：
  - どの試行でも、作業を始める前に評価基準が決まっている。
  - 2回目以降の試行の計画に、前の試行の指摘への対応が含まれている。

## 5. Web管理画面

### REQ-009 画面の構成

- 要件：生成プラグインは、ローカルWebサーバーを1つ起動し、ブラウザーで次の3つを表示する。
  - 開始前：設定（役割ごとのモデルなど）
  - 実行中：エージェントの動きの監視
  - 終了後：結果とサマリー
- 根拠：憲章 第12条〜第14条／ナレッジ「ハーネスエンジニアリングの目的と人間の役割」
- 受け入れ基準：
  - 1つのローカルWebサーバーで、3つとも表示できる。

### REQ-010 接続の制限

- 要件：Web管理画面のサーバーは、既定ではローカルホストのアドレスだけで接続を待ち受ける。
- 根拠：憲章 第12条2項
- 受け入れ基準：
  - 既定の設定で、同じマシンのブラウザーからは開ける。
  - 既定の設定で、ほかのマシンからは開けない。

### REQ-011 実行中の監視

- 要件：実行中は、次をリアルタイムで表示する。
  - 各エージェントの状態と担当タスク
  - 現在の PDS のフェーズ
  - エージェント間のデータの受け渡し（図で表示する）
  - 実行を止めるボタン
- 根拠：憲章 第13条／ナレッジ「ハーネスエンジニアリングの目的と人間の役割」
- 受け入れ基準：
  - ページを再読み込みしなくても、表示が更新される。
  - 止めるボタンを押すと、実行が止まる。

### REQ-012 終了後の結果

- 要件：終了後は、次を表示する。
  - 各エージェントの実行結果
  - 検証結果（評価基準ごとの合否と指摘）
  - 実行全体のサマリー
- 根拠：憲章 第14条／ナレッジ「ハーネスエンジニアリングの目的と人間の役割」
- 受け入れ基準：
  - 終了後に、上の3つが表示される。

## 6. ログと自己改善

### REQ-013 ログ

- 要件：実行中は、次をログに残す。
  - 各エージェントの開始と終了
  - エージェント間で受け渡したデータ
  - ツールやスクリプトの実行と、その結果（失敗を含む）
  - PDS のフェーズの切り替え
- 根拠：憲章 第16条1項／ナレッジ「自己改善」
- 受け入れ基準：
  - 振り返りの3つの観点（実行の失敗、エージェントの詰まりや停止、データの流れ）を、ログだけで確かめられる。

### REQ-014 振り返り

- 要件：実行後は、ログを振り返って次の観点で課題を洗い出し、Web管理画面に一覧で表示する。
  - 何かの実行に失敗していないか
  - エージェントが詰まったり止まったりしていないか
  - データがきれいに流れているか
- 根拠：憲章 第16条1項／ナレッジ「自己改善」
- 受け入れ基準：
  - 実行後に、課題の一覧が Web管理画面に表示される。

### REQ-015 Issue の起票

- 要件：洗い出した課題のうち、生成プラグイン自身の改善につながるものについて、Issue の案（タイトルと本文）を作ってユーザーに見せる。ユーザーが承認した案だけを、生成プラグイン自身の GitHub リポジトリに起票する。
- 根拠：憲章 第16条2項・3項／ナレッジ「自己改善」
- 受け入れ基準：
  - 承認されていない案は、起票されない。
  - 起票先は、`plugin.json` の `repository` に書いたリポジトリである。
