# 出力の要件

クリエイターが出力する生成プラグインが満たす要件を定める（憲章 第10条）。

## REQ-001 準拠仕様

- 要件：生成プラグインは、Agent Plugins 1.0.0 と GitHub Copilot CLI の公式プラグイン仕様に従う。両仕様が両立しない場合は、Agent Plugins 1.0.0 を優先する。
- 根拠：憲章 第5条
- 受け入れ基準：
  - Agent Plugins 1.0.0 の仕様に適合している。
  - GitHub Copilot CLI でインストールして使える。
  - Agent Plugins 1.0.0 が定めていない部品（カスタムエージェントなど）は、Agent Plugins 1.0.0 が定める拡張の仕組みに沿って置かれている。

## REQ-002 リポジトリの構成

- 要件：生成プラグインのリポジトリは、憲章・仕様書・設計書・実装資産の4種類の成果物を基本とする。
- 根拠：憲章 第6条1項
- 受け入れ基準：
  - 生成プラグインのリポジトリに、憲章・仕様書・設計書・実装資産がそろっている。

## REQ-003 成果物の優先順位

- 要件：生成プラグインの成果物の優先順位は、憲章 ＞ 仕様書 ＞ 設計書 ＞ 実装資産 とし、下位は上位に矛盾しない。
- 根拠：憲章 第6条2項
- 受け入れ基準：
  - 生成プラグインの成果物に、この優先順位が示されている。
  - 下位の成果物が、上位の成果物と矛盾していない。

## REQ-004 要件の追跡

- 要件：生成プラグインの仕様書の要件は、設計書・実装資産・テストまで追跡できるようにする。
- 根拠：憲章 第6条3項
- 受け入れ基準：
  - 生成プラグインの仕様書の各要件から、対応する設計書・実装資産・テストをたどれる。

## REQ-005 開発の進め方

- 要件：生成プラグインは、ユーザーと対話しながら、憲章 → 仕様書 → 設計書 → 実装資産 の順に開発・保守する。
- 根拠：憲章 第7条
- 受け入れ基準：
  - 生成プラグインの成果物は、ユーザーとの対話を通じて、憲章 → 仕様書 → 設計書 → 実装資産 の順に作られている。
  - 生成プラグインの成果物に、保守もこの順に行うことが示されている。

## REQ-006 分かりやすさ

- 要件：生成プラグインが人間に伝える内容と、人間が読む成果物は、分かりやすさを何より重視し、簡潔に、伝わる用語で書く。
- 根拠：憲章 第9条1項
- 受け入れ基準：
  - Web管理画面の表示、ユーザーへのメッセージ、人間が読む成果物が、簡潔で、伝わる用語で書かれている。

## REQ-007 指摘の直し方

- 要件：生成プラグインは、人間の指摘を、文言をそのまま残さず、目的に沿って直す。
- 根拠：憲章 第9条2項
- 受け入れ基準：
  - 指摘を受けて直した成果物に、指摘の文言や経緯がそのまま残っていない。

## REQ-008 マルチエージェント構成

- 要件：生成プラグインは、統括エージェント1体、作業エージェント1体以上、検証エージェント1体で構成する。
- 根拠：憲章 第11条1項
- 受け入れ基準：
  - 統括エージェントが1体定義されている。
  - 作業エージェントが1体以上定義されている。
  - 検証エージェントが1体定義されている。

## REQ-009 判定と修正の分担

- 要件：作業エージェントは、自らの成果物を判定しない。検証エージェントは、成果物を修正せず、指摘を統括エージェントに返す。
- 根拠：憲章 第11条2項
- 受け入れ基準：
  - 作業エージェントは、自らの成果物の判定を行わない。
  - 検証エージェントは、成果物を書き換えない。
  - 検証エージェントの指摘は、統括エージェントに返される。

## REQ-010 Web管理画面での設定

- 要件：生成プラグインは、ローカルWebサーバーを起動し、Web管理画面で各種設定を行えるようにする。
- 根拠：憲章 第12条1項
- 受け入れ基準：
  - ローカルWebサーバーを起動できる。
  - ブラウザーで Web管理画面を開き、設定を変更できる。

## REQ-011 接続の制限

- 要件：Web管理画面は、既定ではローカルホストからの接続だけを受け付ける。
- 根拠：憲章 第12条2項
- 受け入れ基準：
  - 既定の設定で、ローカルホストから接続できる。
  - 既定の設定で、ローカルホスト以外からの接続を受け付けない。

## REQ-012 監視

- 要件：Web管理画面で、各エージェントの状態・担当タスク・PDS のフェーズを監視でき、実行を停止できるようにする。
- 根拠：憲章 第13条
- 受け入れ基準：
  - 実行中に、各エージェントの状態が表示される。
  - 実行中に、各エージェントの担当タスクが表示される。
  - 実行中に、現在の PDS のフェーズ（Plan・Do・Study）が表示される。
  - Web管理画面から実行を停止できる。

## REQ-013 結果確認

- 要件：Web管理画面で、各エージェントの実行結果と検証結果を確認できるようにする。
- 根拠：憲章 第14条
- 受け入れ基準：
  - 各エージェントの実行結果を表示できる。
  - 検証エージェントの検証結果を表示できる。

## REQ-014 PDS サイクル

- 要件：生成プラグインは、PDS サイクルで成果物と作業の進め方を改善する。
  - Plan：統括エージェントが実施内容と評価基準を決める。
  - Do：作業エージェントが計画に沿って試行する。
  - Study：検証エージェントが結果を分析し、統括エージェントが次の試行に反映する。
- 根拠：憲章 第15条
- 受け入れ基準：
  - 試行の前に、統括エージェントが実施内容と評価基準を決める。
  - 作業エージェントが、計画に沿って試行する。
  - 検証エージェントが、試行の結果を分析する。
  - 統括エージェントが、分析の結果を次の試行に反映する。

## REQ-015 ログと振り返り

- 要件：生成プラグインは、実行中にログを残し、実行後にログを振り返って課題を洗い出す。
- 根拠：憲章 第16条1項
- 受け入れ基準：
  - 実行中にログが残る。
  - 実行後に、ログから洗い出した課題が示される。

## REQ-016 Issue の起票

- 要件：生成プラグインは、自身の改善につながる課題を見つけたら、自身の GitHub リポジトリに Issue を起票する。起票は毎回ユーザーの承認を得てから行う。
- 根拠：憲章 第16条2項・3項
- 受け入れ基準：
  - 改善につながる課題について、Issue の起票をユーザーに提案する。
  - ユーザーが承認した場合だけ、生成プラグイン自身の GitHub リポジトリに Issue を起票する。
