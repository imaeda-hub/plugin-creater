## 第1章 総則

### 第1条 目的と適用範囲

1. 本憲章は、クリエイターによって生成された生成プラグインである本プラグインの、開発・保守における原則を定める。
2. 本プラグインの仕様書・設計書・実装資産は、本憲章に従わなければならない。

### 第2条 憲章の構成

1. 本憲章は次の章で構成する。
   - 第2章 共通条項：クリエイターと全生成プラグインに共通の条項
   - 第3章 生成プラグイン機能条項：全生成プラグインが備える機能の条項

## 第2章 共通条項（共通条項版 0.4.0）

> 本章はクリエイター憲章と生成プラグイン憲章で**同一の文面**とする。本章の「本プラグイン」は、その憲章が適用されるプラグイン（クリエイター、または各生成プラグイン）を指す。

### 第C1条 用語

| 用語 | 定義 |
| --- | --- |
| クリエイター | リポジトリ plugin-creater 自身。Agent Plugin を生成するプラグインである |
| 生成プラグイン | クリエイターが生成した Agent Plugin |
| クリエイター憲章 | クリエイターの憲章（plugin-creater の `docs/constitution/constitution.md`） |
| 生成プラグイン憲章 | 生成プラグインの憲章。クリエイターがテンプレートから生成し、生成プラグインに同梱する |

本プラグインの全成果物は上記の用語を統一して使わなければならない。

### 第C2条 準拠仕様

1. 本プラグインは次の公式仕様に従わなければならない。
   - **Agent Plugins 1.0.0**（ベンダー中立のプラグイン形式）
   - **GitHub Copilot CLI** の公式プラグイン仕様
2. 少なくとも次を満たさなければならない。
   - プラグインのルートに `plugin.json` マニフェストを置き、必須項目（`name`、`version`）を記載する。
   - マニフェスト等で参照するパスはプラグインルートからの相対パスとし、ルートの外を指してはならない。
   - スキルは `SKILL.md`、エージェントは各仕様が定める定義ファイル形式で記述する。
   - MCP 設定などの構成ファイルに認証情報（トークン・パスワード等）を直接埋め込んではならない。
3. 両仕様で要求が異なる場合は、まず両方を満たす構成を検討しなければならない。両立できない場合は **Agent Plugins 1.0.0 を優先**し、GitHub Copilot CLI で動作しなくなる点などの差異と影響を設計書に記録して、ユーザーに伝えなければならない。
4. 準拠の判断は、常に各仕様の**最新の公式文書**を一次情報としなければならない。記憶や非公式資料のみを根拠にしてはならない。
5. 準拠仕様のバージョンは仕様書に明記し、仕様の改訂時は影響を評価しなければならない。

### 第C3条 自己改善

1. 本プラグインは、自身の改善につながる課題を発見した場合、**自身のソースコードを管理する GitHub リポジトリ**に Issue を起票する機能を持たなければならない。
2. 起票先は、自身のリポジトリと、固有条項で定めるリポジトリに限らなければならない。それ以外のリポジトリへ起票してはならない。
3. 起票前に既存 Issue との重複を確認しなければならない。
4. Issue には、課題の内容・発見の経緯・根拠（検証結果や試行結果など）・改善案を記載すべきである。
5. Issue に秘密情報・個人情報・ユーザーの機密データを含めてはならない。
6. 起票は外部への公開行為であるため、**毎回**ユーザーの承認を得てから行わなければならない。承認を省略する設定や自動起票を設けてはならない。

### 第C4条 リポジトリの構成と成果物の階層

1. 本プラグインのリポジトリは、次の4種類の成果物を基本としなければならない。

   | 成果物 | 内容 |
   | --- | --- |
   | 憲章 | プロジェクトが必ず守る最上位ルール |
   | 仕様書 | 実現する機能や振る舞いの要件 |
   | 設計書 | 仕様を実現するための構造・方式 |
   | 実装資産 | ソースコード、テストコード、`SKILL.md` 等のエージェント用定義ファイル |

2. 成果物の優先順位は **憲章 ＞ 仕様書 ＞ 設計書 ＞ 実装資産** とする。下位の成果物は上位の成果物に矛盾してはならない。
3. 矛盾を発見した場合は、下位の成果物を修正するか、正規の手続きで上位の成果物を改訂しなければならない。黙って下位側で上書きしてはならない。
4. 仕様書の各要件は、設計書・実装資産・テストへ追跡可能でなければならない（トレーサビリティ）。

### 第C5条 SWEBOKに基づくソフトウェアエンジニアリング

1. 本プラグインは、**SWEBOK（Software Engineering Body of Knowledge）の知識体系・考え方を踏まえてソフトウェア開発を行わなければならない。**
2. 要求分析、設計、実装、テスト、保守、品質管理などの観点を、Agent Plugin の作成・検証・改善に適用しなければならない。
3. 開発・検証の際は、SWEBOK の該当する知識領域を参照すべきである。
4. SWEBOK を一律の開発手順として扱ってはならない。対象プラグインの規模・目的に適した実践方法を選択し、その選択理由を設計書に記録すべきである。

### 第C6条 ユーザーとの対話による開発・保守

1. 本プラグインの開発・保守は、ユーザーと対話しながら **憲章 → 仕様書 → 設計書 → 実装資産** の順に進めなければならない。
2. 各成果物は、ユーザーの合意を得てから次の成果物の作成に進まなければならない。
3. 開発途中のユーザーの意見・判断は、該当する成果物に反映し、判断の経緯を記録しなければならない。
4. 後工程で前工程の変更が必要になった場合は、前工程の成果物に戻って修正し、ユーザーの合意を得なければならない。

### 第C7条 安全性と品質

1. 本プラグインは、ユーザーの承認なしに不可逆な操作や外部への公開行為（Issue 起票、push、外部送信など）を行ってはならない。
2. 秘密情報は環境変数や各クライアントの秘密情報管理機構を通じて扱い、成果物・ログ・画面表示に残してはならない。
3. 実装資産にはテストコードを含め、テストによる検証を経なければならない。

## 第3章 生成プラグイン機能条項

> 本章は生成プラグインだけに適用する。クリエイターはこれらの機能を持たず、生成プラグインがこれらを備えていることを検証する（クリエイター憲章 第P1条・第P3条）。

### 第F1条 機能に関する用語

| 用語 | 定義 |
| --- | --- |
| 統括エージェント | 作業全体の指揮とタスク分担を行うエージェント |
| 作業エージェント | 割り当てられた作業を実行するエージェント |
| 検証エージェント | 作業成果物を検証するエージェント |
| Web管理画面 | ローカルWebサーバーが提供する、設定・監視・確認を行うブラウザ画面 |
| 監視 | エージェントの動作・進捗を Web管理画面で把握すること |
| 確認 | 実行結果・検証結果を Web管理画面で参照すること |
| PDSサイクル | Plan（計画）– Do（実行）– Study（評価・学習）の反復 |

上記の用語を統一して使わなければならない（例：「指揮エージェント」ではなく「統括エージェント」）。

### 第F2条 マルチエージェント構成

1. 本プラグインは次の構成をとらなければならない。
   - **統括エージェント**：1体
   - **作業エージェント**：1体以上（複数体を想定）
   - **検証エージェント**：1体
2. 役割を分離しなければならない。
   - 作業エージェントは、自らの成果物の合否を判定してはならない。
   - 検証エージェントは、検証対象の成果物を自ら修正してはならない。指摘として統括エージェントへ返す。
   - 統括エージェントは、タスクの分担・進行・次の試行への反映に責任を持つ。
3. エージェント間の指示・報告・検証結果は記録として残し、後から追跡できなければならない。

### 第F3条 Web管理画面（設定・管理）

1. 本プラグインはローカルWebサーバーを起動し、ブラウザ上の Web管理画面から各種設定を行えなければならない。
2. ローカルWebサーバーは、既定でローカルホスト（ループバックアドレス）のみで待ち受けなければならない。外部公開はユーザーが明示的に設定した場合に限る。
3. Web管理画面は、設定変更の内容を保存前に表示し、変更履歴を残すべきである。
4. Web管理画面は、認証情報などの秘密情報を平文で表示・記録してはならない。

### 第F4条 実行監視

1. 各エージェントの動作・進捗は、第F3条と**同じ** Web管理画面で監視できなければならない。
2. 監視画面では、少なくとも各エージェントの状態（待機・実行中・完了・失敗など）、担当タスク、現在の PDS フェーズを把握できなければならない。
3. ユーザーが実行を停止・中断できる手段を提供しなければならない。

### 第F5条 実行結果の確認

1. 各エージェントの実行結果および検証結果は、第F3条と**同じ** Web管理画面で確認できなければならない。
2. 実行結果と、それに対する検証結果は対応付けて表示しなければならない。
3. 検証結果には、合否だけでなく判定根拠（評価基準・観測事実）を含めなければならない。

### 第F6条 PDS試行サイクル

1. 本プラグインは PDS サイクルを用いて、成果物と開発プロセスを継続的に改善しなければならない。
   - **Plan（計画）**：統括エージェントが実施内容と評価基準を決める。評価基準は Do の前に確定しなければならない。
   - **Do（実行）**：作業エージェントが計画に沿って試行する。
   - **Study（評価・学習）**：検証エージェントが結果を評価基準に照らして分析し、統括エージェントが次の試行へ反映する。
2. 各サイクルの計画・実行結果・評価結果・反映内容は記録し、Web管理画面で確認できなければならない。
3. Study で得た学びのうち、本プラグイン自身の改善に関わるものは第C3条（自己改善）の対象とする。

## 第4章 生成プラグイン固有条項

### 第G1条 共通部分の不変性

1. 第2章から第4章は、変更・削除してはならず、その効力を弱める条項を追加してはならない。
2. 本プラグイン固有の原則は、第5章に追加してよい。

### 第G2条 自己保守

1. 生成後の本プラグインの保守は、本プラグイン自身が担う。
2. 保守は、第C6条の手続き（ユーザーとの対話、成果物の順序、合意）と第F6条の PDS サイクルに従って行わなければならない。

### 第G3条 クリエイターへの Issue 起票

1. 本プラグインは、課題の原因がクリエイター（生成の不備、テンプレートの誤りなど）にあると判断した場合、クリエイターのリポジトリ（{{GENERATOR_REPOSITORY}}）にも Issue を起票してよい。
2. この起票にも第C3条の第3項から第6項（重複確認、記載内容、秘密情報の除外、毎回の承認）を適用する。
3. Issue には、本プラグインの名称、共通条項版、クリエイターに原因があると判断した根拠を記載すべきである。

### 第G4条 改訂

1. 第5章の改訂は、改訂理由・変更内容・影響範囲を明示し、ユーザーの承認を得て行わなければならない。
2. 改訂時は版を更新し、変更履歴に記録しなければならない。
3. 改訂後は、仕様書・設計書・実装資産との整合を確認しなければならない。
