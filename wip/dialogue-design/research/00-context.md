# 調査の共通の前提（全エージェント共通）

## プロジェクト

- リポジトリ `/home/user/plugin-creater`（読むだけ。変更・コミット・push はしない）。
- 「クリエイター」= GitHub Copilot CLI 向けの Agent Plugin で、ユーザーとの対話でユーザーの仕事のナレッジ（本人には当たり前で、AI が知らないこと）を引き出し、それを組み込んだ Agent Plugin（「生成プラグイン」）を生成する。
- 最大の目的：ユーザーとの対話を通じてユーザーのナレッジを引き出し、それを組み込んだ、公式仕様に準拠した Agent Plugin を生成する（`docs/constitution/constitution.md`）。
- 対象：GitHub Copilot CLI 1.0.98（2026年10月時点。npm の最新は 1.0.101）、Agent Plugins 1.0.0。今日は 2026-10-20。
- 仕様：`docs/specs/creation-requirements.md`（特に REQ-015〜REQ-020、REQ-024、REQ-026、REQ-032〜REQ-038、REQ-043、REQ-049）。
- 既存の設計：`docs/design/creator-structure.md`（スキル make-plugin、メインのエージェント、作業エージェント）、`docs/design/generated-plugin-structure.md` 9章（クリエイターの画面と記録のツール）、`docs/design/testing.md` 6章（外側の EVAL：ユーザー役の AI で対話を模擬して採点）。
- ナレッジ：`.claude/memory/`（特に knowledge-elicitation.md、skill-creator.md、user-simulation.md、custom-agents.md、copilot-cli-testing.md、skills.md、communication.md）。

## 決まっている制約

- ユーザーと話すのはメインのエージェント（ユーザーが Copilot CLI で選んだモデル。GPT 系・Claude 系・Gemini 系などがあり得て、プラグインからは決められない）。サブエージェントはユーザーに質問できないものとして設計する。
- 対話の手順はスキル `make-plugin` の SKILL.md に書く。
- 決まったことは、クリエイターのエクステンションの記録のツールで、ブラウザーの画面（見るだけ）に出す。
- 仕様で決まっている「何を聞くか」：作業の目的／頼む場面と言い方／受け取るもの／進め方／成果物／合否の決め方／決まった書き方やルール／守らないと困ること／使う道具と環境／いつもと違うとき（REQ-015）。実際の1回をたどる（REQ-016）。ファイルを読んで「〜という決まりですか？」と確かめる（REQ-017）。画面で設定したいこと・見たいこと（REQ-026）。既存の資産（REQ-018）。標準機能と公開プラグイン（REQ-019）。生成前の確認（REQ-020）。既存プラグインの作り直し（REQ-032〜036）。質問の改善案（REQ-049）。

## これから設計で決めること（調査はこれに答える材料を集める）

1. 対話の段階と順番（項目ごとの質問、実際の1回、ファイル、資産、画面、確認をどの順で、どう組み合わせるか）
2. 質問の形（質問のツールの選択肢か自由回答か、1回に1つか複数か、推奨の選択肢を示すか、質問の理由を示すか）
3. 答えがあいまいなときの見分け方と聞き直し方（深掘りの型、回数の上限、「分からない」への対応）
4. 聞き漏らしの管理と、聞き終える判断（網羅の確かめ、飽和、ユーザーの疲れ、質問の数の目安）
5. 引き出したナレッジの残し方（一覧の形、ユーザーの言葉をどこまで残すか、復唱して確かめるか、合否の基準と EVAL の課題への変え方）
6. 長い対話の状態の保ち方（会話の要約・圧縮で手順や途中の結果が消えないか、中断と再開）
7. ファイルを読んで決まりを推し量るときの進め方
8. 仕事の分け方（メインのエージェントに残すことと、サブエージェントに任せられること）とモデル
9. 分かりやすい伝え方（専門用語を避ける）
10. どの質問が効いたかの記録（質問の改善 REQ-049 と外側の EVAL のため）
11. 費用の低いモデルや、ユーザーが選んだ様々なモデルでも、手順が守られるようにする書き方

## 調査の決まり（必ず守る）

- 推測で書かない。すべての主張に出典を付ける（URL とアクセス日、または「パッケージのファイルのパス＋版」、または「実際に動かした結果＋手順」）。
- 一次情報（公式ドキュメント、公式リポジトリ、論文の本文、パッケージの中身、実際に動かした結果）と、二次情報（ブログ、紹介記事）を分けて示す。
- 大事な主張は、原文を短く引用する（英語のままでよい）。
- 公開日・版を書く。古い情報（2024年以前）は古いと明記し、今も有効か確かめる。
- 情報が食い違うときは両方を示す。見つからなかったことは「見つからなかった」と書く（どこを探したかも）。
- 学習データの記憶だけで書かない。必ず実物を開いて確かめる。
- 報告は指定のファイルに Markdown で書く（日本語。引用は原文のまま）。最後に、設計で決めること 1〜11 のどれに効く情報かの対応表と、確信度（高・中・低）を付ける。
- 最終の返事には、ファイルの場所と、要点（10〜20行）を返す。
