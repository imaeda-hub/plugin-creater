### 注 A　check_structure.py で直すこと

1. カスタムエージェントの項目の許可リストに `model-policy` がない（実装の書き方。今は警告止まり）。`model` が1つでも優先する順のリストでも認める（testing.md 2章）。`tools` の型だけ見ていて `model` の型は見ていない。
2. 設計が1段目に足すと決めた検査が、試作にはない。
   - 作業の定義が決まりの形に合う、EVAL の課題の基準の写しが作業の定義と同じ、ナレッジの番号が種類ごとの置き場所にある（testing.md 10.3）。
   - 検証エージェントの `tools` に書き込みとコマンドがない、統括・作業・検証の `tools` に `skill` がない、記録のツール名の頭がプラグイン名、要件の追跡の表がそろっている（generated-plugin-structure.md 10章、8章）。
   - クリエイター自身には、会話例の版と `plugin.json` の版、make-plugin の SKILL.md の行数とトークン数、references の大きさ（hearing.md 12章）。
3. 試験の入口（10.2）が読めるよう、報告をファイルにも書く。
4. フックの検査は `type: command` だけ見ている。Copilot のフックには `http`・`prompt` の型と、`exec` を `bash`・`powershell`・`command` と併用できない決まりもある（2026-10-22 の公式リファレンス）。生成プラグインのフックが `hooks.json` に残るなら足す。残らないなら（フックがエクステンションの中に移る）、足さない。

1. 試験の対象が変わる。フックは `hooks.json` からエクステンションの中へ、MCP サーバーは固定の1つから作業ごとのものへ。固定の `calc_server.py` 向けの試験は、`mcp.json` を読んで各 stdio サーバーを起動し、`initialize`→`tools/list`→（作業エージェントが書く）呼び出しの事例、という汎用の形にする。

3. Inspector は `npx -y @modelcontextprotocol/inspector`（版の指定なし）で呼んでいる。毎回同じ結果にするため、版を固定する。最新の 2.12.0 で、試作が使う書き方（`--cli`、`--method tools/list`、`--method tools/call --tool-name … --tool-arg amount=…`）が今も通ることを確かめた。

### 注 C　convert.py で直すこと（testing.md 4章との差）

1. モデル。試作は、Claude のモデルを別名（`haiku`、`sonnet`、`opus`、`fable`）にし、Claude 以外は `inherit` にしている。`model` が優先する順のリスト（設計の書き方）のときは、文字列でないので「Claude Code で使えない」と警告して `inherit` にする（不具合）。設計は、次のとおり。
   - 候補の最初の Claude のモデルを、Claude Code の ID にする（例：`claude-haiku-5.5`→`claude-haiku-5-5`）。
   - 候補に Claude がなければ、Copilot の価格表で同じ値段の Claude にする（変換スクリプトに表を持つ）。
   - `model` のないエージェントには `model: inherit` を入れる。
   - `model-policy` を外す（試作は、黙って写さないだけで、警告も出さない）。
   - 別名ではなく ID にする理由：別名の解決先はプロバイダーで変わる（公式 model-config。Anthropic API では sonnet＝Sonnet 5.5、haiku＝Haiku 5.5、opus＝Opus 5.5。AWS・Bedrock・Foundry では古い版）。
   - Web管理画面で選ぶモデル（Copilot の名前）を ID にする同じ表を、試験の仕組みも使えるようにする。
2. エクステンションのツール名（`weekly-report_plan` のような名前）を、`mcp__<サーバー名>__<ツール名>` に置き換える処理がない（新規）。本文の置き換えの正規表現（`` `([a-z_]+)` ``）は、ハイフンを含む名前に合わない。
3. 会話例を置き換えた版から外す（6.6）。
4. 変換の直後に `claude plugin validate` を呼ぶ（試作は呼んでいない。4章の決まり）。
5. SKILL.md とエージェントの本文の `${PLUGIN_ROOT}` を `${CLAUDE_PLUGIN_ROOT}` にする。公式（plugins-reference）では、本文の中の `${CLAUDE_PLUGIN_ROOT}` が読み込みのときに置換される。試作の変数の置き換えは、設定ファイル（`.mcp.json`、フック）だけである。生成プラグインの本文がこの変数を使うなら、直す。
6. 小さな不具合：`tools` が文字列のとき（check_structure は認めている）、1文字ずつ処理する。フックの `timeout`（`timeoutSec` の別名）と、`powershell` だけの項目を扱わない。
7. エクステンション（`com.github.copilot/extensions/`）は、`com.github.copilot` を丸ごと除いているので、黙って外れる。設計の「外す」と同じ結果だが、変換レポートに記録すると追いやすい。
8. 変換スクリプトの2段目の試験（4章）が、試作にない。

### 注 D　lib.mjs で直すこと

1. `pathToClaudeCodeExecutable` に `which claude` を使っている。SDK は同じ版の Claude Code の本体を同梱している（0.3.302→2.1.302、0.3.307→2.1.307）。手元の `claude` を使うと、版が食い違う。今の環境は、手元の `claude` が 2.1.307 で、試作の SDK が 0.3.302 なので、試作のままでは食い違う。設計 11.1 の「Claude Code と同じ版にそろえる」は、この指定をやめれば自然に満たされる（要確認：同梱の本体で、サンドボックスが動くこと）。

## 2. 模擬ユーザーの合い具合

試作の模擬ユーザー（週報、議事録）の形は、次のとおり。両方に共通：`request`（依頼の文）、`profile`（人物の説明）、`knowledge`（4件。`id`、`fact`、`reveal`＝答える条件、`volunteer`＝自分から話すか）、`markers`（生成プラグインに入ったかを見る言葉）、`userRoleTests`（ユーザー役の試験の質問と、聞いたかを見る言葉 `askedMarkers`、漏れを見る言葉 `leakMarkers`）、`styles`（話し方）。週報だけ：`inner`（内側の EVAL の入力、頼む言葉、画面の設定、採点6件）。ナレッジの内訳は、どちらも「自分から話す」2件、「聞かれないと話さない」2件。

### 足すもの（まとめ）

- 示すファイル（`files`）：名前、中身（docx か xlsx を1つ以上。本当の決まり、例外のある決まり、たまたまの書き方を1つずつ）、ユーザー役が答える場所。置く処理は試験の仕組みに足す。docx・xlsx を作るのに、この環境には python-docx 1.2.0 と openpyxl 3.1.5 が入っている（試作の `requirements.txt` にはない）。作って置くか、作った実物を置くかは決めていない。
- ナレッジの種類（本当の決まり、例外のある決まり、たまたま）と、決まりの確かめの各答えでのユーザー役の答え方。「違う」「たまたま」のナレッジが組み込まれていないことを見る採点（6.5）。
- まだやったことのない模擬ユーザー（ファイルなし、想定の1回）。
- 話し方：「分からない」がち、「特にない」がち、急いでいる。急いでいるは、途中で急ぎの合図（「早く」「まだ？」、答えが短くなる。REQ-015）を出させる必要があり、話し方の1文だけで足りるかは、ユーザー役の試験で確かめる。
- 議事録に、内側の EVAL の課題と採点。
- 画面で選ぶモデルを Copilot の名前に。

## 流用の見積もり（憲章 第10条）

- 流用する（直して）：`convert.py`、`check_structure.py`、公式スキーマの写し、`lib.mjs`（`runAgent`、`askUserRole` の版3）、`outer.mjs`、`inner.mjs`（画面の操作を除く）、`test_user_role.mjs`、`test_components.py` と `ui_test.mjs` の骨組み、模擬ユーザーの形。試作 2,393行のうち、約 1,760行（`convert.py` 283、`check_structure.py` 188、スキーマ 185、`lib.mjs` 198、`outer.mjs` 115、`inner.mjs` 132、`test_user_role.mjs` 110、`test_components.py` 144、`ui_test.mjs` 88、模擬ユーザー 318）が流用の元になる。
- 使わない：`template/` 一式、`scaffold.py`、試作と対照の `SKILL.md`、`sandbox_smoke.mjs`、試作の `README.md`、`calc_server.py`（試験の仕組みの自己試験が要るときだけ例外）。
- 新しく書く量が最も多いもの：Agent SDK 用のつなぎ口、中心の処理の2段目の試験（偽物のつなぎ口）、6.5 の機械的な採点、示すファイルと決まりの確かめに合う模擬ユーザー、ユーザー役の試験の合格条件。

## 判断が要ること

各項目に、推奨とその理由をつけた。

1. **開発の試験の仕組みを置く場所と、2章の表への行**。[creator-structure.md](../../../docs/design/creator-structure.md) 2章の部品の表に、変換スクリプト、Agent SDK の runner、模擬ユーザー、ユーザー役の試験の行がない（11.1 は「試験の仕組みのフォルダ」と書くが、場所を決めていない）。
   - 推奨：表に「開発の試験の仕組み」の行を足し、置き場所を1つのフォルダに決める。理由：表は、仕様書の要件を部品にたどれるようにするためのもの（憲章 第6条3項）で、表にない部品は追跡できない。
2. **「見ない模擬ユーザー」の扱い**。模擬ユーザーのファイルをリポジトリに置くと、実装する AI が読める（6.6 が会話例について書いているのと同じ理由）。試作の週報と議事録は、この調査で両方読まれたので、見ていない模擬ユーザーとしては使えない。
   - 推奨：試作の2人（週報、議事録）は「直すときに使う」模擬ユーザーとして直して使い、見ない模擬ユーザーは別の分野で新しく作って、リポジトリの外に置く。理由：6.3 のねらいは、見ていない模擬ユーザーで確かめることで、すでに読まれたものでは果たせない。リポジトリに置いて「読まない約束」にするだけでは、守られたかを確かめられない。
3. **示すファイル（docx・xlsx）を作る方法**。毎回スクリプトで作るか、作った実物を置くか。
   - 推奨：スクリプトで作る（python-docx と openpyxl。環境に入っている）。理由：中身が文章として読め、差分が見える。実物のバイナリを置くと、中身を確かめにくく、リポジトリも膨らむ（憲章 第10条）。`requirements.txt` に2つを足す。
4. **ユーザー役のモデル**。試作は Sonnet の別名で通った。
   - 推奨：ID に固定したうえで、ユーザー役の試験をやり直し、通ったものを固定する。理由：別名の解決先はプロバイダーで変わり、ユーザー役が変わると同じクリエイターでも結果が変わる（6.2）。
5. **Playwright の版**。
   - 推奨：1.56.1 に固定したままにする。理由：環境のブラウザーが 1.56.1 用で、1.64.1 は起動に失敗した。環境のブラウザーを入れ直すときに、版を上げる。
