### D-01（medium）作業エージェントが動かなかった試行で、検証を頼み直し続けて実行が終わる
- 場所：手順の2の3つ目「作業エージェントが何を返しても（作れなかったと返しても）、評価に進む。」と、3の3つ目「合否を記録できなかったと返ったときは、その理由を書き添えて、もう一度頼む。」
- 問題：`task` の呼び出しがエラーで返り、作業エージェントが起動しなかったとき（エージェントの種類の名前の書き違いなど）も、手順は評価に進ませる。中心の処理は、その試行に作業エージェントが1体もいないと合否の記録を断り、「この試行の作業エージェントが、まだ終わっていません。作業が終わってから合否を記録してください。」と返す。検証エージェントは直せないので理由を返し、統括は3の3つ目に従って検証だけを頼み直す。合否の断りは数えられるので、やり直しの上限（3回）を超えて、実行が「途中で終わった（記録のやり直しが上限を超えた）」になる。作業エージェントを呼び直す手順がどこにもない。計画の記録より前に作業エージェントを呼んでしまったとき（手順の1の理由に書かれた場面）も同じ断りになり、同じ道をたどる。
- 根拠：records.mjs の recordVerdict「`if (workers.length === 0 || workers.some(isActiveAgent)) refuse('この試行の作業エージェントが、まだ終わっていません。…')`」と、COUNTED_TOOLS に verdict が入ること・LIMITS.RETRY_LIMIT が 3。設計書 4.8「その試行の作業エージェントが終わる前の合否の記録は断る」「断られたやり直しには上限（例：3回）を置く」。B2 の指示の「決まり」の統括の手順「記録のツールに断られたら、返された理由に沿って直す」。
- 直し方：手順の2に「`task` の呼び出しがエラーで返った（作業エージェントが動かなかった）ときは、エージェントの種類の名前を上の一覧と見比べて直し、もう一度呼ぶ。動いた作業エージェントが返したことなら、何を返しても評価に進む。」と分けて書く。3の3つ目に「理由が『この試行の作業エージェントが、まだ終わっていません』なら、検証を頼み直さず、この試行の計画が記録されていることを確かめてから、作業エージェントを呼ぶ（2）。」を足す。あわせて、作業エージェントが1体もいないときの断りの文を「この試行では、まだ作業エージェントが動いていません」と分ける案を、作業のメモで A1（core）に渡す（今の文は、動いていないのか終わっていないのかが分からない）。
- 確かさ：たぶん（手順に呼び直しがないことは確か。`task` に知らない名前を渡したときに、`subagent.started` が出ずにエラーで返るかは、実機か 1.0.102 のパッケージで確かめる）

### D-02（medium）振り返りとまとめのツールが「まだ繰り返しの途中です」と断られたときの扱いがない
- 場所：「記録のツールに断られたとき」の節。箇条は「計画が「繰り返しはもう終わっています」と断られたら、まとめ（5〜8）に進む。」と「作業を終えてください」の2つだけ。
- 問題：計画の側の食い違い（中心の処理はまとめ中、統括は繰り返しの途中と思っている）は書かれているが、逆の食い違い（統括はすべて合格か上限に達したと思って `_review` を呼ぶが、中心の処理はまだ実行中）が書かれていない。起きるのは、検証エージェントが「記録した」と返したのに合否を記録していなかったとき、統括が試行の数を数え違えたときなどである。断りの文は「まだ繰り返しの途中です。…_review は、評価基準をすべて満たすか、上限の回数まで試行した後に呼んでください。」だけで、合否がないのか不合格が残るのかを言わない。節の冒頭の「理由に沿って直して、呼び直す」に従うと、`_review` を呼び直す、合否のないまま次の試行の計画を出す（中心の処理は断らない）、検証を頼み直す、のどれにもぶれる。`_review` を呼び直すと、断りが数えられて上限を超え、実行が途中で終わる。
- 根拠：records.mjs の requireSummarizing（まとめ中でなければ断る）と、COUNTED_TOOLS に review・issue・finish が入ること。A1 のメモ「前の試行の合否が未記録のまま次の計画を出すことは断らない（データの流れの課題に入る）」。設計書 4.8「実行中（繰り返しの途中）の `_review`・`_issue`・`_finish` は断り、「まだ繰り返しの途中です」と返す。まとめ中に移るのは、合否の記録ですべて合格か、上限の試行の合否が記録されたときである。」。REQ-011 の受け入れ基準「ユーザーは、試行ごとに、評価基準と、評価基準ごとの合否・指摘を見られる」。
- 直し方：節に箇条を足す。「`{{plugin_name}}_review`・`_issue`・`_finish` が「まだ繰り返しの途中です」と断られたら、今の試行の合否が記録されていないか、不合格が残っていて上限に達していない。検証エージェントに、記録したかを書き添えて確かめを頼み直す（3）。返った合否に不合格があり、上限に達していなければ、次の試行に進む（4）。`_review` をそのまま呼び直さない。」。あわせて、断りの文で「試行 n の合否がまだ記録されていません」と「不合格が残っています（試行 n／上限 m）」を分ける案を、作業のメモで A1 に渡す。
- 確かさ：確か（手順にないことと、断りが数えられること）。どれだけ起きるかは、たぶん（EVAL で見る）

### D-03（low）「この実行は止められた」として拒まれたことを、モデルが見分けられないおそれ
- 場所：「記録のツールに断られたとき」の2つ目「…またはツールが「この実行は止められた」として拒まれたときは、ほかのツールを呼ばずに、…手番を終える。」（検証の定義の手順の3の3つ目にも同じ文がある）
- 問題：止めた後のツールは、エクステンションのフック（onPreToolUse）で拒まれる。設計書は、拒んだツールが「Denied by preToolUse hook」で失敗すると書く。つなぎ口は理由（「この実行は止められたため、ツール「…」は使えません。」）を `permissionDecisionReason` で返すが、モデルに理由まで届くかは確かめていない。届かなければ、統括は条件に当たらないと読み、別のツールを試し続ける（どれも拒まれる）。取り消し（tasks.cancel）で止まるのが本筋なので害は小さいが、止めきれなかったときに、拒まれたツールを繰り返す跡が課題に出る。
- 根拠：設計書 4.4「拒んだツールは「Denied by preToolUse hook」で失敗し、チャットの許可の確認は出ない（確かめた、11章 #13）」。adapter.mjs の onPreToolUse「`return { permissionDecision: 'deny', permissionDecisionReason: String(verdict.reason ?? '') }`」。index.mjs の preToolUse の理由の文。
- 直し方：統括と検証の文を「ツールが「この実行は止められた」か「Denied by preToolUse hook」として拒まれたとき」にする。作業エージェントにも同じ扱いを足す（D-06）。
- 確かさ：たぶん（理由の文がモデルに届くかを、実機の 11章 #13 の記録か 1.0.102 のパッケージで確かめる）

### D-04（low）最後の返事の形が、画面のまとめと終わった理由を言い換えて繰り返す
- 場所：「返す形」の雛形「結果：<すべての評価基準を満たした／上限の回数まで試行した／途中で終えた（理由）>（試行 <回数> 回）」「成果物：<場所>」「まとめ：<1〜3文>」
- 問題：同じ画面に、中心の処理が決めた終わった理由（「評価基準をすべて満たした」「上限の回数に達した」など）と、`_finish` で記録したまとめ（試行の数、満たした基準、成果物の場所）が出る。最後の返事は、統括の枠の返事の要約にも出るので、同じことが言い換えの言葉（「上限の回数まで試行した」と「上限の回数に達した」）で2回出る。また、終わった理由をモデルが自分の言葉で申告する形になり、記録と食い違ったときに、ユーザーはどちらを信じればよいか分からない。「途中で終えた（理由）」は、止められたかつながりが切れたときにしか書かれず、そのときは統括が取り消されるか画面が切れていて、返事は画面に出ない見込みである。
- 根拠：REQ-025 の受け入れ基準「同じことを繰り返して書いていない」。設計書 4.8「終わった理由は、AI の申告ではなく、記録とイベントから中心の処理が決める（REQ-012）」。憲章 第10条1項。ui/static/app.js（エージェントの枠に `agent.replySummary`、終わりの欄に `run.endReason` と `run.summary` を出す）。
- 直し方：最後の返事を、まとめの記録を繰り返さない短い形にする。たとえば「実行の番号：<番号>」「まとめの記録：<記録した／記録できなかった（理由）>」「足した Issue の案：<件数>」だけにし、結果と成果物は `_finish` のまとめに書く、と書く。結果の行を残すなら、終わった理由の言葉を REQ-012 と同じ（「評価基準をすべて満たした」「上限の回数に達した」）にそろえる。
- 確かさ：たぶん（画面で2回出ることは app.js で確か。どの形がよいかは、画面の見え方で決める）
