### 1. skills/_entry_/SKILL.md（入口のスキル）

#### L-1 URL を示すときに、開始ボタンを押すと始まることを伝える指示がない

- 重さ：medium
- 場所：「作業を頼まれたとき」の 2.「返った URL を示し、あわせて次の3つを伝える。」
- 問題：ユーザーに伝える中身が「`/clear` を使わない」「確認はチャットで答える」「前もって許可するしかたは README にある」の3つに限られていて、いちばん大事な次の行動（URL をブラウザーで開き、画面で設定して開始ボタンを押すと作業が始まる。チャットで待っていても始まらない）が入っていない。「次の3つ」と数を決めているので、モデルがこの3つだけを伝え、ユーザーが作業はもう始まったと思ってチャットで待つおそれがある。
- 根拠：
  - REQ-005 の要件「ユーザーは、ブラウザーでこの画面を開き、開始前の設定をして開始ボタンを押す」、受け入れ基準「開始ボタンを押すと、チャットでもう一度頼まなくても、頼んだ作業が始まる」。
  - README のひな形「使い方」2・3「ブラウザーで開きます」「…決めて、開始ボタンを押します」。
  - R1 (3-3)「Sonnet 5 は…1つの項目への指示を、ほかの項目に広げない」（並べた項目だけを伝えやすい）。
- 直し方：2. を「返った URL を示し、あわせて次の4つを伝える」にし、先頭に「URL をブラウザーで開き、画面で設定して開始ボタンを押すと作業が始まること（チャットで待っていても始まらない）」を足す。
- 確かさ：たぶん。`{{plugin_name}}_open` の説明の文（tools.mjs）にも「作業はまだ始まらず、ユーザーが画面で設定して開始ボタンを押すと始まる」があるので、モデルが自分から伝えることもある。試しの会話か EVAL で、URL の案内に開始ボタンのことが入るかを見れば決まる。

#### L-2 実行中にまた頼まれたとき、新しい頼みが始まらないことがユーザーに伝わらない

- 重さ：medium
- 場所：「実行中にまた作業を頼まれたときも、`{{plugin_name}}_open` を呼ぶ。新しい実行は始まらず、今の画面の URL が返る。」
- 問題：この場面でユーザーに何を伝えるかが書かれていない。しかも、core の `open`（core/index.mjs の `open()`）は、実行中でも準備中でも同じ形（URL と、`/clear` とチャットの確認の2つの知らせ）を返し、実行中のときは渡された `requestText` を黙って捨てる。メインのエージェントは、ユーザーが画面で開始を押したかを知らないので、実行中か準備中かを見分けられない。その結果、ユーザーは新しい頼みが受け付けられたと思うが、実際には今の実行が続くだけになる。
- 根拠：
  - 設計書 4.2「実行中に画面を開くツールがまた呼ばれたら、新しく始めず、今の URL を返す」。
  - core/index.mjs の `open()`：`active` のときは `ctx.requestText` を置き換えず、`notices` は `[CLEAR_NOTICE, CHAT_CONFIRM_NOTICE]` だけ（終わった後の「前の実行が途中で終わっていました」の知らせしか足されない）。
  - 憲章 第9条1項（人間に伝える内容は、分かりやすさを何より重視する）。
- 直し方：
  1. core の `open()` が、実行中のときに知らせを1つ足す（例：「いまの実行が終わるまで、新しい作業は始められません。今の画面で実行の様子を見られます。」）。これは処理の変更で B2 の範囲（説明の文だけ）の外なので、作業のメモの「上位の文書で直すこと」か A1 への引き継ぎに書く。
  2. スキルの上の文は、「新しい実行は始まらず、今の画面の URL と、そのことの知らせが返る。知らせのとおりに伝える」にする（2. の「返り値にほかの知らせ…があれば、それも伝える」で受けられるなら、この文は「新しい実行は始まらない」までで足りる）。
- 確かさ：確か（core/index.mjs の `open()` を読んで確かめた）。

#### L-3 ツールがないときの「確認の意味」が、チャットに出る英語の項目と対応づいておらず、README と形がそろっていない

- 重さ：low
- 場所：「`{{plugin_name}}_open` がないとき」の 2. の「確認の意味：{{plugin_name}} の記録のツールが、確認なしで画面の状態だけを書く。止めた実行のエージェントのツールを拒む。エージェントの許可の求めを見て画面に示すが、答えない…」と、題の「`Extension "…" wants elevated permissions`」、選択肢の「`Yes, and always allow "…" in this directory`」。
- 問題：
  - ユーザーがチャットで見るのは英語の「skip tool permission prompts, register hooks, handle permission requests」で、スキルの3つの文がそのどれに当たるかが分からない。README のひな形は、項目ごとに英語と意味を対で示している。
  - 「記録のツール」は説明のない言葉のまま出る。「止めた実行のエージェントのツールを拒む」は、何のためか（画面で止めた実行を確実に止めるため）が抜けていて伝わりにくい。
  - 名前の部分が、スキルでは `"…"`、README では `"<名前>"` で、書き方がそろっていない。
- 根拠：憲章 第9条1項。設計書 4.1「README と入口のスキルで、この確認の意味と、許可する理由と、2つの選び方とその違い…を示す」。README のひな形「3. 読み込むときの確認を許可する」の箇条（`skip tool permission prompts`（ツールの許可の確認を省く）：…、`register hooks`（フックを登録する）：止めた実行のエージェントのツールを拒むために…、`handle permission requests`（許可の求めを扱う）：…）。
- 直し方：「確認の意味」を README と同じ対の形にする。例：
  - `skip tool permission prompts`：{{plugin_name}} が画面の状態を書くためのツールを、確認なしで動かす（ファイルやコマンドなど外は変えない）。
  - `register hooks`：画面で止めた実行のエージェントが、ツールを使えないようにする。
  - `handle permission requests`：エージェントの許可の求めを見て、画面に「チャットで確認を待っています」と示す。答えはしない（許可も拒否も、ユーザーがチャットで行う）。
  
  題と選択肢の名前の部分は、README と同じ `"<名前>"` にする。
- 確かさ：確か。

#### L-4 失敗の理由を「そのまま」伝えると、説明のないエラーの文が出うる

- 重さ：low
- 場所：「作業を頼まれたとき」の 1. の「失敗が返ったときは、返った理由をそのまま伝えて、手番を終える。」
- 問題：画面を開けなかったときの理由には、下の部品のエラーの文がそのまま入る（core/index.mjs の `ensureUi` の「画面を開けませんでした：${e?.message ?? e}」）。英語のエラーの文などを、そのままユーザーに示すことになり、何が起きて、どうすればよいかが伝わらない。
- 根拠：憲章 第9条1項（簡潔に、伝わる用語で書く）。
- 直し方：「返った理由を伝える。英語のエラーの文や専門用語が入っていたら、その文は添えたうえで、何が起きたかを短く言い添える。そして手番を終える。」にする。
- 確かさ：たぶん。どんなエラーの文が返りうるかは、B1 の adapter の `startUi`（画面のサーバーの起動）の失敗のしかたで決まる。B1 の実装を見れば決まる。

#### 見たが指摘にしなかったこと（SKILL.md）

- 言語の決まり（「日本語で応答する。ユーザーが別の言語で書いたら、その言語で応答する」）：R1 の (1) 11 と同じ形で、作った者の判断（tasks/B2.md「決めたこと」）は正しい。
- `/clear`、チャットの確認、前もって許可するしかたの3つの文：README の「実行中に気をつけること」「任せたいツールを前もって許可する」（見出しの名前も一致）と食い違わない。`{{plugin_name}}_open` の返す知らせ（core/constants.mjs の `CLEAR_NOTICE`・`CHAT_CONFIRM_NOTICE`）と中身が重なるが、「同じことは2回書かない」で受けている。
- ツールがないときの3つの原因と直し方、「Yes」と「always allow」の違い、Disabled が次のセッションにも残ること：README の「うまく始まらないとき」と「3. 読み込むときの確認を許可する」と食い違わない。
- 終わりの知らせで伝える中身（各エージェントの結果、検証の結果、まとめ、終わった理由、課題の一覧と Issue の案）：README の「使い方」5 と合う。

### 2. com.github.copilot/extensions/_plugin_/core/tools.mjs（記録のツールの説明の文）と、画面に出る文の書き方

#### T-1 画面に出る文（計画、合否の指摘、まとめ、最後の返事）に、REQ-025 の書き方の指示がない

- 重さ：medium
- 場所：
  - tools.mjs：`plan` の説明と `plan` の引数の説明「この試行の計画。…」、`verdict` の `note` の説明「指摘。不合格のときは、直す点を書く。」、`finish` の説明と `summary` の説明「実行全体のまとめ」。
  - orchestrator.agent.md「返す形」の「記録のツールに渡す文（計画、Issue の案、まとめ）と最後の返事は、日本語で書く。画面でユーザーが読むためである。」
  - verifier.agent.md「返す形」の「次の形で、日本語で書く。指摘は、画面でユーザーも読む。」
  - worker.agent.md「返す形」の「次の形で、日本語で書く。」

- 根拠：REQ-025 の要件「Web管理画面の表示と Issue の案は、簡潔で、説明のない専門用語を使わない」、受け入れ基準「Web管理画面の表示と Issue の案に、説明のない専門用語がない」「同じことを繰り返して書いていない」。REQ-012（各エージェントの実行結果、検証結果、まとめを画面で見る）。

  - verifier.agent.md「返す形」を「次の形で、平易な日本語で簡潔に書き、説明のない専門用語を使わない。指摘と返事は、画面でユーザーも読むためである。」にする。
  - worker.agent.md「返す形」を「次の形で、日本語で簡潔に書く。返事は画面でユーザーも読むためである。」にする。
  - tools.mjs の説明の文には足さなくてよい（足すなら `issue` と同じ1文を `plan`・`verdict`・`finish` にそろえて置く）。

#### T-2 `plan` の「理由に沿って直して呼び直す」が、直せない断りでも呼び直すように読める

- 重さ：low
- 場所：`plan` の説明「決まりに合わない記録は、理由を返して断るので、理由に沿って直して呼び直す。」（`verdict` は「直せるときは直して呼び直す」）
- 問題：記録のツールは、直せない断りも返す（「この実行は止められました。ツールは使えません。作業を終えてください。」「画面とのつながりが切れたので、作業を終えてください。」「記録のやり直しが上限（3 回）を超えたため、この実行を終えます。作業を終えてください。」。core/constants.mjs、core/records.mjs）。`plan` の説明は無条件に「直して呼び直す」と書くので、統括の定義の「『作業を終えてください』と返されたときは、ほかのツールを呼ばずに…手番を終える」と食い違って読める。`verdict` と書き方もそろっていない。
- 根拠：R1 の (1) SKILL.md 10「食い違う指示やあいまいな指示を残さない。GPT-6 の族は…食い違いがあると止まりやすい」と、カスタムエージェント 12（同じにする）。統括の定義「記録のツールに断られたとき」。
- 直し方：`plan` と `verdict` の該当の文を、同じ「決まりに合わない記録は、理由を返して断る。返った理由に従い、直せるときは直して呼び直す。『作業を終えてください』と返ったら、呼び直さない。」にそろえる。
- 確かさ：たぶん。統括の定義が補っているので、実際にぶれるかは、止めた後や上限を超えた後に統括が呼び直すかを EVAL（または試しの実行）で見れば決まる。

#### T-3 `show` の key が「番号」と呼ばれ、エージェントが目にしない言葉（作業の定義、displays）で説明されている

- 重さ：low
- 場所：`show` の `key` の説明「表示の番号（作業の定義の displays の key）」、説明の本文の「作業ごとの指示に書かれた表示（key）」と「作業の定義にない key」、`value` の説明の「progress は { value, max, label? }」。
- 問題：
  - key は英字で始まる英数字と `_` の名前で（core/task.schema.json の displays の key の pattern `^[A-Za-z][A-Za-z0-9_]*$`）、番号ではない。「番号」と書くと、数（1、2…）を渡すと読まれうる。
  - 統括と作業エージェントが見るのは「作業ごとの指示」で、「作業の定義」「displays」は見ない。同じ説明の中で「作業ごとの指示」と「作業の定義」が混ざっている。
  - `value` の説明は、progress の「0〜100 の数」の形を落としていて、説明の本文と合わない。`label?` は TypeScript の書き方で、本文の「label はなくてよい」とそろっていない。
- 根拠：R1 の (1) SKILL.md 10（あいまいな指示を残さない）とカスタムエージェント 12。worker.agent.md の手順 4「作業ごとの指示に、送る表示が書かれていれば」。tasks/B2.md の差し込み口 `{{slot:orchestrator-task}}`・`{{slot:worker-task}}`「送る表示（key）」。
- 直し方：
  - `key`：「表示の名前（作業ごとの指示に書かれた key。英字で始まる英数字と _）」。
  - 本文：「作業の定義にない key と、形の合わない値は」を「作業ごとの指示にない key と、形の合わない値は」にする。
  - `value`：「…progress は 0〜100 の数か { value, max, label }（label はなくてよい）、…」と本文にそろえる。
  - 引数の説明（`parameters` の中の description）を直すことが B2 の範囲（「ツールの説明の文（description）だけ。引数の形は変えない」）に入るかは、統括が決める。入らないなら、本文の言葉の揺れだけを直す。
- 確かさ：確か（言葉のずれ）。「番号」で取り違えるかは、たぶん（断るときに使える key の一覧が返るので、2回目には直る）。

#### T-4 `open` の説明から、どの作業のためのツールかが分からない

- 重さ：low
- 場所：`open` の説明「ユーザーから、このプラグインの作業を頼まれたときに呼ぶ。」
- 問題：説明の文は core の決まった文で、どの生成プラグインでも同じになる（`buildToolDefinitions` は description をそのまま渡す）。メインのエージェントは、多くのツールの説明を並べて見るので、「このプラグインの作業」だけでは、何の頼みのときに呼ぶのかが分からない。入口のスキルを読まずにツールを選ぶ場面では、手がかりにならない。
- 根拠：R1 (3-1) の description の勧め（「何をするかと、いつ使うか。仕事を見分けるキーワードを入れる」、Anthropic「三人称で書く」）。スキルの説明の勧めだが、ツールの説明も同じく、モデルが選ぶ手がかりとしてシステムプロンプトに入る。
- 直し方：処理を変えずに直すなら「ツールの名前の頭にあるプラグインの作業を頼まれたときに呼ぶ。どんな作業かは、そのプラグインのスキルにある。」にする。作業の名前（task.json の name）を説明に入れるのは処理の変更になるので、入れるなら作業のメモに書いて A1 に頼む。
- 確かさ：たぶん。入口のスキルが先に読まれれば困らない。スキルを読まずにツールが呼ばれる（または呼ばれない）ことがあるかは、EVAL で決まる。

#### T-5 `finish` の説明と統括の定義で、まとめに書く中身がずれている

- 重さ：low
- 場所：`finish` の説明「実行全体のまとめ（何回の試行で、どの評価基準を満たしたか、成果物の場所）を記録し」と、orchestrator.agent.md の手順 7「まとめには、何回の試行で、どの評価基準を満たし、どれを満たせなかったかと、成果物の場所を書く。」
- 問題：統括は両方を読むので、満たせなかった基準を書かないまとめになりうる。上限の回数に達して終わったときに、ユーザーが画面のまとめで、何が足りなかったかを読めない。
- 根拠：R1 の (1) SKILL.md 10 とカスタムエージェント 12（食い違う指示を残さない）。REQ-012（実行全体のまとめを見られる）。
- 直し方：`finish` の説明の括弧を「（何回の試行で、どの評価基準を満たし、どれを満たせなかったか、成果物の場所）」にそろえる。あるいは括弧を消して、中身は統括の定義の手順 7 だけに書く（重複が減る。憲章 第10条）。
- 確かさ：確か（文のずれ）。

#### 見たが指摘にしなかったこと（tools.mjs）

- どの説明も「誰が、いつ呼ぶか → 何をするか → 決まり → 断るとき」の順で、三人称で書かれ、強い言葉がない（R1 の (1) 8）。

- `issue` の「平易な日本語で簡潔に書き、説明のない専門用語を使わない」は REQ-025 に合う。
- ナレッジの番号の例（`K-` に数字）は、説明の文にない。
