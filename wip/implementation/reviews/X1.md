### X1-01 統括の tools が、作業・検証のツールを含まない（子のツールは親のツールの範囲内になる）

- 重さ：high
- ファイルと場所：skills/make-plugin/assets/template/com.github.copilot/agents/orchestrator.agent.md のフロントマター `tools:`（`agent`、`read`、`search`、`{{plugin_name}}_plan`・`_review`・`_issue`・`_finish`・`_show`、`{{orchestrator_extra_tools}}`）。あわせて skills/make-plugin/scripts/scaffold.py の extra_tools の差し込み（作業・検証の extra_tools を統括に足さない）と、tests/stage1/check_structure.py の agent-tools の検査。
- 問題：Copilot CLI 1.0.102 では、`task` で呼んだサブエージェントのツールが、親（統括）のツールとの共通部分になる。統括が `edit`・`execute`・`{{plugin_name}}_verdict`・作業や検証の作業ごとの MCP のツールを持たないので、作業エージェントは成果物を書けず、検証エージェントは合否を記録できない。合否が記録されないので、どの実行も「途中で終わった」になり、REQ-010（合否は検証が出す）、REQ-011（繰り返し）、REQ-012 の結果が成り立たない。部品の間で見ると、作業・検証の定義の `tools`（worker.agent.md の `edit`・`execute`、verifier.agent.md の `{{plugin_name}}_verdict`、`{{worker_extra_tools}}`・`{{verifier_extra_tools}}`）と、統括の定義の `tools` の取り決めが食い違っている。1段目の検査もこの食い違いを見ない。
- 根拠：research/V1-copilot-cli-smoke.md 3節「そのままでは検証が `<名前>_verdict` を使えず、実行は途中で終わった」、4節「書いたツールだけが載る … ただし親が持つツールの範囲内」。tasks/V1.md「【重大】生成プラグインの作業エージェントと検証エージェントは、統括エージェントが持つツールしか使えない」（更新履歴 1.0.67「Subagent sessions keep parent tool restrictions」、1.0.68）。設計書 generated-plugin-structure.md 4.7 の表（統括は `agent`、`read`、`search`、記録のツール。作業は `edit`・`execute`…、検証は合否の記録のツール）は、この制約を前提にしていない。
- 直し方：V1 の 5節の案を待って、統括の取り決めを決め直す。案：(1) 統括の `tools` に、作業・検証が使うツールの和（`edit`、`execute`、`{{plugin_name}}_verdict`、作業・検証の extra_tools）を足し、scaffold.py が manifest.json の workers[].extra_tools と verifier.extra_tools を `{{orchestrator_extra_tools}}` にも入れる。統括の本文の「してはいけないこと」は今のまま（成果物を作らない、合否を決めない）にし、`_verdict` を統括が呼んでも core の records.mjs が役割で断ることを書き添える。(2) check_structure.py に「統括の tools ⊇ 作業・検証の tools」の検査を足す。(3) 設計書 4.7 の表と、ひな形の docs/design/design.md 3.5 の表を直す（上位の文書で直すこと）。
- 確かさ：確か（V1 が本物の Copilot CLI 1.0.102 と偽物のモデルで確かめた）

### X1-02 画面の「担当している作業」に、`task` の description でなくエージェントの短い名前が出る

- 重さ：medium
- ファイルと場所：skills/make-plugin/assets/template/com.github.copilot/extensions/_plugin_/adapter.mjs の `taskDescriptionOf`（「task ツールで起動したサブエージェントは、agentDisplayName に、呼び出しの説明（task の description）が入る」）と、orchestrator.agent.md「`description` には、何を頼むかが分かる短い説明 … を書く。画面に、そのエージェントの担当として出るためである。」
- 問題：統括の定義は「description が画面の担当に出る」を理由に書かせているが、つなぎ口が使う `agentDisplayName` は、実機では `worker`・`verifier` などの短い名前で、`task` の description ではない。画面の枠の「担当している作業」に `worker` と出て、REQ-008 の「担当している作業」と設計書 4.5 の「担当している作業（`task` を呼んだときの説明）」を満たさない。統括の定義が書く理由も事実と合わなくなる。
- 根拠：research/V1-copilot-cli-smoke.md 3節「`agentDisplayName` は短い名前（`orchestrator`、`worker`、`verifier`）」「画面の枠の『担当』（`task` 欄）が、呼び出しの説明ではなく、エージェントの短い名前になる。… `task` の `description` は、`tool.execution_start`（統括の `task` 呼び出し。`arguments.description`、`toolCallId`）にあり、`subagent.started.data.toolCallId` と同じ番号で結べる」。設計書 4.5「担当している作業（`task` を呼んだときの説明）」。
- 直し方：adapter.mjs の変換で、`tool.execution_start` の `toolName` が `task` のときに `toolCallId` → `arguments.description` を覚え、`subagent.started` の `data.toolCallId` で引いて `agent.started.description` に入れる。見つからないときだけ今の `agentDisplayName`／`agentDescription` を使う。tests/stage2/adapter/events.test.mjs の「担当」の試験を、この形の偽物のイベントに直す。
- 確かさ：確か（V1 の実測。偽物のモデルで、`task` の description の届き方を見た）

### X1-03 生成プラグインの設計書のひな形が、起動し直したときの扱いでユーザーの答え14と実装に反する

- 重さ：medium
- ファイルと場所：skills/make-plugin/assets/template/docs/design/design.md 5.1「自分のセッションの終わっていない実行は、すぐ途中で切れたとする。」と 3.7「エクステンションが起動したときに、終わっていない実行のうち途中で切れたものを、『途中で終わった（途中で切れた）』として終わらせる。」
- 問題：実装（core/recovery.mjs の `classifyUnfinishedRun`：自分のセッションの実行は `cancel_and_end`。動いているエージェントを `tasks.list` で探して取り消し、「途中で終わった（エクステンションが再起動した）」にする）と食い違う。生成プラグインの中で、設計書と実装資産が矛盾する（生成プラグインの憲章 第6条2項「下位は上位に矛盾しない」）。ユーザーが直すときに設計書を信じると、取り消しの処理を消してしまうおそれがある。
- 根拠：RESUME.md ユーザーの答え14「前の実行の統括・作業・検証エージェントがまだ動いていれば、tasks.list で探して tasks.cancel で取り消し、実行を『途中で終わった（エクステンションが再起動した）』にする」。tasks/A1.md「起動し直したとき（ユーザーの決定。…）」。ひな形の docs/constitution.md 第6条2項。
- 直し方：design.md 5.1 の「途中で切れた実行の見分け方」を、「自分のセッションの終わっていない実行は、木のエージェントを拒む一覧に入れ、`tasks.list` で動いているものを取り消して『途中で終わった（エクステンションが再起動した）』にする。動いているものがなければ『途中で切れた』にする（`/clear` の後など）」に直す。3.7 と 3.3 の「途中で終わった（理由つき）」の行にも「エクステンションが再起動した」を足す。クリエイターの設計書 4.13・6.5・10章も同じに直す（A1 の「上位の文書で直すこと」と同じ）。
- 確かさ：確か

### X1-06 起票の手順の文が「インストールはコピー」と書くが、README の入れ方では手元のフォルダを直接読む

- 重さ：low
- ファイルと場所：skills/make-plugin/assets/template/com.github.copilot/extensions/_plugin_/core/github.mjs の `STEP_REPOSITORY`「（インストールはコピーなので、入れ直さないと反映されません）」。ひな形の docs/design/design.md 5.3「インストールしたプラグインはコピーで、`.git` が残らないためである。」
- 問題：README のひな形は、手元のフォルダのマーケットプレイスから入れる手順にしている。この入れ方では、プラグインはコピーされず、フォルダを直接読む（次のセッションで反映される）。README の「`/restart` か新しいセッションで反映されます」と、画面に出る手順の理由が食い違う。手順そのもの（repository を書いて入れ直す）は REQ-014 のとおりで害はないが、理由が事実と合わない。
- 根拠：research/V1-copilot-cli-smoke.md 1節「手元のフォルダのマーケットプレイスから入れたプラグインは、コピーされず、そのフォルダを直接読む（`source: "live"`）」。README.md のひな形 23行目。
- 直し方：STEP_REPOSITORY の括弧を「（入れ直すか、新しいセッションを始めると反映されます）」にする。design.md 5.3 の理由を「マーケットプレイスから入れたプラグインはコピーのことがあり、`.git` から知れるとは限らないためである」に直す。クリエイターの設計書 4.11 も同じ（上位の文書で直すこと）。
- 確かさ：確か

- 直し方：task.schema.json の settings の key に `"not": { "enum": ["maxIterations"] }` を足す（または pattern で除く）。check_structure.py の task の試験に1件足す。
- 確かさ：確か
