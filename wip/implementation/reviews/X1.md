### X1-01 統括の tools が、作業・検証のツールを含まない（子のツールは親のツールの範囲内になる）

- 重さ：high
- ファイルと場所：skills/make-plugin/assets/template/com.github.copilot/agents/orchestrator.agent.md のフロントマター `tools:`（`agent`、`read`、`search`、`{{plugin_name}}_plan`・`_review`・`_issue`・`_finish`・`_show`、`{{orchestrator_extra_tools}}`）。あわせて skills/make-plugin/scripts/scaffold.py の extra_tools の差し込み（作業・検証の extra_tools を統括に足さない）と、tests/stage1/check_structure.py の agent-tools の検査。
- 問題：Copilot CLI 1.0.102 では、`task` で呼んだサブエージェントのツールが、親（統括）のツールとの共通部分になる。統括が `edit`・`execute`・`{{plugin_name}}_verdict`・作業や検証の作業ごとの MCP のツールを持たないので、作業エージェントは成果物を書けず、検証エージェントは合否を記録できない。合否が記録されないので、どの実行も「途中で終わった」になり、REQ-010（合否は検証が出す）、REQ-011（繰り返し）、REQ-012 の結果が成り立たない。部品の間で見ると、作業・検証の定義の `tools`（worker.agent.md の `edit`・`execute`、verifier.agent.md の `{{plugin_name}}_verdict`、`{{worker_extra_tools}}`・`{{verifier_extra_tools}}`）と、統括の定義の `tools` の取り決めが食い違っている。1段目の検査もこの食い違いを見ない。
- 根拠：research/V1-copilot-cli-smoke.md 3節「そのままでは検証が `<名前>_verdict` を使えず、実行は途中で終わった」、4節「書いたツールだけが載る … ただし親が持つツールの範囲内」。tasks/V1.md「【重大】生成プラグインの作業エージェントと検証エージェントは、統括エージェントが持つツールしか使えない」（更新履歴 1.0.67「Subagent sessions keep parent tool restrictions」、1.0.68）。設計書 generated-plugin-structure.md 4.7 の表（統括は `agent`、`read`、`search`、記録のツール。作業は `edit`・`execute`…、検証は合否の記録のツール）は、この制約を前提にしていない。
- 直し方：V1 の 5節の案から、設計者（統括）が1つに決める。注意：既定のモデル（ユーザーの答え17。統括は Claude の族、作業は GPT の族）では、統括の `tools` に `edit` を足しても、作業は `apply_patch` を受け取れなかった（V1 の 5節「混ぜたモデルの族の注意」）。そのため、(1) の案だけでは、既定のモデルで作業エージェントがファイルを編集できない。
  - 案 A：統括の定義から `tools:` を消し（全ツール）、統括に使わせたくないツール（`edit`・`execute`、設計書 4.7 が外す `skill` など）は、つなぎ口の `onPreToolUse` で統括の agentType のときに拒む（拒みの理由は「Denied by preToolUse hook: <理由>」でモデルに届く。V1 の 5節）。V1 の gen-d/ で、統括が Claude の族でも作業が `apply_patch` を受け取れた。core の preToolUse に「統括の番号のときに拒むツール」の決まりを足し、tests/stage2 に試験を足す。
  - 案 B：統括の `tools` に、作業・検証が使うツールの和（`edit`、`execute`、`{{plugin_name}}_verdict`、作業・検証の extra_tools）を足し、scaffold.py が workers[].extra_tools と verifier.extra_tools を `{{orchestrator_extra_tools}}` にも入れる。統括と作業のモデルの族が違うときの編集のツールの扱いを、別に決める必要がある。
  - どちらでも、check_structure.py の agent-tools に、選んだ形の検査（案 A なら統括に tools がないことを認める・検証に書き込みがないこと、案 B なら「統括の tools ⊇ 作業・検証の tools」）を足し、設計書 4.4・4.7・4.8 と、ひな形の docs/design/design.md 3.5 の表を直す（上位の文書で直すこと）。
- 確かさ：確か（V1 が本物の Copilot CLI 1.0.102 と偽物のモデルで確かめた）

- 重さ：medium
- ファイルと場所：skills/make-plugin/assets/template/com.github.copilot/extensions/_plugin_/adapter.mjs の `taskDescriptionOf`（「task ツールで起動したサブエージェントは、agentDisplayName に、呼び出しの説明（task の description）が入る」）と、orchestrator.agent.md「`description` には、何を頼むかが分かる短い説明 … を書く。画面に、そのエージェントの担当として出るためである。」

### X1-03 生成プラグインの設計書のひな形が、起動し直したときの扱いでユーザーの答え14と実装に反する

### X1-08 記録のツールの断りの理由が、モデルに届かない（統括・作業・検証の手順が、届かない文に頼っている）

- 直し方：adapter.mjs の `callTool` で、`RecordRefusal`（と、画面を開くツールの失敗）を受けたら、例外にせず `{ textResultForLlm: e.message, resultType: 'failure' }` を返す。想定外の例外も同じ形で平易な文にする。core の API（断るときは Error を投げる）は変えない。tests/stage2/adapter/fake-sdk.mjs を、本物と同じく「例外の文はモデルに届かない」「`textResultForLlm` が届く」形に直し、register.test.mjs の上の試験を「断りの理由が、ツールの結果の文として返る」に直す。R2 3.3 と設計書 4.8 の書き方も直す（上位の文書で直すこと）。クリエイターの creator.mjs の `guard` も同じ（X2 の範囲）。
- 確かさ：確か（V1 が本物の Copilot CLI 1.0.102 と SDK 1.0.25 で確かめた）

### X1-09 EVAL の課題の check の誤りを、1段目が見つけず、EVAL を頼んだときに初めて断られる

- 重さ：medium
- ファイルと場所：skills/make-plugin/assets/template/tests/stage1/check_structure.py の `check_eval`（program の基準は `check` に `type` の文字があることだけを見る）。skills/test-plugin/scripts/grade.mjs の `validateTask`・`validateCheck`（`check.type` は file_exists・contains・not_contains・regex の4種類、種類ごとの必須の項目、知らない項目は誤り、グロブの書き方、正規表現が読めるか、settings の値の型）。tasks.mjs の `loadTasks`（誤りがあれば `tasks_invalid` で EVAL を始めない）。
