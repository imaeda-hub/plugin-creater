### X2-01 画面の段階の抜き書きの例が、ユーザーの言葉でない字を足させ、外側の EVAL の採点で落ちる

- 重さ：medium
- ファイルと場所：skills/make-plugin/references/screen.md「## 記録」の「抜き書きには、決めたことが分かるユーザーの言葉を入れる（例：「〇〇を毎回選ぶ（選ぶ欄）」）。」
- 問題：例の「（選ぶ欄）」は、ユーザーが自由入力で話した言葉ではなく、決める問いの選択肢（またはメインのエージェントのまとめ）である。1つの抜き書きに、別の答え（自由入力の答えと、決める問いの答え）の言葉と、メインのエージェントの言葉を混ぜさせている。外側の EVAL の「全項目をヒアリングしたか」は、未着手から状態を変えたときの抜き書きが、それより前の1つの答えの中にあるかで見る（outer-grade.mjs の quoteFound は、空白・句読点・かぎ括弧だけを無視し、丸括弧「（）」は無視しない。「…」で区切った断片も、すべてが同じ1つの答えの中にあることを求める）。例のとおりに書くと、正しくヒアリングしても、この観点で不合格になる。
- 根拠：hearing.md 7.2「状態を変えるときは、ユーザーの言葉の抜き書きを添える」。testing.md 6.5「未着手から状態を変えたときに添えたユーザーの言葉の抜き書きが、それより前のユーザー役の答え…の中にある。答えの中にない抜き書きがあれば、不合格にする」。outer-grade.mjs の normalizeQuote・quoteFound。
- 直し方：screen.md の例を、1つの答えの言葉だけにする（例：「〇〇を毎回選ぶ」）。決めた部品は、抜き書きに足さず、問答の記録（決める問いの答え）に残ることと、生成前の確認で作業の定義の案に入ることを書く（confirm.md の冒頭の「会話にない答えは、振り返りの材料の問答の記録から拾う」と同じ扱い）。
- 確かさ：確か（食い違いは確か。モデルが例のとおりに書くかは、外側の EVAL の記録で見る）

### X2-02 EVAL の課題の「作業の画面に入れる設定の値」が、生成前の確認で示されず、記録にも残らない

- 重さ：medium
- ファイルと場所：skills/make-plugin/references/confirm.md「## 2」の「頼むときの言葉には、作業に要る情報をすべて書く。作業の画面に入れる設定の値も決める。」と「## 3」の渡すもの・示すもの。エクステンションの tool-defs.mjs の `confirm` の `evalTasks`（`prompt`・`inputs`・`criteria` だけ）。generate.md「## 2」の「よいと答えた内容が会話にないとき…state.json…から写す」と、渡すものの「作業の画面に入れる設定の値」。
- 問題：設定の値は、confirm.md の3で示す3つのどれにも入っておらず、ユーザーが確かめない。`plugin-creator_confirm` の引数にも欄がないので state.json に残らず、クリエイターの画面にも出ない。コンパクションの後は、generate.md が state.json から写すよう求めるが、そこに値がないので、作業エージェントへの頼みから抜けるか、メインのエージェントが推し量って補う（generate.md 2 の「補えるのは、生成前の確認でよいと答えた内容と、1で決めたことだけ」に反する）。
- 根拠：testing.md 10.1 の表「EVAL の課題（頼むときの言葉、入力のファイル、Web管理画面の設定、基準の番号と文の写し、基準ごとの採点のしかた）」。REQ-038「生成する前の確認で…EVAL に使う課題と合否の基準も示す。ユーザーが直したり足したりして、よいと答えたものを、生成プラグインのリポジトリに入れる」。hearing.md 7.1「生成前の確認の一覧…は、すべてこの記録から作る」。
- 直し方：次のどちらか。(a) `plugin-creator_confirm` の `evalTasks` に `settings`（`maxIterations` と `task` の値）を足し、state.json と画面に出し、confirm.md の3の2で示す（C1 と B3 で合わせる）。(b) 設定の値を頼みの文（`prompt`）に書く決まりにし、eval.json の `settings.task` は組み立てのスクリプトが作業の定義の初めの値から書く。どちらにするかは統括が決める。
- 確かさ：確か

### X2-03 作業エージェントが書く eval.json が、ユーザーが確かめた課題と同じかを、何も確かめない

- 重さ：medium
- ファイルと場所：skills/make-plugin/scripts/scaffold.py の `prepare_eval`（eval.json の `criteria` に id と text を入れるだけで、`prompt`・`inputs`・課題ごとの基準の組を見ない。state.json の `confirmation.evalTasks` を読む箇所がない）。worker.agent.md「試験の課題」。
- 問題：生成前の確認でよいと答えた課題（頼むときの言葉、入力のファイル、課題ごとの基準）は state.json の `confirmation.evalTasks` にあるが、生成プラグインの eval.json は、会話を見ていない費用の低いモデル（作業エージェント）が、メインのエージェントの頼みから書き写す。組み立てのスクリプトも1段目も、写しが確かめた課題と同じかを見ない（1段目が見るのは、基準の文が作業の定義と同じかと、どの基準もどれかの課題に入っているかまで）。頼みの文の言い換え、基準の付け落とし（別の課題には入っている基準）、入力のファイルの指定の誤りが、見つからずに残る。
- 根拠：REQ-038 の受け入れ基準「生成プラグインのリポジトリに、課題（入力のファイルを含む）と合否の基準が入っている」と要件の「よいと答えたものを、生成プラグインのリポジトリに入れる」。creator-structure.md 3.5（作業エージェントが書いたものは試験の中で確かめる）。BLUEPRINT 8章「EVAL の課題の基準の写しは、組み立てのスクリプトがヒアリングの記録から書く」。
- 直し方：組み立てのスクリプトが、`confirmation.evalTasks` と eval.json を突き合わせる（課題の数、課題ごとの `prompt` が同じ、`criteria` のナレッジの番号の組が同じ、`inputs` が eval_inputs と parts/files の置き場所に合う）。違えば断り、作業エージェントに直させる。あるいは、`prompt`・`inputs`・基準の組を、組み立てのスクリプトが state.json から書き、作業エージェントには `grading` と `check` だけを書かせる。課題と state.json の課題の並びを結ぶため、課題の番号（T-01）を confirm の引数に足すことも合わせて決める。
- 確かさ：確か

### X2-04 初めての EVAL では AI クレジットの見込みが出ず、試験を頼むときの要件を満たせない。スキルにもその場合の扱いがない

- 重さ：medium
- ファイルと場所：skills/test-plugin/scripts/estimate.mjs の `GUIDELINE`（`measured: false`、値がすべて null。前の記録がなければ `credits.estimate` が null）。skills/test-plugin/SKILL.md の手順6「回数と見込みを示し、始めてよいかを聞く」と選択肢「この回数と見込みで始める」。
- 問題：ユーザーが初めて EVAL を頼むと、見込みが出ない。スキルは見込みがない場合を書いておらず、選択肢も見込みがある前提である。返り値の `message`（「見込みは出せません。使った AI クレジットは、終わった後に示します。」）をそのまま示すことも書いていないので、モデルが見込みを推し量って示すおそれもある。
- 根拠：REQ-040「EVAL を始める前には、実行の回数と、使う AI クレジットの見込みを示し」、受け入れ基準「EVAL の前に、実行の回数と AI クレジットの見込みが示される」。testing.md 8.2「初めてのときは、開発の試験で測った目安（1回あたりのトークン数）に、使うモデルの価格（Copilot の価格表）をかけて出す」。tasks/C3.md の B3 への引き継ぎ3（null のときの伝え方）。
- 直し方：(1) 統括の波 E で目安を測って GUIDELINE を埋めるまで、REQ-040 が満たせないことを、最終報告の「残り」に挙げる。(2) test-plugin の手順6に、`credits.estimate` が null のときは返り値の `message` のとおりに伝え、見込みを推し量らないこと、選択肢を「この回数で始める」にすることを足す（C3 の引き継ぎ3のとおり）。
- 確かさ：確か

### X2-05 EVAL の実行が長くかかることへの備えが、スキルの手順にない

- 重さ：medium
- ファイルと場所：skills/test-plugin/SKILL.md の手順7「`node <スキルのフォルダ>/scripts/eval.mjs run …`。結果は…に書かれる。」
- 問題：C3 は「数十分かかりうる（1回の上限は既定30分。実行は課題×回数×2回）。シェルのツールの時間切れに注意し、バックグラウンドで動かして、結果のファイルを読むとよい」と引き継いだが、手順7は、そのまま動かすことだけを書く。Copilot CLI のシェルのツールが待ちきれずに返ると、モデルが途中で結果を読みに行く・もう一度動かす・止まったと判断する、のどれかになりうる。結果のファイルが実行ごとに書き直され、途中は `status: "running"` であることも書いていない。
- 根拠：tasks/C3.md「B3 への引き継ぎ」4「数十分かかりうる…シェルのツールの時間切れに注意し、バックグラウンドで動かして、結果のファイルを読むとよい。…途中は status: "running"」。BLUEPRINT 9章「スキルの担当（B3）は、この形で手順を書き、点検で突き合わせる」。
- 直し方：手順7に、長くかかることをユーザーに先に伝えることと、シェルのツールで裏で動かして待つこと、`result.json` の `status` が `running` の間は終わっていないこと、同じ EVAL を二重に始めないことを足す。シェルのツールの待ち方（裏で動かす指定の名前）は、R1・R2 にないので、公式のコマンドリファレンスで確かめてから書く。
- 確かさ：たぶん（Copilot CLI 1.0.102 のシェルのツールが、長いコマンドをどこまで待つか、裏で動かす指定があるかを、公式のコマンドリファレンスか本物の Copilot CLI で確かめれば決まる）
