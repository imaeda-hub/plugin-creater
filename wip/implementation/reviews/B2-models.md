### 前提（指摘の根拠に使った、組み合わせの事実）

- 統括への最初の指示文は、core/lifecycle.mjs の `buildInstruction` が組み立てる。中身は「実行の番号」「## 頼まれた作業」「## 繰り返しの上限」「## 作業ごとの設定の値（- 見出し（key）：値）」「## ユーザーと確かめた合否の基準（計画の評価基準に、番号と文を変えずに、すべて入れてください）（- C-01：文）」だけで、何をするか（定義の手順で進める、作業と検証に頼む）は書かれていない。作業エージェントの名前・作業フォルダ・入力のファイルの場所も入らない。
- 合否の基準は task.schema.json で1件以上（`minItems: 1`、番号は `C-` に数字）なので、「- （なし）」の行は出ない。統括が足す基準の番号の例（A-01）とは重ならない。
- 記録のツールの断りは、ツールを呼んだエージェントにエラーの文として返る（R2 3章の SDK `_executeToolAndRespond`）。断られた回数は、記録のツールごと（plan・verdict・review・issue・finish）に、実行の全体で数え（records.mjs の `run.refusals[shortName]`。検証エージェントが替わっても足し続ける）、受け付けられたら 0 に戻る。4回目の断りで、実行は「途中で終わった（記録のやり直しが上限を超えた）」になる（`LIMITS.RETRY_LIMIT` 3）。
- 統括が手番を終える（`agent.idle`・`agent.completed`・`agent.failed`）と、その時点で実行が終わる（events.mjs の `onAgentEnded` → `rootEnded`）。繰り返しの途中なら「途中で終わった」になる。
- 作業エージェントを数えるのは、計画の記録の後に起動した、種類が `<プラグイン>:worker…` のエージェントだけである（events.mjs の `addToTree`、analysis.mjs の `roleOfAgentType`）。合否の記録は、その試行に作業エージェントが1体もいないか、動いているものがあると断られる（records.mjs 96〜99行、「この試行の作業エージェントが、まだ終わっていません。作業が終わってから合否を記録してください。」）。

  - `task` の一覧は、設定されたすべてのエージェントを示す（「advertising every configured subagent」）。組み込みのエージェント（explore、task、research、rubber-duck、code-review など。R1 (3-2)）も呼べる見込み。

A completion notification will arrive as a new turn」。`write_agent` は「only supports background agents」、「write_agent can message siblings」「For status or a same-task follow-up, use IDs from task, read_agent, or notifications directly with read_agent/write_agent」。

#### M-01 検証の記録ができなかったときの頼み直しが、理由で分かれていない

- 重さ：medium
- ファイルと場所：orchestrator.agent.md「## 手順」3 の「合否を記録できなかったと返ったときは、その理由を書き添えて、もう一度頼む。」と、2 の「作業エージェントが何を返しても（作れなかったと返しても）、評価に進む。」
- 問題：検証エージェントが返す「記録できなかった」の理由には、検証を頼み直しても通らないものがある。頼み直すたびに検証エージェントが同じ断りを受け、断りの数が実行の全体で足されるので、4回目で実行が「途中で終わった（記録のやり直しが上限を超えた）」になる。
  - 「この試行の作業エージェントが、まだ終わっていません」：作業エージェントが1体も動いていない（`task` が「Unknown agent_type」などのエラーを返した、計画の前に呼んだ）。2 の「何を返しても評価に進む」は、`task` そのもののエラーでも評価に進むと読めるので、この道に入る。直すには作業エージェントに頼み直すしかない。
  - 「試行 N の合否は、すでに記録されています」：前の検証エージェントは記録できていた。頼み直さずに 4 に進むべき場面である。
  - 「繰り返しはもう終わっています。合否は記録できません。」：まとめに進むべき場面である。
  - 「作業を終えてください」「この実行は止められた」（検証エージェントが手順 3 のとおりに返す）：「記録のツールに断られたとき」の決まりでは手番を終えるが、手順 3 では頼み直すことになり、2つの決まりが食い違う。
  - GPT の族は、明示した細かい指示に従い（R1 (3-3)「junior coworker」）、Sonnet 5 の族も低い effort では文字どおりに従う（R1 (3-3)）。理由を見分けずに「もう一度頼む」を繰り返す余地が大きい。
- 根拠：records.mjs の `recordVerdict`（断りの文）と `applyRecord`（断りの数え方）。B2.md「決まり」：「記録のツールに断られたら、返された理由に沿って直す。」。R1 (1) 10「食い違う指示やあいまいな指示を残さない。GPT-6 の族は…食い違いがあると止まりやすい」。
- 直し方：手順 2 と 3 を次のようにする。
  - 2 に足す：「`task` がエラーを返して作業エージェントが動かなかったときは、`agent_type` の名前と `mode` を確かめて、もう一度頼む。作業エージェントが動かないと、その試行の合否を記録できないためである。」。「何を返しても評価に進む」は「作業エージェントが返事を返したら（作れなかったと返しても）、評価に進む」に直す。
  - 3 の「合否を記録できなかったと返ったとき」を、理由で分ける：「作業エージェントが、まだ終わっていません」なら 2 に戻って作業エージェントに頼み直してから検証を頼む。「すでに記録されています」なら頼み直さずに 4 に進む。「繰り返しはもう終わっています」ならまとめ（5〜8）に進む。「作業を終えてください」か「この実行は止められた」なら、ほかのツールを呼ばずに「返す形」で返事を書いて手番を終える。そのほか（評価基準の過不足、試行の番号の違いなど）は、理由を書き添えて、もう一度頼む。
- 確かさ：確か（断りの文と数え方は core の実装で確かめた。どの場面がどれだけ起きるかは、EVAL で確かめる）

#### M-02 まとめの記録が「まだ繰り返しの途中です」と断られたときの扱いがない

- 重さ：medium
- ファイルと場所：orchestrator.agent.md「## 記録のツールに断られたとき」（計画の断りと、作業を終える知らせの2つしか書いていない）と、まとめの 5「`{{plugin_name}}_review` を呼び、…」
- 問題：統括は検証エージェントの返事で合否を知るが、中心の処理は記録で決める。次のときに、統括は「まとめに進む」と決めても、`_review`・`_issue`・`_finish` が「まだ繰り返しの途中です。…評価基準をすべて満たすか、上限の回数まで試行した後に呼んでください。」と断る。
  - 上限の試行の合否が記録されていない（検証エージェントが記録したと返したのに記録がない、記録できなかったのに統括が先へ進んだ）。このとき次の計画も「繰り返しの上限（N 回）を超えます」と断られるので、統括から見ると、どちらのツールも進めない。
  - 返事の合否と記録の合否が違う（返事では全部合格、記録には不合格がある）。
  - 断りの文に従って「直す」には、統括が自分の思い込み（上限まで試行した、全部合格した）を疑う必要があり、定義はその手がかりを与えていない。GPT-6 の族はあいまいなときに止まりやすく（R1 (1) 10）、止まると「途中で終わった（繰り返しを終えないまま統括エージェントが終わった）」になる。同じ記録を繰り返すと、やり直しの上限で終わる。
- 根拠：records.mjs の `requireSummarizing`、`recordPlan`（上限を超える番号の断り）。設計書 4.8「まとめ中に移るのは、合否の記録ですべて合格か、上限の試行の合否が記録されたときである」。B2.md「決まり」：「記録のツールに断られたら、返された理由に沿って直す。」。
- 直し方：「## 記録のツールに断られたとき」に1項目を足す：「まとめの記録（`{{plugin_name}}_review`・`_issue`・`_finish`）が「まだ繰り返しの途中です」と断られたら、記録の上では、最後の試行の合否がないか、不合格がある。最後の検証エージェントの返事の「記録」の行が「記録できなかった」なら、その試行の確かめを検証エージェントにもう一度頼む。「記録した」なら、番号を1つ進めて 1 に戻る。その計画が上限を超えると断られたら、最後の試行の確かめを検証エージェントにもう一度頼む。」。あわせて、core の断りの文（records.mjs の `requireSummarizing`。A1 の部品なので、直す担当は統括が決める）に、どの試行の合否がないかを入れると、統括が迷わない。
- 確かさ：確か（断りの道は core の実装で確かめた）

#### M-07 頼みの文に、成果物の中身そのものを書いて作業エージェントに写させる余地がある

- 重さ：medium
- ファイルと場所：orchestrator.agent.md「## 作業エージェントと検証エージェント」の「要ることは、すべて `prompt` に書く。」と、「## してはいけないこと」の「成果物を自分で作らない、直さない。」

- 直し方：「Copilot CLI が、統括エージェント（…）が終わった（手番を終えた、失敗した、取り消された）と知らせてきたら、…」にする。
- 確かさ：たぶん（統括が取り消された・失敗したときに、メインのエージェントにどんな知らせが届くかは、実機で確かめる）

### core/tools.mjs の説明の文

指摘なし。7つの説明の文は、定義の手順と同じことを言っている（計画は作業エージェントに頼む前、合否は検証エージェントが1回にまとめて、まとめの記録は繰り返しの後、`finish` の後は作業を終える）。断りの文（records.mjs）とも食い違わない。記録のツールの名前は、メインのエージェントにも見えるが、説明の文が「統括エージェントが…呼ぶ」「検証エージェントが…呼ぶ」と呼ぶ者を書いているので、メインのエージェントが呼ぶ余地は小さい。

### 作った者の判断（tasks/B2.md）について

- モデルの書き方（統括・検証 `[claude-sonnet-5.5, gpt-6.1-sol]`、作業 `[gpt-6-luna, claude-haiku-5.5]`、`models`・`model-policy` なし）は、ユーザーの答え17と R1 (1) のカスタムエージェント 3 に合う。統括が `task` にモデルを渡さない決まりも、`task` の `model` の引数の説明（「Specify a value only when the user's current request … explicitly require that value」）と合う。
