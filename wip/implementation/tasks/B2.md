## 決めたこと

- フロントマターの値の差し込み口は、二重引用符の中に置く（C2 の plugin.json と同じ取り決め。中身の escape は C2）。tools の作業ごとの分は、行ごと置き換える差し込み口にした（素の字のまま置き換えても YAML が壊れず、ツールがないときは空の行が残るだけで済む。コメントの形にすると、置き換えを忘れたときに黙ってツールが抜けるので採らない）。
- 統括が作業エージェントの名前を知る手段として、決まった値 `{{worker_agents}}`（manifest.json の workers から機械的に作る一覧）を足した。統括への指示文（core の buildInstruction）に作業エージェントの名前が入らず、作業エージェントの名前を費用の低いモデルに書かせると取り違えの元になるため（creator-structure.md 3.4：AI が書く量をひな形でできるだけ減らす）。
- 作業エージェントの description は、エージェントごとに分けず、ひな形の決まった文にした（呼び名で分けると、呼び名を YAML に escape して入れる決まった値が増えるため。統括は名前で呼ぶので、description で選ばない）。

## 要確認

- （B1 へ。統括に伝えてほしい）画面の「担当している作業」（設計書 4.5：`task` を呼んだときの説明）に入る値。B1 の adapter.mjs は `agent.started.description` に `subagent.started` の `agentDescription` を入れている。SDK 1.0.25 の `session-events.d.ts` の説明では、`agentDescription` は「Description of what the sub-agent does」（定義の description と読める）で、`task` の呼び出しの説明は `agentDisplayName`（「For task-tool subagents this is the invocation's task description」）に入る。設計どおりにするなら `agentDisplayName` を使う見込み。B2 の統括の指示は、設計どおり「`task` の `description` に、何を頼むかの短い説明を書く（画面の担当に出る）」とした。今の対応づけのままだと、画面の担当には定義の description（ひな形の決まった文）が出る。
- （B1 へ）記録のツール、特に `<名前>_open` を `defer: "never"` で登録するか。既定の `"auto"` だと、ツールが多いときにツール検索の裏に回されうる（R2 3.3）。回されると、入口のスキルが「ツールがない」と取り違えて直し方を示して止まるおそれがある。入口のスキルには「ツールを探すツールがあれば、それで探しても見つからないとき」と書いて備えた。
