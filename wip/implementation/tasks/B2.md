## 決めたこと

- フロントマターの値の差し込み口は、二重引用符の中に置く（C2 の plugin.json と同じ取り決め。中身の escape は C2）。tools の作業ごとの分は、行ごと置き換える差し込み口にした（素の字のまま置き換えても YAML が壊れず、ツールがないときは空の行が残るだけで済む。コメントの形にすると、置き換えを忘れたときに黙ってツールが抜けるので採らない）。
- 統括が作業エージェントの名前を知る手段として、決まった値 `{{worker_agents}}`（manifest.json の workers から機械的に作る一覧）を足した。統括への指示文（core の buildInstruction）に作業エージェントの名前が入らず、作業エージェントの名前を費用の低いモデルに書かせると取り違えの元になるため（creator-structure.md 3.4：AI が書く量をひな形でできるだけ減らす）。
- 作業エージェントの description は、エージェントごとに分けず、ひな形の決まった文にした（呼び名で分けると、呼び名を YAML に escape して入れる決まった値が増えるため。統括は名前で呼ぶので、description で選ばない）。
- 統括・作業・検証の description には「チャットの頼みでは呼ばない（作業は Web管理画面から始める）」を入れた。description は `task` のエージェントの一覧でメインのエージェントにも見え、メインのエージェントが直接呼ぶのを防ぐため（`disable-model-invocation: true` は `task` での起動が断られるので使えない。R1 の 6）。
- 統括の手順は、core の決まり（records.mjs）に合わせた：計画の記録を作業エージェントより先にする（作業エージェントは、開始の時点の最後の試行に数えられる。events.mjs の addToTree）。作業エージェントが何を返しても評価に進む（どの試行にも合否が付き、繰り返しが機械的に進む）。合否の記録の後に計画が断られたらまとめに進む。「作業を終えてください」と返されたら、ほかのツールを呼ばずに終える（DISCONNECTED・STOPPED・やり直しの上限・まとめの記録の後の文に共通）。
- 統括の「進められないときは止める」は書かなかった。止めると「途中で終わった」になり振り返りもされないので、分からないことは判断して試行を進め、足りなかったものをまとめと最後の返事に書く形にした（R1 の 10 の「何が足りないかを書く」を、統括では最後まで進めたうえで書く形にした）。
- 統括が `task` に書く引数の名前（`agent_type`、`mode`、`description`、`prompt`）は、設計書の出典（runtime.node の `task` の `mode` と `agent_type`）と、R2 で展開済みの 1.0.102 のパッケージの組み込みの指示の文（「Use the `task` tool with `agent_type: "research"` … Always use `mode: "sync"`」、`task` の引数の説明「3-5 word UI intent.」「Task; include complete context.」）で確かめた。
- 「スキルを使わない」は、`skill` を外して効くかが要確認（設計書 4.7、11章 #16）なので、効かないときの備え（設計書 4.7 の代わりの案）を先に入れた。害がなく、1行で済むため。
- 応答の言語：入口のスキルは「日本語で応答する。ユーザーが別の言語で書いたら、その言語で応答する」（R1 の 11）。統括・作業・検証は、ユーザーと話さず、出す文は日本語の画面に出るので「日本語で書く」とした（作業の成果物の言語は、頼みと作業ごとの指示に従う）。

## 構造の検査の結果

1. 差し込み口が残ったひな形のまま（`python3 -I tests/stage1/check_structure.py <ひな形> --json`）：通らない項目と理由
   - manifest：plugin.json の name が `{{plugin_name}}` のまま（C2 の部品。組み立てで置き換わる）。
   - skills：SKILL.md の name が `{{entry_skill_name}}` のまま（組み立てで置き換わる）。
   - agents：3つの定義のフロントマターが YAML として読めない。tools の作業ごとの分の差し込み口（`{{orchestrator_extra_tools}}` などの行）が素の字のままのため。行ごと置き換える取り決めにしたので、置き換える前は読めない（「決めたこと」の1つ目）。
   - agent-tools：上の agents で定義が読めないので、「定義がない」と出る（連鎖）。
   - task・eval・knowledge・trace：作業ごとの部分（task.json、tests/knowledge.json、tests/eval/）と、エクステンションのフォルダの名前（`_plugin_`）が組み立ての前のため。B2 の部品とは関係がない。
2. 試しの組み立て（スクラッチの `b2/try_assemble.py`。B2 の取り決めどおりに置き換え、作業エージェント2体、統括の作業ごとのツールなし、作業エージェント2体目と検証に MCP のツールあり、説明の文に `"`・`:`・`\` を入れた）：13 項目すべて合格（references はファイルがないので飛ばし）。作業エージェント1体でも同じ。組み立て後のフロントマターは PyYAML で読め、core の `readAgentModels` も model のリストを読めた。
3. ナレッジの番号の例（`K-` と数字）は、B2 の部品にない。
4. core の試験 141 件、adapter の試験 85 件が通った（tools.mjs の説明の文を直した後）。

## 要確認

- （B1 へ。統括に伝えてほしい）画面の「担当している作業」（設計書 4.5：`task` を呼んだときの説明）に入る値。B1 の adapter.mjs は `agent.started.description` に `subagent.started` の `agentDescription` を入れている。SDK 1.0.25 の `session-events.d.ts` の説明では、`agentDescription` は「Description of what the sub-agent does」（定義の description と読める）で、`task` の呼び出しの説明は `agentDisplayName`（「For task-tool subagents this is the invocation's task description」）に入る。設計どおりにするなら `agentDisplayName` を使う見込み。B2 の統括の指示は、設計どおり「`task` の `description` に、何を頼むかの短い説明を書く（画面の担当に出る）」とした。今の対応づけのままだと、画面の担当には定義の description（ひな形の決まった文）が出る。
- （B1 へ）記録のツール、特に `<名前>_open` を `defer: "never"` で登録するか。既定の `"auto"` だと、ツールが多いときにツール検索の裏に回されうる（R2 3.3）。回されると、入口のスキルが「ツールがない」と取り違えて直し方を示して止まるおそれがある。入口のスキルには「ツールを探すツールがあれば、それで探しても見つからないとき」と書いて備えた。
