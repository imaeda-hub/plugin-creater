## 他の部品とのつなぎ方（B1・C1 向け）

```js
createCore({ port, pluginRoot, pluginName, dataRoot, sessionId, cwd,
             startUi: (core) => startApp({ core, cwd }),   // 画面を遅れて起こす。{ url, close? } を返す
             clock?, ghCommand? = 'gh', task? })             // task を渡さなければ core/ の1つ上の task.json を読む
```

- 記録のツール：`core.toolDefinitions`（`{ name, shortName, description, parameters, skipPermission }` の配列。名前は `<プラグイン>_<後ろの部分>`）。ハンドラーは、`open` なら `core.open({ requestText })`（返り値 `{ url, notices }`）、ほかは `core.handleTool(shortName, args, { agentId: invocation.agentId })`（返り値は文。断るときは Error を投げる）。
- フック：`core.preToolUse(input)` は `{ deny, reason }` を同期で返す（`input` は `{ agentId, parentAgentId, toolName }` が読めればよい）。`onPermissionRequest` は `core.onPermissionRequest(req)` を呼び、`{ kind: 'no-result' }` を返す。
- イベント：`core.onEvent(e)`（BLUEPRINT 3.1）。つなぎ口に求めること：
  - `agent.started.agentType` はプラグインの名前つき（`<プラグイン>:orchestrator`）で渡す。遅れて起動した統括の取り消しはこの形で見分ける。
  - `tool.started` に `arguments` を付ける（同じツールを同じ引数で繰り返した跡を課題にするため。なくても動くが、その課題は出ない）。
  - `wait.started.detail` の `sandboxBypass` は、`requestSandboxBypass` の値。`requestSandboxPermissive` が真なら `sandboxPermissive: true` を足す（core は、`sandboxPermissive` が真なら `sandboxBypass` を偽に直す。R2 #13）。
  - `wait.ended` に `agentId` は要らない（core が始めの待ちから補う）。
  - `agent.completed` に `response`（最後の返事）と `cancelled` を付ける。手番を終えた統括は `agent.idle`。
- 窓口 port：`listTasks()` は agent のタスクだけを `{ agentId, displayName, status, executionMode, agentType, parentAgentId }` で返す（`status` は running・idle・completed・failed・cancelled）。`listModels()` の要素は、文字列でも `{ id, name }` でも `{ modelId, displayName }` でも読める（R2：型で決まっていない）。`getCurrentModel()` は `{ model, isAuto }`。
- 画面（A2）から：`core.getState()`（同期）、`start(settings)`・`stop()`・`fileIssue(issueId)`（断るときは Error を投げる）、`getReply(agentId)`（全文か null）、`getFile(fileId)`（`{ path, name, image }` か null）。

## 決めたこと

設計書が決めていない細かいところを、設計書の目的に合う最も単純な形にした。

- **待ち時間と時間**（`core/constants.mjs` の `LIMITS`）：窓口の呼び出しは 10 秒、止める処理の打ち切りは押してから 8 秒（取り直しの間隔 250 ミリ秒）、gh は 60 秒、起票中のまま 5 分で「分からない」、生きている印は 5 秒ごと・30 秒で古い、記録のやり直しは 3 回まで（4 回目で上限超え）、イベントなしは 5 分、同じ呼び出しは 3 回続けたら課題、記録は 20 件。
- **列**：events・記録のツール・開始・止める処理は 1 本の列で 1 つずつ最後まで処理する。止める処理は列を使い続けるので、その間のイベントは列で待つ。そのため、止めた後に届いた子の開始は、フックの入力に親の番号があればその場で拒み、イベントは止める処理の後で拒む一覧に足す。止めるは列に入れず、押した時点で「停止中」にして木を拒む一覧に入れる。
- **記録のファイル**は同期の fs で書く（順番が確かで、試験で時計を進めるだけで済む）。ファイルに書けなくても実行は続ける。
- **開始**：`start()` は開始の処理が終わる（実行中になるか、準備中に戻る）まで返る。失敗したときは Error を投げ、同じ文を `state.startError = { message, unknownLaunch }` にも入れる。開始前の確かめは同期で行い、`すでに実行中です` は列に入れず断る。
- **準備中は `state.run === null`**（`run.status` の `preparing` は使わない）。画面を開く前の `getState()` でも `setup` の形は同じ。
- **統括の名前**は `統括 <実行の番号>`。実行の番号は `<UTC の日時>-<乱数>`（フォルダの名前と同じ）。統括を探すときは `displayName` に実行の番号が入っているかで見る。
- **開始の失敗**：失敗が分かっているとき（エラーを返した）は統括を探さない。時間切れのときだけ探して取り消す。どちらも上書きを外す。開始できなかった実行は `result.json` に `startFailed: true` で残し、準備中の「前の結果」には出さない。
- **遅れて起動した統括**は、(1) 待ちを打ち切った後に起動の結果が届いたとき、(2) どの実行の根でもない `<プラグイン>:orchestrator` の開始のイベントが届いたとき、のどちらでも取り消す（同じ番号は 1 回だけ）。
- **統括が終わる**のは、統括の `agent.idle`・`agent.completed`・`agent.failed` のどれかが最初に届いたとき。終わったら、`listTasks` で統括が `idle` で残っているだけなら、表示を変えずに取り消す。ほかのエージェントも残っていれば「停止中」を通して止める。
- **フェーズ**は「実行中」のときだけ出す（まとめ中・停止中・終了は null）。動いているとは、実行中か確認の待ちのこと。
- **計画の確かめ**：基準の文は、前後の空白と改行の形の違いだけなら同じとして認める。前の試行の合否が未記録のまま次の計画を出すことは断らない（データの流れの課題に入る）。合否は 1 試行に 1 回だけ。合否の基準の番号は、その試行の計画の基準と過不足なく合う（知らない番号と重なりは断る）。作業エージェントが 1 体も動いていない試行の合否も断る。
- **やり直しの数え方**：plan・verdict・review・issue・finish のそれぞれで、断られた回数を数え、その記録が受け付けられたら 0 に戻す。`show` の断りは数えない。「停止中・終了後・今の実行に当たらない」の断りは数えない。
- **表示の値の形**（A2 の render.js と同じ）：text は文字列、kv は `{見出し: 値}`（`[{label, value}]` も可）、table は `{columns, rows}`（各行の長さが columns と同じ）、progress は 0〜100 の数か `{value, max, label?}`、image と file は作業フォルダの中の場所（文字列）。image と file は状態の `displays` には `{ fileId, name, image }` で入る（`image` は拡張子が png・jpeg・gif・webp のとき真）。`getFile` は出すときにもう一度、本当の場所が作業フォルダの中かを確かめる。
- **課題の案**：機械的な案は `M1…`、統括が足した案は `O1…`（`source` は mechanical・orchestrator）。統括の案は、ユーザーが止めたときと「途中で終わった」ときは出さない。課題の文は平易な日本語で、題は短く、本文に実行の番号を入れる。記録のツール自身の断りは「ツールの失敗」の課題にしない（ふつうの動きのため。続けて断られた場合は「やり直しの上限」の課題になる）。
- **まとめ**：まとめの記録があり、終わった理由が「評価基準をすべて満たした」か「上限の回数に達した」のときだけ、統括のまとめを使う。それ以外は記録から機械的に作る（試行の数、最後の合否、終わった時点のフェーズ）。
- **起票の印**：`issues/<案の番号>.json`（試みの番号、状態、URL、理由）。前の印は `.old-<番号>` に名前を変えて退ける。本文の終わりの印は `<!-- <プラグイン>-issue:<実行の番号>/<案の番号> -->`。`gh` の終わりが 0 でも URL が読めなければ「分からない」にする。`gh` の呼び出しは `gh issue create --repo OWNER/REPO --title <題> --body-file -`（本文は標準入力）、探すのは `gh issue list --repo OWNER/REPO --state all --limit 100 --json title,url,body`。
- **起票できるかの確かめ**：画面を開いたときに裏で始め（待たない）、起票の承認で未確認なら待つ。確かめ直すのは、画面を開くたびだけ。`state.canFile = { ok, reason, code, steps, repo }`。`reason` は画面にそのまま出せる平易な日本語の文、`code` は no_repository・not_github・no_gh・not_logged_in。`previous.canFile` と `run.canFile` に同じ形で入る。
- **状態の全体に足したもの**（名前は変えていない）：`startError`、`setup.requestText`・`currentModel`・`taskDisplays`、`previous.runId`・`unstopped`・`canFile`、`endReason.message`、`canFile.code`・`repo`。
- **`endReason.detail` の記号**：cut_off・credit_limit・chat_interrupted・orchestrator_failed・orchestrator_ended・retry_limit・`extension_restarted`（新しい。「エクステンションが再起動した」。画面 A2 の ABORT_DETAILS に足してもらう）。
- **起動し直したとき**（ユーザーの決定。4.13・6.5 の「自分のセッションの終わっていない実行はすぐ途中で切れた」から変えた）：自分のセッションの終わっていない実行は、起動した時点で木のエージェントを拒む一覧に入れ、`listTasks` で動いている（running・idle など）ものを探して `cancelAgent` で取り消し、「途中で終わった（エクステンションが再起動した）」にする。動いているものが見つからないか、一覧が取れなければ「途中で切れた」。取り消しにも 10 秒の上限を付け、8 秒で打ち切り、止まらないものは止めきれなかったエージェントとして `result.json` に残す。この分かれ目は `core/recovery.mjs` の `classifyUnfinishedRun()` 1 か所にある。この後始末は列の中で行うので、その間の開始は列で待つ。
- **ほかのセッションの実行**は、生きている印が古いものだけを「途中で切れた」にし、そのエージェントには触れない。起動した時点で印が新しかった実行は、30 秒＋1 秒後にもう一度だけ確かめる。
- **拒む一覧の作り直し**は、自分のセッションの実行の `log.jsonl` の木の番号から（終わった実行と、起動し直しで終わらせる実行）。ほかのセッションの実行は使わない。
- **`createCore` の引数**：設計図の `ui` は `startUi` として受け取る（`ui` が関数なら同じに扱う）。`ghCommand`（既定 `gh`。試験で偽物の gh に替える）、`task`（試験用）を足した。`core` に足した公開の部品：`toolDefinitions`、`whenIdle()`、`shutdown()`。
- **clock** に `clearTimeout`・`clearInterval` を足した（`now・setTimeout・setInterval` に加えて）。
- **記録のツールの説明の文**（`tools.mjs`）は仮の文（`【仮】`）。引数の JSON Schema は作った。`show` の `value` は型を決めない（種類によって違うため。モデルの提供元によっては型なしを嫌うかもしれない）。

## 要確認

- **上位の文書で直すこと（追加の直し）**：設計書 4.3 の「統括への指示文の中身」に、始めの 1 文（定義の手順で進め、作業・検証に `task` で頼む）を足す。設計書 6.2 の表と 4.2 の「実行中に画面を開くツールがまた呼ばれたら」に、「頼みの文は受け付けず、始められない旨の知らせを返す」を足す。ひな形の docs/design/design.md の同じ箇所（117 行、269 行）も同じ。

- **（解決済み）** 起動し直したときの自分のセッションの実行の扱いは、ユーザーが決めた。設計書 4.13・6.5・10章（「自分のセッションの終わっていない実行は、すぐに『途中で切れた』になる」）が今の実装と食い違うので、設計書の直しが要る。実装は上の「起動し直したとき」のとおり。
- **試験の入口**：Node 22 では `node --test <ディレクトリ>` が動かない（ディレクトリをモジュールとして読もうとして失敗する）。入口（A3 の run.py、C3）は `node --test "<ディレクトリ>/*.test.mjs"` の形にする。
- **`tasks.list` の shell のタスク**：窓口の `listTasks` が agent だけを返す取り決めなので、「止めても止まらなかったシェルの処理」（設計書 4.10 の表）は課題にできない。必要なら窓口に shell を足す。
- **`tool.started` の `arguments`** が BLUEPRINT 3.1 の中立のイベントにない（R2 では `tool.execution_start` にある）。BLUEPRINT に足すか、「同じ呼び出しの繰り返し」の課題をやめるか決める。
- **`agent.started.agentType` の形**：プラグインの名前つきで届く前提（上の「つなぎ方」）。届かない場合、遅れた統括の取り消しが効かない。実機で確かめる（設計書 11章 #4 の「名前は `<プラグイン>:<エージェント>`」は起動の指定の話）。

- **`review`**：統括が呼ぶ前提で、まとめ中だけ受け付ける（設計書 4.8 の「実行中の `_review` は断る」に合わせた）。返り値の文は仮。
- **自然言語の部品**：`tools.mjs` の説明の文は仮。B2 が仕上げる。
- **設計書の突き合わせ**：6.1 の「列の中で待つ呼び出しに上限（10 秒）」と、4.4 の「止める処理の呼び出しは押してから 8 秒で打ち切る」は実装したが、開始の処理が全体で最大 30 秒（現在のモデル、上書き、起動が各 10 秒）かかりうる。設計書は 1 回ごとの上限しか決めていない。
