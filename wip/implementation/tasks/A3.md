## 決めたこと

- 検査は1つのファイル check_structure.py にまとめた。`run_checks(root, kind)` を関数として公開し、クリエイターの1段目が `importlib` で読み込んで使う。kind は generated（生成プラグイン）か plugin（公式仕様の検査だけ）。
- 試験（検査の単位）の名前に、確かめる要件の番号を入れる（CATALOG）。manifest・mcp・skills・agents・layout・symlinks は REQ-004、task・eval は REQ-011、agent-tools は REQ-010、trace は REQ-003、knowledge は REQ-039（クリエイターの要件。生成プラグインの要件の番号とは別の表だが、試験の名前としては REQ-039 を付けた）。
- 追跡の表の「自動のテスト」の行は、その番号を名前に持つテストを、(a) tests/ のテストファイル（node:test の `test/it/describe` の第1引数、Python の `test` で始まる関数の名前と docstring。tests/stage1/ は数えない）と、(b) 1段目の試験の名前（REQ-003、004、010、011、039）から探す。1段目が確かめる要件（設計書 10章）を、「自動のテスト」の行に書けるようにするため。
- 要件の番号の探し方：`REQ-数字` の大文字小文字を問わない形（`REQ-009`、`REQ_009`、`req_009`）。前後が英数字のものは除く。
- 追跡の表は、見出しの行が「要件…｜設計書…｜ファイル…｜確かめ方…｜テスト…」で始まる列を持つ最初の表。ファイルの欄は、バッククォートで囲んだパス（なければ読点・コンマ・改行で区切った語）。`*` はグロブ。`—`・`-`・`なし` は空。確かめ方は「自動のテスト」「EVAL」「人が確かめる」のどれかを含む。1つの要件に複数の行があってもよく、各行を調べる。要件は `docs/specs/requirements.md` の見出し `### REQ-nnn 題`。
- ナレッジの「それ以外」の番号は、プラグインの根のうち tests/・.git・node_modules・__pycache__・作業の定義を除く全ファイルから、`K-数字`（前後が英数字・`-`・`_` でない、数字が続かない）を探す。ひな形の文書や土台に `K-03` のような例が書かれていると、それを見つけて合格してしまう。task.schema.json では番号の例を書かないようにした。
- 作業の定義：criteria と workers は1件以上。`settings` の `options` の要素は文字（`{value,label}` の形は採らない）。`default` の型は種類で決まる。閉じた形（知らない項目は不合格）。番号の重なり、workers の agent のファイル、select の初めの値が選択肢にあることは Python で確かめる。
- EVAL の課題：各課題の criteria の id と text が作業の定義と同じ。作業の定義のすべての基準が、どれかの課題に写っていること（課題ごとにすべてを写す必要はない）。課題が1つもなければ不合格（REQ-038）。形（id、prompt、criteria の grading が program か model、program なら check.type）は設計図 4.3 だけに従って最小限を見る。
- 検証エージェントの tools の書き込み・コマンドの名前：書き込みは edit・write・multiedit・notebookedit・create、コマンドは execute・shell・bash・powershell（大文字小文字は区別しない）。tools がない（すべてのツールが使える）ものも不合格。
- 記録のツール名：`<頭>_(open|plan|verdict|show|review|issue|finish)` の形のものの頭が plugin.json の name と同じ。対象は tools の各要素と、本文のバッククォートで囲んだ語。
- MCP：`command` は1語・素の名前か `./` の相対パス（あれば存在と閉じ込め）・`${…}` は展開されない。`url` は絶対の http/https、ユーザー情報と断片なし、http はループバックだけ。`cwd` と `args` の `${PLUGIN_ROOT}/` 以下は根の中。`headers` の名前は大文字小文字を除いて重ならない。各サーバーは type に合う定義だけで検査する（oneOf のままだと関係ない選択肢の誤りが出るため）。
- フックの検査（hooks.json）は入れない（生成プラグインもクリエイターもフックはエクステンションの中。R4 注 A-4）。
- 検査の単位（CATALOG）に references を足した。tool-names は REQ-010、agents は REQ-004 と REQ-010（tools の skill・* ・知らない名前も見るため）。
- `tests/stage1/selftest/` の試験は、見本 1 つ（samples/good）を試験の中で一時フォルダに写して壊す方式。壊した見本をファイルとして置かない。ひな形の task.schema.json は見本に持たず、試験が写す（二重に持つとずれるため）。

## R1 から検査に入れたもの（機械的に確かめられるもの）

- SKILL.md：フロントマターは Agent Skills の6項目（name、description、license、compatibility、metadata、allowed-tools）だけ。これ以外（user-invocable、disable-model-invocation、argument-hint など）は不合格。`allowed-tools` は項目としては認めるが注意を出す（スキルが呼ばれるとツールが確認なしで許可されるため。書く前にユーザーに確かめる決まり）。description の < と >、「I can」「You can」で始まる書き方は不合格。本文が500行を超えるのは注意（クリエイターの make-plugin だけ、行数とトークン数を不合格にする）。
- references（すべてのスキル）：各ファイルが 20KB 未満（20,000 バイト未満と読んだ）、SKILL.md の本文がファイル名を名指ししている、入れ子のフォルダは注意。
- カスタムエージェント：ID（ファイル名）は小文字の英数字とハイフン。`name` は書かないか ID と同じ。`disable-model-invocation: true` は不合格。`tools` は、`*` と `skill` を不合格にし、各名前が「別名（execute、read、edit、search、agent、web、todo と Claude Code 互換の名前）」「このプラグインのエクステンションのツール（<名前>_…）」「mcp.json か `mcp-servers` にあるサーバーの `サーバー名/ツール名`」のどれかであること（知らない名前は黙って無視されるため不合格）。`tools` がないものは注意（統括・作業・検証は不合格）。`models`・`modelPolicy`・`model-policy`・`reasoningEffort`・`reasoning-effort`・`include-custom-instructions`・`infer`・`user-invocable` は認めるが「書かない決まり」の注意を出す。
- 入れなかったもの：description の書き方（成果と使う場面）、本文の組み立ての順、強い言葉の使い方、言語の指定、作業エージェントに合否の判定を書かせないこと、「ユーザーに質問しない」の一文など、文の意味を読む必要があるもの。コマンド名の書き分け（`/plugin-creator:make-plugin` と `make-plugin`）も、ドキュメントと実測が食い違っていて決まっていないので入れなかった。

## 試験の入口（tests/run.py）

- 標準ライブラリだけで動く（PyYAML・jsonschema がなくても、足りないことを示して止まれるように）。1段目は `python -I check_structure.py <根> --json` を別プロセスで動かして JSON を読む。2段目の node は `node --test --test-reporter=tap <見つけた *.test.mjs>`（Node 20 と 22 で同じに動くよう、フォルダでなくファイルを渡す。作業フォルダは根）を TAP として読み、unittest は別プロセスで `tests/stage2/task/test_*.py` を動かして JSON で受ける。1段階の上限は 900 秒。
- 道具：Python 3.9 以上、PyYAML、jsonschema 4.0 以上は必ず。Node.js（20.19 以上、22.12 以上、23 以上）は *.test.mjs があるとき。Playwright とブラウザー（Chrome か Edge。なければ Playwright の Chromium）は playwright を読み込む試験があるとき（Playwright は、その試験のフォルダから ESM で読めること＝全体に入れたものは使えない）。`--need tiktoken` などで足せる。
- 結果：`<根>/tests/results/latest.json`（`--results` で変えられる）。段階ごとに status（passed・failed・none＝試験なし）、counts、failures（試験の名前と理由）、1段目は checks の一覧。全体の status は passed・failed・stopped。終了コードは 0・1・2。`--json` で同じ JSON を標準出力にも出す。1段目が落ちても2段目は動かす。
- クリエイター自身の入口にも使い回せるよう `--root`・`--stage1-script`・`--stage2-dir`・`--need` がある（クリエイターの2段目の置き場所が決まれば、`run.py --root . --stage1-script tests/creator/check_creator.py --stage2-dir tests/creator --need tiktoken` で1つのコマンドになる見込み。試していない）。
