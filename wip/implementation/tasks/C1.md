## 決めたこと

設計書が決めていない細かいところは、目的に合う最も単純なやり方にした。

記録
- 記録（state.json）を作るのは、状態を変えるツール（progress、record、confirm）の最初の成功した呼び出し。open、state、results、doc_text、issue は作らない（試験を頼まれただけのセッションで、ヒアリングの記録を作らないため）。そのため、記録ができる前の発言と問答は、記録しない（hearing.md 7.4「ヒアリングの最中とは、このセッションの記録があり…」のとおり）。最初の頼みの文は、qa.jsonl に残らない
- 状態を変えるツールは、順に1つずつ動かす（並べて呼ばれても、記録が失われず、番号が重ならない）。1つの呼び出しの中で誤りが1つでもあれば、何も記録しない
- 記録のファイルが壊れていれば、上書きせず、直すよう知らせて断る（ヒアリングの最中でもないものとして扱う）
- 段階が「生成」に進んだ後は、progress・record・confirm のどれも断る（「ヒアリングは終わっています（段階は「生成」）。やり直すときは、/clear してから頼み直してください。」。hearing.md 3.1 始まりの決まりと同じ）。設計書にあるのは「問答を記録しない・差し込みを返さない」だけ。ナレッジの一覧が、組み立てに渡した後で変わらないようにするため
- 項目の状態：未着手 → 聞いた・決まりなし・保留。この3つは行き来できる。未着手には戻せない。状態を変えるたびに、ユーザーの言葉の抜き書き（quote）が要る。だれが知っているか（holder）は、保留のときだけ残る
- 項目「候補の確かめ」は、確かめていない候補（状態「候補」のナレッジ）があれば未着手、なければ聞いた。ツールでは変えられない
- 項目「できていたことの確認」（作り直しのときだけ）：段階「できていたことの確認」に入るか、その項目を記録すると、作り直し（rebuild=true）として、聞く項目に入る。作り直しなら、confirm に rebuild（引き継ぐことと変わること）が要る
- ナレッジ：番号は K-01 から、記録の順に付ける（数は2桁以上。使い回さない。外したものも消さない）。新しいナレッジには、種類・項目・文・出どころ・状態・ユーザーの言葉が要る。ユーザーの言葉は、出どころ「AI の判断」でも要る（「お任せします」などの、任せた言葉）。更新は、番号を渡す。そのとき渡さなかった欄は変わらず、ユーザーの言葉は新しいものに替わる（前の抜き書きは残らない）。項目を直したら、日本語の項目の名前（itemName）もそろえる。状態は、候補 → 決まった・外した。決まった・外したは行き来できる。候補には戻せない。記録した時刻（recordedAt）と、記録のときに項目が未着手でなかったか（itemTouchedAtRecord）は、新しいナレッジを足したときに付け、更新では変えない
- 資産と、標準機能と公開のプラグインの選んだ結果：名前で上書きする。資産の状態は 候補・流用する・流用しない。選んだ結果は 使う・使わない（種類は 標準機能・公開のプラグイン）。設計書に決まりがないので、最小の欄にした
- 質問の改善案の対象（11章の1つ目の観点）：状態が「決まった」のナレッジのうち、(1) 出どころが「ユーザーが自分から話した」で itemTouchedAtRecord が真、(2) 出どころが「生成前の確認で足した」。候補・外したものは含めない（REQ-049 の受け入れ基準「生成プラグインに入れることになったナレッジのうち」）

生成前の確認（confirm）
- 引数：knowledgeIds、behavior、taskPath、evalTasks（prompt、inputs〔path、provisional〕、criteria〔ナレッジの番号〕）、rebuild（keep、change）。BLUEPRINT 7章の「要点」を、この形にした
- 確かめる順：段階が「生成」でないこと → 未着手の項目がないこと（あれば、残りの名前を全部返して断る）→ 引数 → taskPath が `.plugin-creator-work/draft/task.json` で終わること → 作り直しなら rebuild があること → ナレッジの番号（見つかる、外していない、決まっている）→ EVAL の課題の基準が「合否の決め方」のナレッジで、示す一覧にあること → 決まったナレッジがすべて示す一覧にあること → 作業の定義の案（読める、「合否の決め方」のナレッジから基準を差し込んで、ひな形の core/task.schema.json に合う）→ 見本を作る。どれかが失敗すれば、確認を受け付けたことにしない
- knowledgeIds は、重なりを除き、番号の小さい順にそろえて残す。見本の合否の基準（C-01 から）と、組み立てのスクリプトが付ける番号を、同じ並びにするため
- 合否の基準の番号は C-01 から（2桁以上）。文はナレッジの文のまま。「合否の決め方」のナレッジが1つもないと断る（task.schema.json が criteria に1件以上を求めるため）
- 決まったナレッジは、すべて knowledgeIds に入れさせる（入っていないものがあれば断る）。画面の「決まったこと」の一覧と、確認の一覧を、同じにするため（REQ-043）
- 確認を受け付けるとき、示したナレッジの中身の写し（confirmation.knowledge：番号、種類、項目、文、例、例外）を残す。段階を「生成」に進めるとき、今の「決まった」ナレッジが、この写しと違えば（足した・直した・決まったものでなくなった）、断る。示し直す（confirm を呼び直す）と進める。ユーザーがよいと答えたナレッジと、生成に使うナレッジを、食い違わせないため（REQ-020「ユーザーがよいと答えるまで、生成されない」「直した内容が、生成プラグインに反映される」）。ユーザーの言葉と出どころの直しは、ユーザーが確かめる中身ではないので、示し直さなくてよい。設計書にあるのは「確認の前は生成に進めない」だけ。この確かめは、それを、確認の後の変更にも広げたもの
- 受け付けたら、画面に、ナレッジの一覧・振る舞いの案・見本の URL・EVAL の課題と基準（入力のファイルの一覧、仮の印）・作り直しの内容が出る。ナレッジの一覧は「決まったこと」の一覧と同じ形・同じ中身（knowledgeRow を共有）
- 再開（--continue）のあと、生成前の確認が残っていれば、状態取得ツールが見本のサーバーも作り直す（生成に進んだ後は作り直さない）

Web管理画面の見本
- ひな形の生成プラグインの画面（ui/static の index.html、app.js、render.js、style.css）を、そのまま別のサーバーで出す。サーバーはクリエイターの画面とは別（ポートは OS 任せ。合言葉は別）。状態の全体（BLUEPRINT 3.5）は、作業の定義の案から作る
- 動き：最初は「開始前の設定」→「開始する」で、仮のデータの入った「実行中」→「止める」で、仮のデータの入った「終わった後」。必須の設定が空だと「開始する」を押せないので、見本には仮の初めの値を入れる。表示の種類ごとの仮の値（文章、要点、表、進み具合、画像、ファイル）は sample.mjs の sampleValue。画像は SVG、ファイルは文字のファイル。注意の文（見本であること）を notices に入れる
- 設計書は「同じ描画の部品に仮のデータを入れて出す」としか書いていない。開始・止めるで見本の状態を切り替えるのは、実行中と終わった後の両方を、ひな形の画面で見せるための最小の方法
- 見本の画面は、ひな形の app.js が読む窓口（/api/state、/api/files/:id、/api/agents/:id/reply、/api/start、/api/stop、/api/issues/:id/file）だけを持つ。startServer の形（BLUEPRINT 3.4）で使う

クリエイターの画面
- 見るだけ：入力の欄、ボタン、書き込みの窓口を持たない（試験で確かめる）。GET /api/state と GET /api/examples/:name だけ
- 状態の全体は、1秒ごとに取り直し、版（状態の JSON の sha1 の先頭12文字）が変わったときだけ描き直す
- ポートは OS 任せ（0）。127.0.0.1 だけ、合言葉、Host の確かめ、CSP は、ひな形の server.mjs が全部の応答に付ける
- 画面のサーバーを起動できなくても、ほかのツールは動く（ひな形の部品は、最初に必要になったときに動的に読み込む）。起動できない理由は、open がエラーで、state が文で返す
- 会話例：リポジトリの examples/ の Markdown の一覧を出し、一覧にあるファイルだけを text/plain で開く（HTML として動かさない）。examples/ がなければ「会話例はまだありません」
- 試験の結果：results で知らされたファイル（.json、5MB まで。作業フォルダの外でもよい）を、1秒ごとに読む（更新時刻と大きさが同じなら読み直さない）。知らされたファイルの一覧は、記録のフォルダの results.json に残す（最新の20件。起動し直しても出る）。形で読み分ける：stages ありは1・2段目（tests/run.py の latest.json）、runs か scores ありは EVAL（形は決まっていないので、あるものだけを出す）、ほかは整えた JSON

文書をテキストにするツール
- docx：本文、ヘッダー、フッター、脚注、文末脚注、コメント（見出し付き）。段落の終わりで改行、表のセルはタブ、行は改行（セルの中の段落は空白でつなぐ）、タブと改行の印、テキストボックスの重なり（mc:Fallback）は除く、削除された文字（w:delText）は出さない
- xlsx：シートごとに「## シート：名前」（非表示は「（非表示）」）、行は改行、セルはタブ。共有文字列（ふりがなは除く）、インライン文字列、数、真偽、式のあるセルは「値（式：=…）」。日付は数値のまま（先頭の注に書く）
- pptx：presentation.xml の順番どおりに「## スライド N」。表と、ノート（「（ノート）」）。マスターの文字は出さない
- 返す文字は先頭の16,000文字まで（Copilot CLI の大きな出力の上限 51,200 バイトに、日本語3バイトでも収まる）。超えたら切って、全体の文字数を示す。途中で読むのをやめたとき（64,000文字を超えたとき）は「以上」と示す。続きを読む引数は足していない（設計書の引数は path だけ）
- 対応しない：PDF、古い形式（doc・xls・ppt）、パスワード付き、zip64、暗号化された zip。理由を平易な日本語で返す。zip の中の1ファイルは64MB、ファイルは100MBまで（zip 爆弾を避ける）
- 作業フォルダの外の文書も読める（ユーザーの答え15：確認を省く）。相対パスは作業フォルダから

起票
- `gh issue create --repo imaeda-hub/plugin-creator --title=<題> --body-file -`。題は `--title=` の形で渡す（- で始まる題が旗と取り違えられないため）。本文は標準入力。シェルを通さない。60秒で止める（止めるとき、出力の管も閉じて、すぐ返す）。題は1行で256文字まで
- gh がない（ENOENT）、ログインしていない（gh の終了コード4、または 401・「gh auth login」の文）ときは、入れ方とログインのしかたを返す。環境変数は求めない。確認を省かない
- 起票の承認は、チャットで取る（creator-structure.md 4.5）。このツールは、呼ばれたら起票する

フックと差し込み
- フックの関数は、例外を投げず、失敗は標準エラーに知らせる。標準出力は使わない（JSON-RPC の通り道）
- 問答の記録（qa.jsonl の1行）：`{ at, type: "ask_user", question: <toolArgs>, answer: <結果の文>, outcome: "answered"|"cancelled"|"unavailable" }`、`{ at, type: "user_prompt", text }`。outcome は結果の文の頭で見分ける（hearing.md 2.1）
- コンパクションの差し込み：イベントの agentId があるもの（サブエージェント）と、success が false のものは数えない。「差し込み待ち」は、次のメインのエージェント（フック入力に agentId がない）の onPreToolUse で、1回だけ消える。差し込みを返すときに、ヒアリングの最中でなければ返さない
- ツールには defer: "never" を付ける（状態取得ツールの説明が、ツール検索の裏に回ってモデルに見えなくなるのを避ける。R2 3.3、hearing.md 14章 H4）

状態取得ツール
- 返り値は平易な日本語の複数行（段階、項目の状態、まだ聞いていない項目、確かめていない候補、保留、AI の判断、ナレッジの数、資産、生成前の確認、画面の URL、セッションの番号、state.json のパス、make-plugin の読み直し）。URL が前の記録と違うときは、チャットで示すよう知らせる
- 「確かめていない候補」の行は `K-03（項目：進め方、出どころ：ファイルから読んで確かめた）：文` の形（B3 の求め）。段階「決まりの確かめ」は、出どころがファイルか既存のプラグインの候補だけを確かめるので、コンパクションの後に見分けられる
- include「最後の問答」は最後の5件。「振り返りの材料」は、対象のナレッジの番号と理由、問答の記録のすべて（1行が1件の JSON）。大きいときは40,000文字までにして、古い側を省く（記録のファイルの場所を示す）

値の表（記号 → 日本語の名前）

組み立てのスクリプトが守ること（hearing.md 6.3 の関門）
1. 組み立てを始める前に、`stage == "generate"`、`approvedAt` が空でない、`confirmation` が null でない、を確かめる。1つでも違えば、断る（承認の前に組み立てない）
2. ナレッジの一覧（tests/knowledge.json）は、`status == "decided"` のものを、記録の順（番号の小さい順）に、`{ "id", "kind", "item": <itemName>, "text" }` で書く。エクステンションは、段階を「生成」に進めるとき、「決まった」ナレッジが、ユーザーが生成前の確認で見た一覧（`confirmation.knowledgeIds`、番号の小さい順、重なりなし。中身の写しは `confirmation.knowledge`）と同じであることを確かめて、違えば断る。そのため、生成に進んだ記録では、「決まった」ナレッジのすべて ＝ ユーザーが見た一覧。`confirmation.knowledgeIds` の順に書いても、同じになる
3. 合否の基準（task.json の criteria）：2 の一覧のうち、kind が criterion のものを、同じ順に、`{ "id": "C-01"…, "text": <ナレッジの text そのまま>, "knowledge": <番号> }`。番号は C-01 から、2桁以上（`C-` に数字を続ける）。見本の画面（Web管理画面の見本）は、同じ規則で基準を作っている（sample.mjs の injectCriteria）。ナレッジの文を言い換えない（testing.md 7章）
4. EVAL の課題：`confirmation.evalTasks[]` が、ユーザーが生成前の確認で見た課題。`prompt` は頼むときの言葉、`inputs[].path` は入力のファイル（生成プラグインのリポジトリの tests/eval/<課題>/ に入るもの）、`provisional: true` は、仮のファイル（「仮」の印を付ける。hearing.md 6.5）、`criteria` は、その課題の基準にするナレッジの番号（task.json の C-xx に、knowledge の番号で対応づけられる）。eval.json は作業エージェントが書き、基準の id と text は、スクリプトが task.json の写しで埋める（BLUEPRINT 4.3）
5. `confirmation.taskPath` は、ユーザーがよいと答えた作業の定義の案の場所（絶対パス）。`parts/task.json` は、これと同じもの（criteria なし）
6. `confirmation.rebuild`（作り直しのときだけ。`{ "keep": […], "change": […] }`）は、README や説明に使える
7. 資産（`assets` の reuse のもの）と、標準機能と公開のプラグインの選んだ結果（`ossChoices`）は、作業エージェントへの入力に使える。組み立てのスクリプトが使うかは C2 が決める
8. `url` は使わない（画面の URL。合言葉が入っている）。組み立ての結果の JSON に写さない
