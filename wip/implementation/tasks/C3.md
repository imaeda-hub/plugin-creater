## 決めたこと

- 版：@github/copilot-sdk 1.0.25、playwright 1.56.1（どちらも版を固定。lock のファイルは置かない）。Playwright を 1.56.1 にしたのは、開発の環境のブラウザーがその版用であることと、1・2段目（tests/node_modules）と EVAL（tools）で同じ版にすると Playwright の Chromium を1つだけ入れれば済むため。
- EVAL の道具の入れ方は `npm install --ignore-scripts --no-audit --no-fund`。koffi（SDK の依存）には install スクリプトがあるが、`--ignore-scripts` でも SDK は読み込めることをスクラッチで確かめた（8パッケージ、約190MB）。
- 1・2段目の Playwright は `npm install --prefix <生成プラグイン>/tests --no-save --no-package-lock --ignore-scripts playwright@<版>`。`tests/node_modules` だけができ、`package.json` などは増えない（スクラッチで確かめた）。生成プラグインの .gitignore に `tests/.venv/` と `tests/node_modules/` が要る（C2 へ）。
- EVAL の結果の形は、C1 の results.mjs が読む形（`runs[]` に `task`・`variant`〔with か without〕・`criteria[{id,text,pass}]`・`score`、`scores{with,without,difference}`、`credits`〔合計の数〕）に合わせる。
- 実行の status：completed（終わりまで動いた）、incomplete（URL が出ない・画面を操作できない・時間切れ・実行が途中で終わったなど。できていた分を採点する）、error（試験の仕組みの側の失敗。採点せず点数に入れない）、stopped（試験全体が止まったときに動いていた実行）、skipped（始めなかった）。results.mjs の先頭に書いた。
- 点数は、実行ごとに「合格の基準の数 ÷ 基準の数」。あり・なしの点数は、採点した実行の平均。差はありからなしを引く。
- 作業フォルダは OS の一時フォルダの下（生成プラグインのフォルダの外）に作る。生成プラグインのリポジトリの中に作ると、Copilot CLI が親のフォルダの指示ファイル（AGENTS.md など）を拾い、なしの実行にも生成プラグインのものが混ざるため。
- 許可の求めへの答え（permissions.mjs の先頭に書いた）：管理設定で人の承認が要る求めは止める。extension-permission-access は許可。作業フォルダの外への書き込み（kind が write）は拒む。ほかは1回だけ許可。ただし、ブリーフにない拒みを2つ足した：extension-management（エクステンションの読み込み直しなど。EVAL の途中で入れ替わると実行が途中で切れる）と extension-env-access（環境変数。生成プラグインは求めない設計）。シェルのコマンドがどこに書くかは見分けきれないので、許可する（testing.md 10.4 の限界のとおり）。
- 質問（ask_user）への返事は、いつも testing.md 10.4 の決まった文。選択肢だけを認める質問（allowFreeform が偽）には、最初の選択肢で答える（止まらないように）。
- 画面の操作：チャットに出た URL（assistant.message だけ。ツールの返り値は数えない。画面の URL が示されること自体が REQ-005 の確かめ）を、Playwright で開き、設定の欄 `#setting-<key>` に入れて `#start` を押し、`#s-end #end-reason` が出るまで `/api/state` を読んで見る（状態の変わり目だけ記録）。検証エージェントの合否は画面から読めるが、採点には使わない。

## 本物の SDK とランタイムで確かめたこと（使い捨ての環境。偽のモデルの窓口〔OpenAI 互換〕につないだ。リポジトリには入れていない）

SDK 1.0.25 と同梱のランタイム 1.0.102 を、`provider`（独自プロバイダー）で偽のモデルにつなぎ、`--plugin-dir` で小さなプラグイン（エクステンションにツール・フック・許可の受け口を登録）を読み込ませた。

- `requestExtensions: true` だけでは、`session.create` が失敗する。「extensionSdkPath is required when standalone extensions are requested」、続いて「No extension launch provider is registered for standalone extensions」。
- 次の2つを渡すと、エクステンションが起動する（status が running、pid つき）。
  1. セッションの `extensionSdkPath`：SDK パッケージの `dist/` のフォルダ（index.js と extension.js がある）。ランタイムは、これを子プロセスの環境変数 COPILOT_SDK_PATH にして渡す。
  2. `CopilotClient` の `extensionLaunchProvider`（実験的）：`{ resolve({ id, name, modulePath, source }) }` が `{ launch: { executable, args, env } }` を返す。EVAL の仕組みが Node.js で起動する（`extension-launch.mjs`、`extension-bootstrap.mjs`、`extension-sdk-resolver.mjs`）。環境変数 EXTENSION_PATH にエクステンションの入口を入れる。
- 起動のコマンドを返さない（`launch` を省く）と、そのエクステンションは起動されず、status が failed になる。**ユーザーの `~/.copilot/extensions/` のエクステンション（`user:<名前>`）は、SDK のセッションでも見つかる**（R2 の (2) #4 のとおり）が、起動を断れば混ざらない。これを「止める手段」に使う（生成プラグイン以外は起動しない）。
- エクステンションの読み込みのときの確認（`extension-permission-access`）は、この方式では出なかった（フックと許可の受け口を持つエクステンションでも）。
- `requestExtensions` を省いたなしの実行は、エクステンションを見つけもしない（`extensions.list()` が空）。
- `plugins.list()` の要素は `{ name, marketplace, version, enabled }`（`installedFrom` や `source` は出なかった）。名前で見分ける。
- エクステンションの名前（`extensions.list()` の `name`）は `smoke-plugin:smoke-plugin`、`id` は `plugin:smoke-plugin:smoke-plugin`。
- `--plugin-dir` で読み込んだプラグインのエクステンションのツールを、モデルが呼び、結果の URL がチャット（`assistant.message`、`agentId` なし）に出る。`tool.execution_*` も届く。
- **通しの確認（使い捨て）**：本物の SDK・ランタイム・Playwright・ひな形の本物の画面（ui/app.mjs）と、`runEval` をつないだ。エクステンション（小さなもの）が `smoke-plugin_open` で画面を起動して URL を返し、偽のモデルがそのツールを呼ぶ。結果：ありの実行で URL がチャットに出る → Playwright が開く → 設定（週・項目の数・文体・最大の回数）を入れて開始 → 画面の `core.start` に設定がそのまま届く → 終わった理由「評価基準をすべて満たした」→ 作業フォルダの成果物を採点して 2/2 合格。なしの実行は 0/2、差は 1。
  - エクステンションの `process.cwd()` は、セッションの作業フォルダと同じ（R2 の「見込み」が確かめられた）。
  - エクステンションの環境に `COPILOT_HOME` は渡る（EVAL の環境から）。`GITHUB_TOKEN` は渡らない（launch provider が外す）。
  - ユーザーの `user:` のエクステンションは、起動を断られて `failed`。結果の `refusedExtensions` と `extensionLaunch.refused` に残り、「混ざった」には数えない。

   - `plugin-creator_results` には、`result.json`（EVAL）と `tests/results/latest.json`（1・2段目）のパスを渡す。
   - EVAL の前提：ユーザーの手元で Copilot にログインしていること（ログインしていないと、セッションを作れず、実行が `error` になる。`runs[].error` に理由が出る）。生成プラグインの `tests/eval/<課題>/eval.json` が要る（check の書き方は下の「作業エージェントへの引き継ぎ」）。
5. AI クレジットの上限：EVAL 中に AI クレジットの上限の確認が出ると、クレジットを足さずに止め、`stopped.reason` が `credit_limit` になる。続きを回すかは、ユーザーに聞く。

## C1 への引き継ぎ（EVAL の結果のファイルの形。run.mjs と results.mjs で確定）

場所：`<生成プラグイン>/tests/results/eval-<YYYYMMDD-HHMMSS>/result.json`（同じ秒に2つ始めたときは末尾に `-2`）。実行ごとの記録は同じフォルダの `runs/<課題>/<with|without>-<回>/`（`events.jsonl`、`screen.json`、`screen.png`）。`eval.mjs run` は、同じ JSON を標準出力にも出す（`resultFile` に result.json の場所が入る）。1・2段目の入口 run.py の結果（`tests/results/latest.json`）とは別のファイル。

C1 の results.mjs が今読む項目は、すべてこの形にそろえてある（`evalView` の読み分け：`runs` があれば EVAL の結果）。

```text
kind          "eval"
status        "running"（途中の書き出し）| "completed" | "stopped"（試験全体が途中で止まった）
stopped       null | { reason, message, run, at }   reason：managed_approval、credit_limit、plugin_not_loaded、extension_missing、extension_failed、browser_failed、interrupted（外からの中断の合図）
              message は平易な日本語で、止めた理由。そのまま画面に出してよい
plugin        { name, version, path }
startedAt / finishedAt    ISO 8601
options       { runs, model, timeoutMinutes, ... }
versions      { copilotSdk, playwright, node, copilotCli, browser }   使った版（testing.md 10.4）。browser は chrome・msedge・chromium
tasks         [{ id, criteria: [{ id, text, grading }] }]
runs[]        実行ごと
  task        課題の id
  variant     "with"（生成プラグインあり）| "without"
  n           何回目
  status      completed | incomplete | error | stopped | skipped    （意味は results.mjs の先頭）
  error       null | 平易な日本語の理由
  criteria[]  { id, text, grading, pass, reason, error? }   基準ごとの合否（REQ-041 の1つ目）。status が error・stopped・skipped の実行は []
  passed / total / score    score は 合格の数 ÷ 基準の数。採点しない実行は null
  credits     この実行で使った AI クレジット（採点の分は含まない）。creditsStatus：complete | partial | unavailable。creditsByModel
  judgeCredits / judgments  モデルの判定に使った AI クレジットと件数
  endReason   ありのとき、画面に出た終わった理由 { kind, detail, unstoppable, text }。text は「評価基準をすべて満たした」など
  models / skills / subagents / plugins / extensions / foreignExtensions / foreignPlugins / permissions / questions   実行の記録
  workDir    その実行の作業フォルダ（OS の一時フォルダの下。消さずに残してある。中身を見たいときの場所）
  events / screen    実行ごとの記録のファイル（結果のフォルダからの相対）
scores        { with, without, difference, byTask }   あり・なしの点数とその差（REQ-041 の2つ目）。0〜1。採点した実行の平均。差はありからなしを引く。出せないものは null

counts        { runs, graded, judgments, byStatus }
```

## 作業エージェントへの引き継ぎ（eval.json の check の書き方。grade.mjs で確定）

eval.json の形は BLUEPRINT 4.3 のとおり。基準（criteria の1件）の `grading` と `check` は次の決まり。`validateTask`（grade.mjs）が、EVAL の見込みと実行の前に確かめ、誤りがあれば何も始めない。

- `grading: "program"`：文字や形で決まる基準。`check` が要る。
  - `{ "type": "file_exists", "file": "out/*.md" }`：`file` に当てはまる、空でないファイルがある。
  - `{ "type": "contains", "file": "out/*.md", "text": "52万円" }`：当てはまるファイルのどれかに、`text` という文字がある。
  - `{ "type": "not_contains", "file": "out/*.md", "text": "個人名" }`：当てはまるファイルが1つ以上あり、どれにも `text` がない（ファイルが作られていないときは不合格）。
  - `{ "type": "regex", "file": "out/*.md", "pattern": "\\d+万円", "flags": "i" }`：当てはまるファイルのどれかに、正規表現が合う。`flags` は省ける。使えるのは i・m・s・u。最後の行が決まった文字、のような基準も `"以上\\s*$"` で書ける。
- `grading: "model"`：それ以外の基準（読みやすさなど）。`check` は省ける。成果物を絞りたいときだけ `"check": { "files": ["out/*.md"] }`。
- `file` は、作業フォルダの根からの相対のグロブ（`/` 区切り）。使えるのは `*`（`/` を越えない）、`**`（`/` を越える。`**/` は0個以上のフォルダ）、`?`、`[abc]`・`[!abc]`、`{md,txt}`。絶対の場所と `..` と `\` は使えない。大文字小文字は区別する。
- 課題の `inputs` として写したファイルのうち、中身が変わっていないものは「当てはまるファイル」に数えない（入力だけで合格しないため）。docx・xlsx・pptx は中の文字を取り出して調べる。Shift_JIS のファイルも文字として読む。
- 知らない項目は誤りにする（つづりの間違いを見つけるため）。`check` の中の項目は、上に書いたものだけ。
- 基準の数が多いほど AI クレジットがかかるのは model の基準だけ（program はモデルを使わない）。文字や形で決まるものは program にする（testing.md 10.4）。
- `settings` は `{ "maxIterations": 整数, "task": { "<作業の定義の settings の key>": 文字・数・真偽 } }`。画面の欄の id は `setting-<key>`（`\w` と `-` 以外は `_` にする）。欄がない key があれば、その実行は失敗する。
- A3 へ：1段目の EVAL の検査（check_structure.py）は、program の `check.type` が上の4種類で、種類ごとの必須の項目があることまで見てよい（今は `check.type` があることまで）。
