## スクリプトの呼び方と出力（B3 の手順向け）

```text
python3 <make-plugin のフォルダ>/scripts/scaffold.py build --hearing <state.json のパス> --work <作業フォルダ>/.plugin-creator-work --out <作業フォルダ>/<新しいフォルダ>
python3 <make-plugin のフォルダ>/scripts/scaffold.py check-base --out <生成プラグインのフォルダ> [--restore]
```

- `--hearing` の state.json のパスは、`plugin-creator_state` の返り値の「ヒアリングの記録（state.json）：…」にある。
- `--work` は、名前が `.plugin-creator-work` のフォルダ（その親が作業フォルダ）。`--out` は、作業フォルダの中の、まだないフォルダ（作り直しでも新しいフォルダ。名前は何でもよい）。
- 標準出力に JSON を1つだけ出す。終了コード：0 成功、1 断った・失敗した・土台に違いが残る、2 引数の誤り（標準エラーに使い方）。
- build 成功：`{"ok": true, "out", "plugin_name", "marketplace_name", "entry_skill", "workers": [agent…], "criteria": [{"id","knowledge"}…], "knowledge": {"criterion": n, "other": m}, "eval_inputs": [to…], "commit", "work_folder_removed", "warnings": [文…]}`。`warnings` はユーザーかメインのエージェントが読む注意（例：使われなかった差し込み口の文、どの EVAL の課題にも入っていない基準、task.json の形の確かめを 1段目に任せたこと）。
- build が断る・失敗するとき：`{"ok": false, "problems": [平易な日本語の文…]}`、終了コード 1。作ったフォルダは消える。`.plugin-creator-work/` は残る（`problems` に沿って parts を直して、同じコマンドをもう一度動かせる）。成功したときだけ `.plugin-creator-work/` を消す。ヒアリングの記録は変えない。
- 組み立てを断る主な場合：段階が「生成」でない・承認の時刻がない（生成前の確認の関門）、--out がすでにある、--out が作業フォルダの外か一時フォルダの中、parts の形の誤り、埋まらない差し込み口、tools を入れる場所がない、task.json の形の誤り・作業エージェントが criteria を書いた、eval.json の基準の指定の誤り、eval_inputs の実物がない、parts/files がひな形や組み立てのファイルを上書きしようとした。
- check-base 成功：`{"ok": true, "plugin", "differences": [], "restored": [], "remaining": []}`。違いがあるとき：`ok` が false（終了コード 1）で、`differences` は `{"file": 生成プラグインの中のパス, "kind": "changed"|"missing"|"extra", "message"}` の一覧。`--restore` を付けると、changed と missing はひな形から入れ直し、extra（土台の `core/`・`ui/` にあるひな形にないファイル）は消す。入れ直して違いがなくなれば `ok` は true、終了コード 0。見つけた違いは `differences` に残して知らせる（作業エージェントが土台を書き換えた印。直しの回数に数えるか、ユーザーに知らせるかは B3 が決める）。`restored` は入れ直したファイル、`remaining` は直らなかった違い。
- 土台＝ひな形の `extensions/_plugin_/` の下のファイルすべて（extension.mjs、adapter.mjs、core/、ui/。B1 の adapter.mjs を含む）。`core/`・`ui/` の中では、ひな形にないファイルも違いにする。エクステンションのフォルダの直下に足したファイル（task.json など）は違いにしない。
- Python 3.9 以上。PyYAML と jsonschema は要らない（あれば task.json の形も確かめる）。

### 最初のコミットの名前とメール（B3 の依頼 4）

- build の最初のコミットは、ユーザーの git の設定（`user.name` と `user.email`。生成したリポジトリから見える、リポジトリ・ユーザー・システムのどれでも）が両方あれば、それを使う。どちらか一方でもなければ、そのコミットだけ `plugin-creator <plugin-creator@localhost>` を使う（`git -c user.name=… -c user.email=… commit`。git の設定ファイルには何も書かない）。署名（`commit.gpgsign=false`）とコミット前のフック（`--no-verify`）は、人の操作を待たないよう使わない。
- 確かめた（名前とメールがない環境）：最初のコミットは通り、作者は `plugin-creator <plugin-creator@localhost>`。そのあとの普通の `git commit` は「Author identity unknown」で失敗する。
- メインのエージェントが生成の後の直しをコミットするときは、同じ決め方にする：`git config user.name` と `git config user.email` が両方あればそのまま `git commit`、なければ `git -c commit.gpgsign=false -c user.name=plugin-creator -c user.email=plugin-creator@localhost commit --no-verify -am "…"`。タグ `plugin-creator-generated` は、軽いタグ（`git tag -f plugin-creator-generated`）なら名前とメールがなくても付けられる（`-a` の注釈つきのタグは「Committer identity unknown」で失敗するので使わない）。`git diff plugin-creator-generated` で、生成したときとの差分が見られることを確かめた。
- 決めるのは B3・統括：この決め方をするコミットとタグ付けを、`scaffold.py` の小さなサブコマンド（例：`commit --out … --message …  --tag …`）にして、モデルが `-c` の指定を間違えないようにするか。今は足していない（設計書にないため）。

## 作業エージェントへの引き継ぎ（B3 の作業エージェント向け。書き方の決まり）

置き場所は BLUEPRINT 8章のとおり：`.plugin-creator-work/parts/`。

- `manifest.json`（メインのエージェントが書く）：`{ "plugin_name", "plugin_description", "entry_skill": { "name", "description" }, "workers": [{ "agent", "label", "extra_tools": [] }], "verifier": { "extra_tools": [] }, "orchestrator": { "extra_tools": [] }, "eval_inputs": [{ "from", "to" }] }`。知らない項目は断る。
  - `plugin_name`・`entry_skill.name`：小文字の英数字とハイフンだけ、64文字以内。`plugin_description`・`entry_skill.description`：1行、1024文字以内。
  - `workers[].agent`：`worker` か `worker-<名前>`（task.json の workers[].agent と同じ並び・同じ集まり）。`label` は1行で、task.json の workers[].label と同じ。1体目は `worker`。`worker` を載せなければ、`worker.agent.md` は残らない。
  - `extra_tools`：`サーバー名/ツール名` の形（英数字と `.` `_` `:` `/` `-`）。ひな形のエージェントの定義にある差し込み口 `{{orchestrator_extra_tools}}`・`{{worker_extra_tools}}`・`{{verifier_extra_tools}}` に、`  - "名前"` の行として入る。
  - `eval_inputs`（B3 の依頼 3）：EVAL の課題の入力にする実物のファイル。`from` はユーザーの実物の絶対パス（ファイル。なければ build が断り、どれがないかを示す）、`to` は `tests/eval/<課題>/inputs/<名前>`（下の階層も可）。build がこの場所へそのまま写す。仮のファイル（メインのエージェントが中身を作る）は、メインのエージェントが `parts/files/tests/eval/<課題>/inputs/<名前>` に書く（build がそのまま写す）。同じ場所を `eval_inputs` と `parts/files` の両方に書くと断る。eval.json の `inputs` は、課題のフォルダからの相対パス（例：`inputs/前回の週報.docx`）。
- `task.json`：`criteria` は書かない（書くと断る。空の `[]` はよい）。合否の基準は、build がナレッジの「決まった」「合否の決め方」から C-01 から書く。`workers` の agent と label は manifest.json と同じ。形は core/task.schema.json。
- `slots/<差し込み口の名前>.md`：今のひな形が使う差し込み口は 7 つ。
  - `entry-task`（入口のスキルの「このプラグインがする作業」の節）、`orchestrator-task`、`verifier-task`、`task-requirements`（仕様書 7章。`### REQ-101 題` から）、`task-design`（設計書 8章。`### 8.1 題` から）、`task-trace`（設計書 9章の追跡の表の続きの行だけ。5列、見出し行・空行なし）。
  - `worker-task`（B3 の依頼 1）：作業役は、作業エージェントごとに `slots/worker-task.<agent>.md`（`<agent>` は manifest.json の workers[].agent。1体目は `worker.agent.md` 用の `worker-task.worker.md`）。ひな形の worker.agent.md にある `{{slot:worker-task}}` を、build が各エージェントのファイルで `{{slot:worker-task.<agent>}}` に直してから埋める。
  - 空の文、名前の形が違うファイル（`<名前>.md` でないもの）は断る。ひな形が使わない差し込み口の文は、警告を出して入れない。差し込み口の文の中に別の差し込み口は書けない。文の中に `{{plugin_name}}` などの決まった値を書いてよい。`{{` で始まり英字で続く `}}` までの字（`{{名前}}`）は差し込み口と読まれるので、そのほかの用途に使わない（`${{…}}` は読まれない）。
  - 「それ以外」のナレッジの番号（`K-01` の形）は、これらの文かファイルに書く（A3 の構造の検査が探す）。
- `files/<生成プラグインの中のパス>`：そのまま足すファイル（scripts/、mcp.json、tests/stage2/task/、tests/eval/<課題>/ など）。ひな形のファイルと、組み立てが作るファイル（task.json、tests/knowledge.json、土台、文書、README など）の場所には書けない（断る）。シンボリックリンクと `.git` は置けない。中の `{{…}}` は置き換えない。
- `files/tests/eval/<課題>/eval.json`（B3 の依頼 2）：`criteria` の各要素に、作業エージェントは `knowledge`（もとの「合否の決め方」のナレッジの番号）・`grading`・`check` だけを書く。build が、`knowledge` をキーにして task.json の criteria から `id` と `text` を入れ（`knowledge` の項目は消す）、`id`・`text` の並びを先頭にして書き直す。作業エージェントが `id`（C-01 の形）か `text` を書いても、`text` は作業の定義の文で置き換える（`id` と `knowledge` が食い違えば断る）。決まった基準のどれも指していない要素・criteria がない課題は断る。基準が課題のどれにも入っていないときは警告（構造の検査で不合格になる）。

## 組み立てへの引き継ぎ（B1・B2・A1〜A4 向け。ひな形の書き方）

- 差し込み口の書き方：`{{slot:名前}}`（作業エージェントの文）と `{{名前}}`（決まった値）。名前は英字で始まり、英数字と `_` `.` `-`。`${{…}}` と、`{{ ` のように空白が入るものは差し込み口ではない。
- 決まった値：`plugin_name`、`plugin_description`、`marketplace_name`（プラグインの名前と同じ）、`generated_date`（YYYY-MM-DD）、`entry_skill_name`、`entry_skill_description`。
  - JSON のファイルでは、文字列の中に書く（`"{{plugin_description}}"`）。中身を JSON の escape で入れる。
  - SKILL.md・エージェントの定義のフロントマターでは、二重引用符の中（`"{{…}}"`、`"前置き {{…}} 後ろ"`）なら中身だけを escape して入れる。`キー: {{…}}` の形なら、名前（英字で始まる英数字と `.` `_` `-`。`true` などは除く）は引用符なし、そのほかは YAML の二重引用符つきの文字列にして入れる。
  - そのほか（本文、README、文書）は、そのまま入れる。
- 行ごと置き換える差し込み口（その字だけの行に書く）：`{{orchestrator_extra_tools}}`・`{{worker_extra_tools}}`・`{{verifier_extra_tools}}` は、フロントマターの tools の最後の行の次に、行頭の空白なしで置く（B2 の形）。ツールごとに `  - "名前"`（空白2つ。差し込み口の行に字下げがあればその字下げ）の行になり、ツールがなければ行ごと消える。ツールがあるのに差し込み口がないと断る。`{{worker_agents}}` は統括の定義の本文に置く（作業エージェントごとに ``- `プラグインの名前:agent`：label`` の行）。
- 土台のファイル（`extensions/_plugin_/` の下）は、書き換えない。差し込み口があると断る（ひな形の誤り）。
- 作業エージェントが2体以上のとき：worker.agent.md を元に、作業エージェントごとに `<agent>.agent.md` を作る。フロントマターに `name:` があれば、その名前に書き換える（今の worker.agent.md には `name:` がない）。
- 組み立てるプラグインの名前の決まり：`a-z0-9` とハイフン（R3 の勧め）。ひな形にコピー元から要らないもの（`__pycache__`、`.git`、`node_modules`、`.venv`、`tests/results/`）は写さない。

## 決めたこと

- state.json の読み方（C1 の hearing.mjs の形）：段階は記号 `generate`、ナレッジは `kind`＝`criterion`/`other`、`status`＝`decided`、項目の日本語の名前は `itemName`（なければ `item` の記号）。承認の時刻は `approvedAt`。日本語の名前では読まない（names.mjs の「記録には内部の記号を書く」に従う）。`candidate`（候補）と `dropped`（外した）は、基準にもナレッジの一覧にも入れない。
- tests/knowledge.json は 番号・種類・項目（日本語の名前）・文 の4つだけ（出どころとユーザーの言葉は入れない。リポジトリを公開するときに、ユーザーの言葉が出ないようにするため）。
- マーケットプレイスの名前（`{{marketplace_name}}`）は、プラグインの名前と同じ（余分な決まりを作らない）。インストールは `<名前>@<名前>`。
- marketplace.json は必須の項目だけ（name、owner.name、plugins[].name と source）。`owner.name` はプラグインの名前（ユーザーの名前を集めない・コミットに入れない）。`source` は `./`（リポジトリ直下のプラグイン）。plugin.json は `$schema`・name・version（0.1.0）・description だけ。`repository` は公開するまで書かない（core の起票は、これがないと手順を示す）。
- 差し込み口の置き換えの順は A4 のとおり：文、行ごと置き換える差し込み口、決まった値。
- 差し込み口が残る・値が決まっていない・土台に差し込み口がある、は組み立てを断る。使われない差し込み口の文は警告だけ（断らない。作業エージェントの出力が黙って捨てられたことは、警告で見える。ナレッジの番号が抜けていれば構造の検査が見つける）。
- 作業エージェントの数：manifest.json の workers が正。task.json の workers と agent と label が合わなければ断る（画面と統括の指示が食い違うため）。
- EVAL の課題が1つもない・基準がどの課題にも入っていない、は警告にとどめる（構造の検査が不合格にする。組み立ての後は一時フォルダが消えるので、直しは生成プラグインの中で行う）。eval.json の中身が壊れている・基準を指せない、は断る（基準の写しを入れられないため）。
- 1段目と同じ日本語の文で task.json の形の誤りを示すため、ひな形の check_structure.py の `schema_problems` を使う。jsonschema か PyYAML がなければ、確かめを 1段目に任せ、警告を出す（組み立ての時点では、ユーザーの承認の前に試験の道具を入れられないため）。
- git：最初のコミットは `git init` → `git add -A` → `commit`（署名なし、フックなし）。名前とメールの決め方は上のとおり。ブランチ名はユーザーの git の設定に任せる。

## 上位の文書で直すこと・他の担当へ

- BLUEPRINT 8章の manifest.json の形に `eval_inputs`（B3 の依頼 3）を足す。差し込み口の表に、ひな形が使う `worker-task`（作業エージェントごとに `worker-task.<agent>` へ書き換える）と、決まった値 `worker_agents`・`*_extra_tools` の書き方（B2 の取り決め）を足す。`worker-task.<agent>` と書いてある箇所は、ファイル名の規則であって、ひな形の中の字は `{{slot:worker-task}}` である。
- generated-plugin-structure.md 7章：「`core/`、`ui/`、`extension.mjs` は、ひな形からそのまま入れる」に、`adapter.mjs`（B1）が加わる。check-base は、ひな形の `extensions/_plugin_/` の下のすべてのファイルを土台として比べる。
- hearing.md 6.5：仮のファイルは、「承認の後に組み立てのスクリプトがファイルに書く」と読めるが、実装は「メインのエージェントが `parts/files/` の下に書き、build がそのまま写す」。実物のファイルは manifest.json の `eval_inputs` で build が写す。
- creator-structure.md 2章の「スクリプト：組み立て」の行：入力に manifest.json（eval_inputs）が加わること、JSON の出力と終了コードの決まり（上）を書くなら、この行か 4.1。
- A3 へ：ひな形の tests/stage1/selftest/test_check_structure.py と test_run.py が、`extensions/_plugin_/core/task.schema.json` のパスを直書きしている。組み立てでフォルダの名前が変わると、生成プラグインの中ではこの自己試験が動かない（run.py は自己試験を動かさないので、試験の入口には響かない）。
- A3 へ（提案）：1段目に、.github/plugin/marketplace.json の確かめ（name・owner・plugins があり、plugins[].name が plugin.json の name と同じ）を足すと、名前を変えたときのずれが見つかる。今は追跡の表がファイルがあることだけを見る。
- C3・run.py へ：生成プラグインの `python3 tests/run.py` は、tests/node_modules の Playwright がないと「道具が足りない」で止まる。組み立ての直後は必ずこの状態になるので、スキルの手順は「道具の確かめと用意（check_tools.py）→ 入口」の順にする（B3 の手順にすでにある見込み）。
