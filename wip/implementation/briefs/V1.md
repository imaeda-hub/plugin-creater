# V1 の指示：本物の Copilot CLI での読み込みの確かめ（偽物のモデルで）

担当の番号：V1。

## 目的
開発の試験は Claude Code で行う（testing.md 1章）。ただし、Copilot CLI でしか起きない読み込みの不具合を、人の最終確認（testing.md 9章）の前に、できるだけ見つけておく。前のセッションと同じく、本物の Copilot CLI を、ログインせずにオフラインのモードで、偽物のモデルの窓口につないで動かす（ナレッジ .claude/memory/copilot-cli-testing.md の「ログインせずに偽物のモデルで動かす」「偽物のモデルで調べるときの方法」）。これは試験の仕組みの一部ではなく、確かめのための作業である。作ったスクリプトはスクラッチに置き、リポジトリには結果の報告だけを書く。

## 確かめること（できたものから報告に書く）
1. クリエイター（リポジトリの直下）を、手元のフォルダのマーケットプレイスとして入れられるか（`copilot plugin marketplace add <フォルダ>` → `copilot plugin marketplace browse`（あれば）→ `copilot plugin install plugin-creator@<マーケットプレイスの名前>` → `copilot plugin list --json`）。marketplace.json の `source: "./"` が通るか。`--plugin-dir` でも読み込めるか。`copilot skill list --json` に make-plugin と test-plugin が出るか。スキルのコマンドの名前（`/plugin-creator:make-plugin` か、別の形か）。
2. `--experimental`（または `/experimental on`）で、クリエイターのエクステンションが読み込まれるか。読み込みのときの確認の文と選択肢（R2 の 3.10）。偽物のモデルに届いたリクエストに、`plugin-creator_open` などのツールが、どの名前・どの説明で載るか（ハイフンを含む名前が通るか、defer: "never" が効くか）。偽物のモデルに `plugin-creator_open` を呼ばせて、URL が返り、そのサーバーに 127.0.0.1 からつながるか。
3. C2 の組み立てのスクリプトで見本の生成プラグインを作り（tests/creator/scaffold/ の見本。作るのはスクラッチ）、同じように入れて、`<名前>_open` が URL を返すか。画面の「開始」に当たる窓口（POST /api/start）を呼んで、`tasks.startAgent` で統括エージェントが起動するか（偽物のモデルが統括として返事をする）。止める（POST /api/stop）で取り消されるか。
4. カスタムエージェントの定義が読み込まれるか（`model` のリスト、tools の別名 search・web、`skill` を外したとき）。偽物のモデルで分かる範囲だけ。
5. 分からないこと・確かめられないことは、そう書く（推測で書かない）。

## 決まり
- 共通の決まり：wip/implementation/briefs/common.md（作業のメモは wip/implementation/tasks/V1.md）。
- Copilot CLI は `npm pack @github/copilot@1.0.102` と `@github/copilot-linux-x64@1.0.102` をスクラッチの空のフォルダに取り、版を決めて動かす（ナレッジの「版を決めて動かすときの落とし穴」：COPILOT_CACHE_HOME を分け、COPILOT_AUTO_UPDATE=false と --no-auto-update）。COPILOT_HOME もスクラッチの空のフォルダにする（ユーザーの設定を汚さない）。
- 対話モードを動かすときは、Python の pty と端末の模擬で画面を取る（ナレッジの方法）。
- リポジトリのファイルは変えない（見つけた不具合は報告に書き、統括が担当に頼む）。
