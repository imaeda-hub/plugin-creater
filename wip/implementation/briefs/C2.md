## build がすること
1. 入力を確かめる：state.json の段階が「生成」で承認の時刻があること（なければ組み立てを断る。hearing.md 6.3 の関門）。parts/manifest.json、parts/task.json、parts/slots/、parts/files/ の形。--out のフォルダがまだないこと（作り直しでも新しいフォルダ。REQ-036）。--out が作業フォルダの中であること（REQ-021）。
2. ひな形（このスクリプトから見て ../assets/template/）を --out に写し、_plugin_ と _entry_ の名前を変える。作業エージェントが2体以上なら、worker.agent.md を元に worker-<名前>.agent.md を作る。
3. 差し込み口を slots の文で置き換え、その後に決まった値を置き換える（A4 のメモ）。決まった値：plugin_name、plugin_description、marketplace_name、generated_date、entry_skill_name、entry_skill_description、tools の作業ごとの分（B2 のメモの名前）。埋まらない差し込み口が残ったら失敗にし、どの差し込み口かを示す。
4. task.json：parts/task.json に、ナレッジの種類「合否の決め方」で状態「決まった」のものから criteria を作って入れる（番号は C-01 から、文はナレッジの文のまま、knowledge にナレッジの番号。ユーザーの答え4）。core/task.schema.json で確かめる。
5. tests/knowledge.json：状態「決まった」のナレッジを、番号・種類（合否の決め方→criterion、それ以外→other）・項目・文で書く（BLUEPRINT 4.2）。
6. parts/files/ を写す。tests/eval/*/eval.json の criteria の id と text を、task.json の criteria の写しで埋める（作業エージェントは採点のしかただけを書く。形は BLUEPRINT 4.3）。
7. 土台の確かめ（check-base と同じ）。
8. git init、全部を add して最初のコミット。
9. .plugin-creator-work/ を消す。
10. 作ったフォルダと結果を JSON で標準出力に出す。失敗のときは、何が足りないかを平易な日本語で出し、終了コードを0以外にし、途中まで作ったフォルダは消す。
