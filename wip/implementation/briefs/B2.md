## 決まり
- 差し込み口（`{{slot:<名前>}}`）と決まった値（`{{plugin_name}}` など）は、BLUEPRINT 8章と A4 のメモの名前を使う。入口のスキルのフロントマターの name と description は、組み立てのスクリプトが manifest.json の entry_skill から入れる（`{{entry_skill_name}}`、`{{entry_skill_description}}`）。作業・検証・統括の tools の作業ごとの分は、manifest.json の extra_tools から入れる。差し込み口の名前を決めたら、作業のメモの「組み立てへの引き継ぎ」に一覧で書く（C2 が使う）。
- モデル：統括と検証は `model: [claude-sonnet-5.5, gpt-6.1-sol]`（ユーザーの答え17）、作業は `model: [gpt-6-luna, claude-haiku-5.5]`。`models`・`model-policy` は書かない（R1）。
- tools（4.7）：統括は agent、read、search と記録のツール（plan、review、issue、finish、show。名前は core/tools.mjs のものに `{{plugin_name}}_` を付けた形）。作業は read、edit、execute、search と `{{plugin_name}}_show` と作業ごとの分。検証は read、search と `{{plugin_name}}_verdict` と作業ごとの確かめの分（書き込みとコマンドを入れない）。どれも skill を入れない。
- 統括の手順（4.8）：試行ごとに計画の記録 → 作業を task の mode: "sync" で1体ずつ呼ぶ（名前は `{{plugin_name}}:worker` の形）→ 検証を同じく呼ぶ → すべて合格か上限まで繰り返す → 最後に review を受け取って振り返り、Issue の案を issue で足し、finish でまとめる。ユーザーと確かめた基準を外さず、ゆるめない。記録のツールに断られたら、返された理由に沿って直す。成果物を自分で書かない。合否を自分で決めない。core が組み立てる指示文（頼まれた作業の文、上限、作業ごとの設定の値、基準）とどう組み合わさるかを、A1 の実装で確かめる。
- 検証の手順（4.8、憲章 第19条2項）：評価基準ごとに合否と指摘を verdict で記録してから、統括に同じ内容を返す。成果物を直さない。
- 作業の手順：計画と評価基準とナレッジを受け取り、成果物を作る。自分の成果物の合否を判定しない（R1 の 11）。表示の値は show で送る。
- 入口のスキル（4.7）：作業の依頼を受けたら `{{plugin_name}}_open` を呼び、URL と、実行中は /clear しないこと、実行中の確認にはチャットで答えること、任せたいツールを前もって許可するしかたが README にあること、を示して手番を終える。統括の終わりの知らせを受けたら、結果が画面にあることを伝える。ツールがないときは、3つの原因（/experimental on をしていない、読み込みのときのエクステンションの確認を断った、/extensions mode が Disabled）の直し方を示して止まる。作業には加わらない。
- サブエージェントはユーザーに聞けない（R1 の 10）。費用の低いモデルが途中で止まらないよう、最後までやる1文を置く（R1）。
- ナレッジの番号の例（`K-` に数字が続く文字）を書かない（A3 の引き継ぎ）。
- 指示文は日本語。応答の言語は具体の言語名で書く（R1 の 11）。
- 推測で Copilot CLI の事実を書かない。

## 点検の観点（点検の担当は、割り当てられた観点だけを深く見る）

- `design`：設計書と仕様書と憲章に合っているか。generated-plugin-structure.md 4.3（統括への指示文の組み立てと、定義の本文の組み合わさり方）、4.7（構成と tools、エクステンションのツールがないとき）、4.8（計画・実行・評価の繰り返し、記録のツールの決まり、終わった理由）、4.10（振り返りと Issue の案）、4.13・4.14（/clear、確認はチャットで答える）、6.2（記録のツール）、REQ-005〜REQ-014 の受け入れ基準を満たせる指示か。core の実装（core/*.mjs）が断る記録の順番や形と、指示文の手順が食い違わないか。憲章 第19条（作業は自分の成果物を判定しない、検証は直さない）、第23条、第24条、第10条（要らない記述や重複がないか）。ユーザーの答え（RESUME.md）、特に11・12・17と食い違わないか。
- `format`：最新の公式の書き方（R1 の (1) の決まり、R3 のフロントマターの決まり）に合っているか。フロントマターの項目、name とフォルダ名、description の形と長さ、model と tools の書き方、本文の組み立て、ツール名のバッククォート、差し込み口の置き方（組み立ての後に正しい YAML とスキルの決まりになるか。tasks/B2.md と tasks/C2.md の組み立てへの引き継ぎで確かめる）。
- `models`：統括と検証（claude-sonnet-5.5、gpt-6.1-sol）、作業（gpt-6-luna、claude-haiku-5.5）、入口のスキルを読むメインのエージェント（ユーザーが選んだモデル）のそれぞれが、指示をどう読むか。GPT の族と Claude 5 の族のシステムプロンプトの文（hearing.md 2.7）を踏まえ、統括が作業を自分でしてしまう、検証が成果物を直す、作業が合否を判定する、記録のツールを呼ばずに進める、裏で呼ぶ（mode が sync でない）、繰り返しを途中でやめる、費用の低いモデルが途中で止まる、などの余地がないか。食い違う指示、あいまいな指示がないか。
- `language`：入口のスキルがユーザーに示す文（URL を示すとき、ツールがないときの直し方、終わりの知らせ）が、簡潔で、説明のない専門用語がなく、生成プラグインの README と食い違わないか（REQ-025、憲章 第9条）。記録のツールの説明の文が、モデルに正しく伝わる書き方か。
