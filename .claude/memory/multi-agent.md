# マルチエージェントの強み

## 1. コンテキストウィンドウの最適化

- 1つのエージェントでいろいろなタスクをこなすと、コンテキストウィンドウがいろいろなタスクの情報で埋まってしまう。
- タスクを分解し、複数のエージェントがそれぞれのコンテキストを持つと、各コンテキストがそのタスクに特化したものになり、最適化できる。
- 大きなプロジェクトほど、複数のエージェントで担当を分けることが効く。

## 2. 処理速度

- タスクを並列で実行できる単位に分解し、複数のエージェントで同時に実行することで、処理速度を上げられる。

## 3. AI クレジットの最適化

- 一般に、統括役や検証役には高い思考力が求められるため、AI クレジットの単価が高いモデルを使う。
- 作業役には高い思考力が求められないため、ローレンジのモデルを使う。
- これにより、すべてローレンジのモデルにするよりアウトプットが高く、すべてハイエンドのモデルにするより安いクレジットで、高いアウトプットを出せる。

## 並列で動かすときの注意（2026年10月、この開発での実測）

- **利用枠の上限**：6体の作業エージェントを並べると、30〜40分ほどで利用枠の上限に当たった（2日間で少なくとも4回）。上限は約5時間ごとに戻った。プランとモデルの組み合わせで変わる。
- **中断に備える**：共通の指示と担当ごとの指示をファイルに置き、新しいエージェントには「このファイルを読んで従う」とだけ渡す。担当は、最初に作業のメモを作り、ファイルを1つ作るたびに状態を更新する。止まったら、戻ったあとに、メモとできているファイルから続ける。同じセッションなら、止まったエージェントに続きの指示を送れる。新しいセッションなら、同じ指示で新しいエージェントを立て、メモから続けさせる。
- **ワークフロー（Workflow ツール）は、止まると最初からやり直しになる。** プロセスの再起動のあとに、道具が使えなくなったこともあった。長い作業は、担当ごとに Agent の道具で分ける。
- **変異の試験（わざと壊して、試験が落ちるかを見る）は、写しで行う**：元のファイルを壊している間に、途中経過のコミットが入ると、壊した状態がコミットされた（実際に起きた）。別のフォルダの写し（git worktree など）で行い、途中経過のコミットの前に、`git status` で `*.mutbak` のような一時ファイルがないかを見る。
- **読ませないフォルダ**：フォルダの中身を読まないだけでは足りない。`git status`、`git diff --stat`、`git log` は、ファイル名を出力に出す（作業のはじめの `git status` で、読ませないフォルダのファイル名が3つ出た。中身は読んでいない）。除外の指定を付けるか、`grep -v` で出力から外す。検索は `--exclude-dir` で外す。実験用にリポジトリを写すときも、そのフォルダを写さない。
