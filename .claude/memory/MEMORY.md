# ナレッジ索引

- [AI エンジニアリングの5分類](ai-engineering.md) — プロンプト／コンテキスト／ハーネス／ループ／グラフ。提唱された順と、互いの関係
- [ハーネスエンジニアリングの目的と人間の役割](harness-purpose.md) — 目的はヒューマン・オン・ザ・ループ。監督のためエージェントの振る舞いを可視化する。ハーネスは AI が知らないことを人間が対話を通じて作る。Web管理画面は性能の低いモデルでは失敗しやすいので、クリエイターが土台を用意し、作り込みを支援する
- [スキル（GitHub Copilot CLI）](skills.md) — 本質は description。Markdown・スクリプト・アセット・リファレンスで構成し、推論の要否で Markdown とスクリプトに分ける
- [MCP](mcp.md) — 外部システムと安全にデータをやり取りする役割に特化。ローカルの操作はスキルへ移行
- [カスタムエージェント（GitHub Copilot CLI）](custom-agents.md) — マルチエージェント構成の1エージェントを定義。必須は description だけ。権限は tools の別名（read、edit、execute など）で絞る。サブエージェントがスキルを呼んで手順を始めないよう、tools を絞る。プラグインからメインのエージェントのモデルは決められず、Auto だとサブエージェントのモデル指定も効かない。優先する順のモデルの書き方は、公式ドキュメント（`models`）と実装（`model` のリスト）で食い違う。サブエージェントは ask_user を持たない（実測）。システムプロンプトはモデルの族ごとに分かれ、今の GPT と Claude の族にも聞き取りと逆向きの指示がある。退役したモデルの事実に頼らない
- [マルチエージェントの強み](multi-agent.md) — コンテキストウィンドウの最適化、処理速度、AI クレジットの最適化
- [ハーネスの置き場所](harness-placement.md) — 決められた場所に置くことで効果を発揮。GitHub リポジトリでは `.github` 内
- [プラグイン](plugins.md) — ハーネス群の配布・インストールの仕様。Agent Plugins 1.0.0 はスキルと MCP のみ、Copilot CLI はそれ以外も同梱できる。Copilot CLI 固有の部品は `com.github.copilot/` に置けば Agent Plugins と両立する。Copilot CLI は Agent Plugins の形式と以前の形式の両方を読み込める
- [画面と Copilot CLI のつなぎ方](dashboard-integration.md) — Web管理画面とつなぐ候補はフック、MCP サーバー、エクステンション。フックで状態を受け取り、ツールを拒み、エージェントを止められる。時間切れは素通りになる。エクステンションは試験的。サンドボックスを有効にすると、Linux では中で起動した画面にブラウザーからつながらない。設計ではエクステンションでつなぐ。エクステンションからエージェントの起動・取り消し・モデルの取得ができる見込みで、読み込みのときに確認が1回出る
- [ハーネスの調達](harness-sourcing.md) — 標準機能 → OSS（Awesome Copilot など）→ 自作 の順に検討。ユーザーの既存資産も対話で引き出して流用する。既存のプラグインは、まるごと生成プラグインの形に作り直すこともある
- [実例：組み込み機器のプリントデバッグ](example-embedded-print-debug.md) — クロスコンパイル・デプロイ・ログ取得をスキル化し、ヒューマン・オン・ザ・ループにする
- [自己改善](self-improvement.md) — （大事な考え）実行中にログを残し、実行後に振り返って改善提案し、自分のリポジトリへ Issue を発行する
- [AI の思考サイクル（PDS）](pds-cycle.md) — （大事な考え）闇雲に実行を繰り返さず、必ず計画・実行・評価のサイクルを回す
- [ソフトウェア工学の知識体系を参考にする](software-engineering-knowledge.md) — （大事な考え）推測だけでなく、SWEBOK など人間が蓄積してきた知識体系を取り入れる
- [プラグインを作るプラグイン（ハーネスの作り方）](plugin-creator-rationale.md) — （プロジェクトの根幹）プラグインには共通部分があるので、レベルの高いプラグインを再現性高く作るプラグインで質とスピードを上げる。クリエイターの中心は、人間からナレッジを引き出すこと。その質問は性能に直結するので、試験や利用の結果をもとに改善し続ける
- [ナレッジの重要性](knowledge-importance.md) — （大事な考え）人間が蓄積したナレッジを取り込み、対話で得たナレッジもセッションをまたいで残す。索引を直したら、リンクと載せ漏れを確かめる
- [人間と AI のコミュニケーション](communication.md) — （大事な考え）正しさより分かりやすさ。簡潔に、伝わる用語で書き、指摘は文言ではなく目的に沿って直す。質問は、決めないと何が困るかを最初に書く。まとめた言葉で聞かず、何のことかを先に示す。長い比較や調査は HTML のページで見せる。比喩で言い換えず正確な技術用語で聞く、1つの言葉を2つの意味で使わない、事実で決まることは問いにしない
- [リファクタリング](refactoring.md) — 振る舞いを変えずに構造を整える。機能の変更と混ぜず、小さな手順で確かめる。SKILL.md も対象で、description の変更は振る舞いの変更として扱う
- [人からナレッジを引き出す手法](knowledge-elicitation.md) — SWEBOK の要求の引き出し（V3 は7つ、V4 は一覧が違う）。当たり前のことは話されにくい。文字のチャットで使えた手法：実際の1件をたどる（CDM）、見分け方をたどる（laddering）。はい・いいえの確認は「はい」に偏る
- [KISS](kiss.md) — （大事な考え）必要なものだけを、できるだけ単純に作る。AI で作るとリポジトリは肥大化しやすい。リファクタリングはあとから整え、KISS は最初から足さない
- [Copilot CLI の試験機能](copilot-cli-testing.md) — EVAL 専用のコマンドはない。`-p`・`--plugin-dir`・実行記録で組める。トークンなしでもスキルと MCP の読み込みは確かめられるが、カスタムエージェントは確かめられない。ログインせずに、オフラインのモードで偽物のモデルにつなげば、本物の Copilot CLI を動かせる。送られたリクエストを記録すればシステムプロンプトやツールの定義が分かる。版を決めて動かすときは、キャッシュの新しい版が動く落とし穴に注意する。Copilot SDK でプラグインを読み込み、質問に答え、イベントで採点できる。エクステンションの読み込みには `requestExtensions: true` が要る。許可の求めは答える仕組みを登録したすべての相手に届き、先の答えが使われる。AI クレジットの数え方。ドキュメントで分からないことは、npm パッケージの中身（更新履歴、スキーマ、組み込みの定義）で確かめる
- [Claude Code の EVAL の仕組み](claude-plugin-eval.md) — 課題をプラグインあり・なしで3回ずつ実行し、スコアを比べる。採点の種類。プログラムでの採点はなく、ユーザー役が答える仕組みも見当たらない
- [Agent SDK で EVAL を動かすときの注意](agent-sdk-eval.md) — 環境変数は必要なものだけ渡す。コマンドはサンドボックスに閉じ込め、Web 画面の操作だけ外に出す。許可を求めるのは質問だけにする
- [Anthropic の skill-creator](skill-creator.md) — 軽く作り、試して直すことに重きを置く。結果を見る画面で感想を集めて直す、紛らわしい依頼で呼ばれ方を試して説明文を直す、採点者が試験の弱さも指摘する。集計のフォルダの食い違い、費用の見込みを出さないことに注意
- [ユーザー役の AI で人を模擬するときの注意](user-simulation.md) — 模擬したユーザーは人の代わりにならない。使う前にユーザー役だけを試験し、モデルと指示を固定する。対照のクリエイターと別の分野の模擬ユーザーで、試験が正しく働くかも確かめる。会話例は点数だけで選ばず、クリエイターの AI に読ませない
