# ハーネスエンジニアリングの目的と人間の役割

## ハーネスは手段

- ハーネスはあくまで手段である。ハーネスによって達成される目的として有名なものが、ヒューマン・オン・ザ・ループである。

  | 用語 | 意味 |
  | --- | --- |
  | ヒューマン・イン・ザ・ループ | 繰り返し作業の中に、人間の作業が介入する状態 |
  | ヒューマン・オン・ザ・ループ | ハーネスエンジニアリングによって、人間の作業だった部分を AI が自律的にできるようになった状態 |

- ヒューマン・イン・ザ・ループからヒューマン・オン・ザ・ループに変わると、開発効率が格段に上がる。これが、ハーネスエンジニアリングによって達成できることの一つである。

## ヒューマン・オン・ザ・ループでの可視化

- ヒューマン・オン・ザ・ループでは、AI が基本的に自律的にループ処理を行い、人間はそれを監督する立場になる。
- このとき大事なのは、エージェントの振る舞いを可視化すること、つまり AI の振る舞いを人間が簡単に見られるようにすることである。
- そうすることで、人間が AI の異常を素早く検知し、適切に介入して軌道修正できる。
- 現在の GitHub Copilot CLI には、このための明確な機能は見つかっていない。
- そのため現時点では、ローカルサーバーを立て、ブラウザーで HTML 形式でエージェントの振る舞いを表示することが推奨されている。
- 例えば ASCII アートなどで、各エージェントの動作状況や、エージェント間のデータの受け渡しをリアルタイムで可視化すると、人間がヒューマン・オン・ザ・ループの振る舞いを監督しやすくなる。

### ユーザーの方針

- プラグインを作るときは、できるだけ HTML 形式でブラウザーで見やすくすることを心がけている。
- 1つのローカルサーバーで、次のすべてを HTML 形式で視覚的に表示することを心がけている。
  - ヒューマン・オン・ザ・ループを開始するまでの設定
  - 開始して動いている間のエージェントの振る舞いの可視化
  - 終わった後の結果やサマリー

### Web管理画面は、土台を用意して作り込みを支援する

- このようなローカルサーバー（Web管理画面）を、性能の低い AI モデルに一から作らせると、たいてい失敗する。
- 大事なのは、見た目のデザイン、機能、ローカルサーバーと Copilot CLI のスムーズな連携を、再現性高く作れることである。
- 画面の中身は生成プラグインごとに変わるが、土台は同じである。
- そのためクリエイターは、土台の設計を用意し、その上で、デザインの仕方、機能の作り込み方、Copilot CLI との連携を重点的に支援する（憲章 第15条）。
- ユーザーがこれまでに経験した失敗：
  - 見た目と機能：デザインが毎回ばらばらになる。表示が自動で更新されない（再読み込みが要る、途中で止まる）。見にくい、並びが崩れる。
  - Copilot CLI との連携：サーバーが起動しない、使う番号（ポート）がぶつかる、Copilot CLI を閉じてもサーバーが残る。開始ボタンでエージェントが動き出さない。止めるボタンで止まらない。エージェントの状態が画面に届かない、実際とずれる。
- これらが起きないことを、仕様の合格の条件にしている（出力の要件の REQ-005、REQ-008、REQ-009、REQ-029、REQ-030）。つなぎ方の候補は [画面と Copilot CLI のつなぎ方](dashboard-integration.md) にある。

## これからの技術者の役割

- コードを書くのではなく、ハーネスを設計し、ヒューマン・オン・ザ・ループの環境を作る。
- AI の振る舞いを監督し、適切なタイミングで介入して軌道修正する。
- ハーネスをメンテナンスする。

## ハーネスは人間が作る

- ハーネスとは、これまで人間がやっていたことを AI に自律的にやらせるための指示、手順、ルールなどである。
- AI が知らないことだから、人間がハーネスとして実装する必要がある。そのため、ハーネス自体を AI に 100% 作らせることはできず、人間のリソースを割く必要がある。
- AI がハーネスを自律的に作れるのなら、それはそもそもハーネスとして作る必要がなかったものかもしれない。
- ハーネスの設計では、AI と人間が密に対話し、人間からナレッジをきちんと引き出す必要がある。
